VM のブート順序とブートソースの構成

概要

本チュートリアルでは、OpenShift Virtualization で VM のブート順序、ブートソース、ブートオプションを構成する方法を説明します。ブート構成を理解することは、カスタム OS のインストール、レスキューおよびリカバリのシナリオ、マルチブート環境、セキュリティコンプライアンス要件において不可欠です。

ブート構成により、VM がどのデバイスから起動を試みるか、その順序や使用するファームウェアモード (BIOS または UEFI) を制御できます。OpenShift Virtualization は、永続ボリューム、コンテナイメージ、ネットワークベースのソースなど、さまざまなブートソースをサポートしています。

前提条件

  • OpenShift Virtualization Operator がインストールされた OpenShift 4.18 以降

  • CLI ツール: oc, virtctl, kubectl

  • VM のブートプロセスに関する基本的な理解

  • 永続ボリューム用に構成された Storage Class

  • コンテナレジストリの例を使用する場合: コンテナレジストリ (Quay.io、Docker Hub、または内部レジストリ) へのアクセス権

OpenShift Virtualization のブートソースタイプ

OpenShift Virtualization は、複数のブートソースタイプをサポートしています。

ブートソースタイプ 説明 ユースケース

PersistentVolumeClaim (PVC)

ストレージを基盤とする永続ディスクから起動

本番環境の VM、ステートフルなワークロード、カスタム OS のインストール

ContainerDisk

コンテナにパッケージ化されたディスクイメージから起動

一時的な VM、テスト、CI/CD、Immutable なワークロード

DataVolume

Containerized Data Importer (CDI) を介してプロビジョニングされたディスクから起動

HTTP、S3、レジストリソースからのイメージのインポート

CloudInitNoCloud

初期化ディスク (起動不可だが、ブートディスクと併用されるのが一般的)

VM の構成と初期化

ブートファームウェアモード

OpenShift Virtualization は、2 つのファームウェアモードをサポートしています。

BIOS (Legacy Mode)

  • 従来の PC BIOS ファームウェア

  • 古いオペレーティングシステムとの互換性あり

  • ブートデバイスのサイズ制限 (MBR で 2TB まで)

  • 起動時間が短い

  • ほとんどの Linux ディストリビューションのデフォルト

UEFI (Unified Extensible Firmware Interface)

  • モダンなファームウェアインターフェース

  • セキュアブートに必須

  • GPT パーティションテーブルと大容量ディスク (2TB 超) をサポート

  • Windows 11 および最新の Windows Server バージョンで必須

  • より優れたセキュリティ機能

ブートデバイス順序の理解

ブートデバイスの順序は、VM ファームウェアがブート可能なコンテンツをチェックするデバイスと、そのシーケンスを決定します。KubeVirt では、ディスクとインターフェースの bootOrder フィールドを使用してブート順序を制御します。

重要な概念:

  • bootOrder の数値が小さいほど優先度が高くなります (1 は 2 より先に起動)

  • ディスクとインターフェースのみにブート順序を指定可能

  • bootOrder が指定されていない場合、ファームウェアが決定します

  • 通常、プライマリブートディスクには bootOrder: 1 を割り当てます

シナリオ 1: PersistentVolumeClaim (PVC) からの起動 (最も一般的)

これは、永続ストレージを使用する本番 VM の標準構成です。

テスト用の namespace を作成します。

oc create namespace boot-demo
この例の cloud-init パスワードはデモ目的専用です。本番環境では、常に強力でユニークなパスワードまたは SSH キー認証を使用してください。

vm-boot-from-pvc.yaml をダウンロード

apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: vm-boot-pvc
  namespace: boot-demo
spec:
  dataVolumeTemplates:
    - apiVersion: cdi.kubevirt.io/v1beta1
      kind: DataVolume
      metadata:
        name: vm-boot-pvc-disk
      spec:
        sourceRef:
          kind: DataSource
          name: fedora
          namespace: openshift-virtualization-os-images
        storage:
          resources:
            requests:
              storage: 30Gi
  runStrategy: RerunOnFailure
  template:
    metadata:
      labels:
        kubevirt.io/domain: vm-boot-pvc
    spec:
      domain:
        cpu:
          cores: 2
        devices:
          disks:
            - disk:
                bus: virtio
              name: rootdisk
              bootOrder: 1
            - disk:
                bus: virtio
              name: cloudinitdisk
          interfaces:
            - masquerade: {}
              name: default
          rng: {}
        machine:
          type: pc-q35-rhel9.4.0
        memory:
          guest: 4Gi
      networks:
        - name: default
          pod: {}
      volumes:
        - dataVolume:
            name: vm-boot-pvc-disk
          name: rootdisk
        - cloudInitNoCloud:
            userData: |-
              #cloud-config
              user: fedora
              password: fedora123
              chpasswd: { expire: False }
              ssh_pwauth: True
          name: cloudinitdisk

重要ポイント:

  • rootdisk の bootOrder: 1 により、最初に起動することが保証されます

  • DataVolume が自動的に PVC をプロビジョニングしてデータを格納します

  • cloud-init ディスクは構成を提供しますが、ブート可能ではありません

  • ディスクへの変更は、VM の再起動後も保持されます

デプロイと検証:

oc apply -f vm-boot-from-pvc.yaml
oc get vm vm-boot-pvc -n boot-demo
oc get vmi vm-boot-pvc -n boot-demo

使用する場合:

  • 永続ストレージを必要とする本番ワークロード

  • 再起動後もデータを保持する必要がある VM

  • 従来のサーバーデプロイメント

  • 状態の永続性が必要な開発環境

シナリオ 2: ContainerDisk からの起動 (一時的)

ContainerDisk は、OCI コンテナ形式でディスクイメージをパッケージ化します。Immutable (不変) でステートレスなワークロードに最適です。

vm-boot-from-containerdisk.yaml をダウンロード

apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: vm-boot-containerdisk
  namespace: boot-demo
spec:
  runStrategy: RerunOnFailure
  template:
    metadata:
      labels:
        kubevirt.io/domain: vm-boot-containerdisk
    spec:
      domain:
        cpu:
          cores: 2
        devices:
          disks:
            - disk:
                bus: virtio
              name: containerdisk
              bootOrder: 1
            - disk:
                bus: virtio
              name: cloudinitdisk
          interfaces:
            - masquerade: {}
              name: default
          rng: {}
        machine:
          type: pc-q35-rhel9.4.0
        memory:
          guest: 4Gi
      networks:
        - name: default
          pod: {}
      volumes:
        - name: containerdisk
          containerDisk:
            image: quay.io/containerdisks/fedora:latest
        - cloudInitNoCloud:
            userData: |-
              #cloud-config
              user: fedora
              password: fedora123
              chpasswd: { expire: False }
              ssh_pwauth: True
          name: cloudinitdisk

重要な注意点:

  • ContainerDisk は一時的です。VM の停止時にすべての変更が失われます

  • レジストリからイメージがプルされるため、デプロイが高速です

  • テストや CI/CD パイプラインに最適

  • quay.io/containerdisks のパブリックイメージを使用するか、自作も可能です

デプロイ:

oc apply -f vm-boot-from-containerdisk.yaml

使用する場合:

  • テストおよび開発

  • CI/CD パイプライン

  • Immutable なインフラストラクチャパターン

  • 永続性が不要なシナリオ

  • ストレージのオーバーヘッドなしで素早く VM をプロビジョニングしたい場合

シナリオ 3: HTTP ソースの DataVolume からの起動

DataVolume を使用して HTTP/HTTPS ソースからブートイメージをインポートします。中央管理されたイメージから VM プロビジョニングを自動化するのに役立ちます。

vm-boot-from-http.yaml をダウンロード

apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: vm-boot-http
  namespace: boot-demo
spec:
  dataVolumeTemplates:
    - apiVersion: cdi.kubevirt.io/v1beta1
      kind: DataVolume
      metadata:
        name: vm-boot-http-disk
        annotations:
          cdi.kubevirt.io/storage.bind.immediate.requested: "true"
      spec:
        source:
          http:
            url: "https://download.fedoraproject.org/pub/fedora/linux/releases/43/Cloud/x86_64/images/Fedora-Cloud-Base-Generic-43-1.6.x86_64.qcow2"
        storage:
          resources:
            requests:
              storage: 30Gi
  runStrategy: RerunOnFailure
  template:
    metadata:
      labels:
        kubevirt.io/domain: vm-boot-http
    spec:
      domain:
        cpu:
          cores: 2
        devices:
          disks:
            - disk:
                bus: virtio
              name: rootdisk
              bootOrder: 1
            - disk:
                bus: virtio
              name: cloudinitdisk
          interfaces:
            - masquerade: {}
              name: default
          rng: {}
        machine:
          type: pc-q35-rhel9.4.0
        memory:
          guest: 4Gi
      networks:
        - name: default
          pod: {}
      volumes:
        - dataVolume:
            name: vm-boot-http-disk
          name: rootdisk
        - cloudInitNoCloud:
            userData: |-
              #cloud-config
              user: fedora
              password: fedora123
              chpasswd: { expire: False }
              ssh_pwauth: True
          name: cloudinitdisk

主な機能:

  • CDI が自動的にイメージをダウンロードおよび変換します

  • イメージは一度だけインポートされ、その後は PVC に格納されます

  • 次回以降の起動は PVC (永続ストレージ) を使用します

  • 一部の Storage Class では、アノテーション cdi.kubevirt.io/storage.bind.immediate.requested: "true" が必要です

インポートの進捗状況を監視:

oc apply -f vm-boot-from-http.yaml
oc get dv vm-boot-http-disk -n boot-demo --watch

使用する場合:

  • 自動化されたデプロイパイプライン

  • 中央レポジトリからのゴールデンイメージのインポート

  • 標準化された VM プロビジョニング

  • Web サーバーやオブジェクトストレージでイメージがホストされている場合

シナリオ 4: ブート順序を指定した複数のブートデバイス

複数のブート可能デバイスを明示的な順序で構成します。レスキューシナリオやマルチブート構成に役立ちます。

vm-multiple-boot-devices.yaml をダウンロード

apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: vm-multi-boot
  namespace: boot-demo
spec:
  dataVolumeTemplates:
    - apiVersion: cdi.kubevirt.io/v1beta1
      kind: DataVolume
      metadata:
        name: vm-multi-boot-primary
      spec:
        sourceRef:
          kind: DataSource
          name: fedora
          namespace: openshift-virtualization-os-images
        storage:
          resources:
            requests:
              storage: 30Gi
    - apiVersion: cdi.kubevirt.io/v1beta1
      kind: DataVolume
      metadata:
        name: vm-multi-boot-secondary
      spec:
        source:
          blank: {}
        storage:
          resources:
            requests:
              storage: 20Gi
  runStrategy: RerunOnFailure
  template:
    metadata:
      labels:
        kubevirt.io/domain: vm-multi-boot
    spec:
      domain:
        cpu:
          cores: 2
        devices:
          disks:
            - disk:
                bus: virtio
              name: primarydisk
              bootOrder: 1
            - disk:
                bus: virtio
              name: secondarydisk
              bootOrder: 2
            - cdrom:
                bus: sata
              name: installcdrom
              bootOrder: 3
            - disk:
                bus: virtio
              name: cloudinitdisk
          interfaces:
            - masquerade: {}
              name: default
          rng: {}
        machine:
          type: pc-q35-rhel9.4.0
        memory:
          guest: 4Gi
      networks:
        - name: default
          pod: {}
      volumes:
        - dataVolume:
            name: vm-multi-boot-primary
          name: primarydisk
        - dataVolume:
            name: vm-multi-boot-secondary
          name: secondarydisk
        - name: installcdrom
          containerDisk:
            image: quay.io/containerdisks/fedora:latest
        - cloudInitNoCloud:
            userData: |-
              #cloud-config
              user: fedora
              password: fedora123
              chpasswd: { expire: False }
              ssh_pwauth: True
          name: cloudinitdisk

ブートシーケンスの説明:

  1. bootOrder: 1 - プライマリディスク (最初に起動を試みる)

  2. bootOrder: 2 - セカンダリディスク (プライマリが失敗した場合のフォールバック)

  3. bootOrder: 3 - CD-ROM (インストールメディア、最後の手段)

デプロイ:

oc apply -f vm-multiple-boot-devices.yaml

使用する場合:

  • 災害復旧 (DR) シナリオ

  • カスタム OS のインストール

  • さまざまな OS 構成のテスト

  • フォールバックブートオプションを必要とする環境

シナリオ 5: UEFI ブートモード

従来の BIOS ではなく UEFI ファームウェアを使用するように VM を構成します。セキュアブートや最新の Windows バージョンに必要です。

vm-boot-uefi.yaml をダウンロード

apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: vm-boot-uefi
  namespace: boot-demo
spec:
  dataVolumeTemplates:
    - apiVersion: cdi.kubevirt.io/v1beta1
      kind: DataVolume
      metadata:
        name: vm-boot-uefi-disk
      spec:
        sourceRef:
          kind: DataSource
          name: fedora
          namespace: openshift-virtualization-os-images
        storage:
          resources:
            requests:
              storage: 30Gi
  runStrategy: RerunOnFailure
  template:
    metadata:
      labels:
        kubevirt.io/domain: vm-boot-uefi
    spec:
      domain:
        cpu:
          cores: 2
        devices:
          disks:
            - disk:
                bus: virtio
              name: rootdisk
              bootOrder: 1
            - disk:
                bus: virtio
              name: cloudinitdisk
          interfaces:
            - masquerade: {}
              name: default
          rng: {}
        firmware:
          bootloader:
            efi:
              secureBoot: false
        machine:
          type: pc-q35-rhel9.4.0
        memory:
          guest: 4Gi
      networks:
        - name: default
          pod: {}
      volumes:
        - dataVolume:
            name: vm-boot-uefi-disk
          name: rootdisk
        - cloudInitNoCloud:
            userData: |-
              #cloud-config
              user: fedora
              password: fedora123
              chpasswd: { expire: False }
              ssh_pwauth: True
          name: cloudinitdisk

主な構成:

  • firmware.bootloader.efi が UEFI モードを有効にします

  • secureBoot: false - セキュアブートは無効です (サポートされている OS では有効化可能)

  • マシンタイプ pc-q35-rhel9.4.0 は UEFI と互換性があります

デプロイ:

oc apply -f vm-boot-uefi.yaml

使用する場合:

  • Windows 11 または最新の Windows Server VM

  • セキュアブートを必要とするシステム

  • 大容量ディスク (2TB 超) のサポート

  • 強化されたセキュリティ要件

  • UEFI を推奨するモダンな Linux ディストリビューション

シナリオ 6: セキュアブート付き UEFI (上級者向け)

セキュアブートは、ブートプロセス中に未承認のコードが実行されるのを防ぎます。これには UEFI ファームウェアと互換性のあるオペレーティングシステムが必要です。

vm-boot-uefi-secureboot.yaml をダウンロード

apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: vm-boot-secureboot
  namespace: boot-demo
spec:
  dataVolumeTemplates:
    - apiVersion: cdi.kubevirt.io/v1beta1
      kind: DataVolume
      metadata:
        name: vm-boot-secureboot-disk
      spec:
        sourceRef:
          kind: DataSource
          name: fedora
          namespace: openshift-virtualization-os-images
        storage:
          resources:
            requests:
              storage: 30Gi
  runStrategy: RerunOnFailure
  template:
    metadata:
      labels:
        kubevirt.io/domain: vm-boot-secureboot
    spec:
      domain:
        cpu:
          cores: 2
        devices:
          disks:
            - disk:
                bus: virtio
              name: rootdisk
              bootOrder: 1
            - disk:
                bus: virtio
              name: cloudinitdisk
          interfaces:
            - masquerade: {}
              name: default
          rng: {}
        firmware:
          bootloader:
            efi:
              secureBoot: true
        machine:
          type: pc-q35-rhel9.4.0
        memory:
          guest: 4Gi
        features:
          smm:
            enabled: true
      networks:
        - name: default
          pod: {}
      volumes:
        - dataVolume:
            name: vm-boot-secureboot-disk
          name: rootdisk
        - cloudInitNoCloud:
            userData: |-
              #cloud-config
              user: fedora
              password: fedora123
              chpasswd: { expire: False }
              ssh_pwauth: True
          name: cloudinitdisk

重要な要件:

  • secureBoot: true がセキュアブートを有効にします

  • features.smm.enabled: true がセキュアブート (System Management Mode) に必要です

  • オペレーティングシステムがセキュアブートをサポートしている必要があります (ほとんどの最新 Linux および Windows)

  • ブートローダーとカーネルが信頼されたキーで署名されている必要があります

デプロイ:

oc apply -f vm-boot-uefi-secureboot.yaml

使用する場合:

  • セキュリティコンプライアンス要件

  • Windows 11 (セキュアブートが必要)

  • 厳格なブート整合性要件がある環境

  • ルートキットやブートレベルのマルウェアに対する防御

すべてのオペレーティングシステムがセキュアブートをサポートしているわけではありません。VM が起動しない場合は、セキュアブートを無効にして、標準の UEFI を使用してください。

シナリオ 7: ネットワークブート (PXE)

PXE (Preboot Execution Environment) を使用してネットワークから起動するように VM を構成します。OS の自動インストールやディスクレスワークステーションに役立ちます。

vm-boot-pxe.yaml をダウンロード

apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: vm-boot-pxe
  namespace: boot-demo
spec:
  dataVolumeTemplates:
    - apiVersion: cdi.kubevirt.io/v1beta1
      kind: DataVolume
      metadata:
        name: vm-boot-pxe-disk
      spec:
        source:
          blank: {}
        storage:
          resources:
            requests:
              storage: 30Gi
  runStrategy: RerunOnFailure
  template:
    metadata:
      labels:
        kubevirt.io/domain: vm-boot-pxe
    spec:
      domain:
        cpu:
          cores: 2
        devices:
          disks:
            - disk:
                bus: virtio
              name: rootdisk
              bootOrder: 2
            - disk:
                bus: virtio
              name: cloudinitdisk
          interfaces:
            - masquerade: {}
              name: default
            - bridge: {}
              name: pxe-net
              bootOrder: 1
          rng: {}
        machine:
          type: pc-q35-rhel9.4.0
        memory:
          guest: 4Gi
      networks:
        - name: default
          pod: {}
        - name: pxe-net
          multus:
            networkName: pxe-network
      volumes:
        - dataVolume:
            name: vm-boot-pxe-disk
          name: rootdisk
        - cloudInitNoCloud:
            userData: |-
              #cloud-config
              user: fedora
              password: fedora123
              chpasswd: { expire: False }
              ssh_pwauth: True
          name: cloudinitdisk

主な構成:

  • セカンダリネットワークインターフェース (pxe-net) に bootOrder: 1 を設定 (ディスクより先に起動)

  • ディスクに bootOrder: 2 を設定 (ネットワークブート試行後のフォールバック)

  • Multus を介して構成されたセカンダリネットワーク (例: pxe-network) が必要

  • 直接的なネットワークアクセスにブリッジインターフェースバインディングを使用

  • プライマリ Pod ネットワーク (default) は一般的な接続用として維持

PXE ブートの前提条件:

  • セカンダリネットワークが構成されておりアクセス可能であること (ネットワークチュートリアルを参照)

  • セカンダリネットワーク上で PXE サーバーが構成されていること

  • DHCP サーバーがブート情報を提供していること

  • TFTP サーバーがブートファイルを提供していること

  • VM と PXE インフラストラクチャ間のネットワーク接続

使用する場合:

  • 自動化された OS インストール

  • ディスクレスワークステーション環境

  • ネットワークベースのリカバリシステム

  • 大規模な自動化デプロイ

ブートメニューの構成

VM 起動時にブートデバイスを選択できる対話型ブートメニューを有効にできます。

vm-boot-menu.yaml をダウンロード

apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: vm-boot-menu
  namespace: boot-demo
spec:
  dataVolumeTemplates:
    - apiVersion: cdi.kubevirt.io/v1beta1
      kind: DataVolume
      metadata:
        name: vm-boot-menu-disk
      spec:
        sourceRef:
          kind: DataSource
          name: fedora
          namespace: openshift-virtualization-os-images
        storage:
          resources:
            requests:
              storage: 30Gi
  runStrategy: RerunOnFailure
  template:
    metadata:
      labels:
        kubevirt.io/domain: vm-boot-menu
    spec:
      domain:
        cpu:
          cores: 2
        devices:
          disks:

                bus: virtio
              name: rootdisk
              bootOrder: 1
            - cdrom:
                bus: sata
              name: installcdrom
              bootOrder: 2
            - disk:
                bus: virtio
              name: cloudinitdisk
          interfaces:
            - masquerade: {}
              name: default
          rng: {}
        firmware:
          bootloader:
            bios:
              useSerial: true
        machine:
          type: pc-q35-rhel9.4.0
        memory:
          guest: 4Gi
      networks:
        - name: default
          pod: {}
      volumes:
        - dataVolume:
            name: vm-boot-menu-disk
          name: rootdisk
        - name: installcdrom
          containerDisk:
            image: quay.io/containerdisks/fedora:latest
        - cloudInitNoCloud:
            userData: |-
              #cloud-config
              user: fedora
              password: fedora123
              chpasswd: { expire: False }
              ssh_pwauth: True
          name: cloudinitdisk

ブートメニューへのアクセス:

oc apply -f vm-boot-menu.yaml

# VNC経由でアクセスしてブートメニューを表示
virtctl vnc vm-boot-menu -n boot-demo

# またはコンソール経由
virtctl console vm-boot-menu -n boot-demo

  • 起動中に ESC または F12 を押してブートメニューにアクセス

  • 利用可能なオプションからブートデバイスを選択

  • useSerial: true により、シリアルコンソール経由でブートメニューにアクセス可能になります

一般的な問題と解決策

問題: 指定されたデバイスから VM が起動しない

事象: VM が bootOrder: 1 を持つデバイスから起動しない。

解決策:

  • デバイスが実際にブート可能 (ブートローダーがある) か確認

  • デバイスが VM に正しく接続されているか確認

  • VM イベントを確認:

oc describe vmi vm-boot-pvc -n boot-demo

  • コンソールにアクセスしてエラーメッセージを確認:

virtctl console vm-boot-pvc -n boot-demo

問題: セキュアブートにより VM が起動しない

事象: secureBoot: true を設定した VM が起動しない、またはブートエラーを表示する。

解決策:

  • OS がセキュアブートをサポートしていることを確認

  • フィーチャーで smm.enabled: true が設定されているか確認

  • 問題を切り分けるためにセキュアブートを一時的に無効にしてみる

  • ブートローダーとカーネルが適切に署名されているか確認

# VMを編集してセキュアブートを無効化
oc edit vm vm-boot-secureboot -n boot-demo
# secureBoot: true を secureBoot: false に変更

問題: PXE ブートが機能しない

事象: PXE ブート用に構成された VM がブート情報を受信しない。

解決策:

  • PXE サーバーがネットワークからアクセス可能か確認

  • DHCP が PXE ブートオプションを提供するように構成されているか確認

  • VM ネットワークインターフェースがブリッジバインディングを使用していることを確認

  • ファイアウォールルールが PXE トラフィック (DHCP、TFTP) を許可しているか確認

  • ネットワークインターフェースに bootOrder が設定されていることを確認

問題: ContainerDisk イメージのプルに失敗する

事象: ContainerDisk を使用する VM がイメージプルエラーで失敗する。

解決策:

  • コンテナイメージが存在し、アクセス可能であることを確認

  • プライベートレジストリを使用している場合は、イメージプルシークレットを確認

  • イメージが正しい形式 (コンテナ内の /disk/ パスにあるディスク) であることを確認

# Podイベントの確認
oc get events -n boot-demo
# virt-launcher Podログの確認 (最初に実際のPod名を確認)
oc get pods -n boot-demo
oc logs -n boot-demo virt-launcher-vm-boot-containerdisk-xxxxx

問題: HTTP DataVolume インポートが失敗する

事象: HTTP ソースを持つ DataVolume が ImportInProgress でスタックするか失敗する。

解決策:

  • URL がクラスターからアクセス可能であることを確認

  • 十分なストレージクォータがあることを確認

  • Storage Class が動的プロビジョニングをサポートしていることを確認

  • 必要に応じて即時バインディング用のアノテーションを追加

# DataVolumeステータスの確認
oc get dv -n boot-demo
oc describe dv vm-boot-http-disk -n boot-demo

# Importer Podログの確認 (最初に実際のPod名を確認)
oc get pods -n boot-demo
oc logs -n boot-demo importer-vm-boot-http-disk-xxxxx

# 必要に応じてCDIコントローラーログを確認
oc get pods -n openshift-cnv | grep cdi-deployment
oc logs -n openshift-cnv cdi-deployment-xxxxx

ベストプラクティス

ブート順序の構成

  • プライマリブートデバイスには必ず bootOrder を明示的に設定する

  • 1、2、3 のように順番に番号を振る (番号を飛ばさない)

  • VM アノテーションまたはラベルにブートシーケンスをドキュメント化する

  • コンソール経由で BIOS/UEFI セットアップにアクセスしてブート順序をテストする

ファームウェアの選択

  • 新規デプロイメントには UEFI を使用する (優れたセキュリティ、モダンな機能)

  • BIOS は古いオペレーティングシステムとの互換性のためにのみ使用する

  • セキュアブートは、必要であり、OS がサポートしている場合のみ有効にする

  • セキュアブートを使用する場合は、常に SMM を有効にする

ブートソースの選択

  • 永続性を必要とする本番ワークロードには PVC を使用する

  • 一時的で Immutable なワークロードには ContainerDisk を使用する

  • 中央レポジトリからの自動デプロイには HTTP DataVolume を使用する

  • カスタムイメージはバージョン管理のために ContainerDisk としてパッケージ化する

セキュリティ

  • Windows 11 やセキュリティに敏感なワークロードにはセキュアブートを有効にする

  • 強化されたセキュリティ機能のためには BIOS ではなく UEFI を使用する

  • セキュリティパッチを含めるためにブートイメージを定期的に更新する

  • デプロイ前にコンテナイメージの脆弱性をスキャンする

パフォーマンス

  • ディスクパフォーマンス向上のために virtio バスを使用する

  • パフォーマンスチューニングにはディスクキャッシングモードを検討する

  • 適切な Storage Class を使用する (ブートディスクには SSD)

  • VM 起動を高速化するために PVC を事前プロビジョニングする

クリーンアップ

本チュートリアルで作成されたすべてのリソースを削除するには:

# すべてのVMを削除
oc delete vm --all -n boot-demo

# namespaceを削除
oc delete namespace boot-demo
VM を削除すると、関連付けられた DataVolume と PVC も削除され、データが失われます。
