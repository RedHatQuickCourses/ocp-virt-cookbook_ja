ローカルの qcow2 イメージからブートボリュームを作成する

概要

このチュートリアルでは、既存の qcow2 ディスクイメージをローカルの KVM プラットフォームから OpenShift Virtualization にインポートして、ブートボリュームを作成する方法を説明します。これは、他の仮想化プラットフォームから仮想マシン (VM) を移行する場合や、OVA 形式では利用できないカスタム OS テンプレートをデプロイする場合に特に役立ちます。

qcow2 (QEMU Copy-On-Write version 2) は、KVM やその他の QEMU ベースの仮想化プラットフォームで一般的に使用されるディスクイメージ形式です。これらのイメージをインポートすることで、既存のワークロードを OpenShift Virtualization へ迅速に移行できます。

このチュートリアルは、OpenShift Virtualization を導入した OpenShift 4.18.33 環境で、AWS EBS gp3-csi ストレージクラスを使用してテストされています。

前提条件

  • OpenShift 4.18 以降と OpenShift Virtualization Operator のインストール

  • CLI ツール: oc, virtctl

  • qemu-img (オプション) - qcow2 イメージの詳細をローカルで調査するために使用

  • ローカルで利用可能な (または HTTP/S3 経由でアクセス可能な) qcow2 イメージファイル

  • ストレージクラスの設定 - 動的なボリュームプロビジョニング用

  • namespace 内の十分なストレージクォータ

インポート方法の概要

qcow2 イメージを OpenShift Virtualization にインポートする主な方法は 4 つあります。

方法 用途 主な特徴

virtctl image-upload

ワークステーションからの単発インポート

最もシンプルな手法。DataVolume/PVC へ直接アップロード

DataVolume with HTTP/S3

共有イメージや自動化

Web サーバー上のイメージを指定し、DataVolume が自動的にプル

ContainerDisk

イミュータブルでバージョン管理されたイメージ

コンテナイメージとして qcow2 をパッケージ化し、レジストリへプッシュ

VM with DataVolumeTemplate

アップロードを伴う VM 作成

VM spec にアップロードソースを含む DataVolumeTemplate を組み込む

このチュートリアルでは、導入として最も分かりやすい virtctl image-upload メソッドに焦点を当てます。その他の方法は後のセクションで扱います。

ステップ 1: qcow2 イメージの準備

インポートの前に、qcow2 イメージが OpenShift Virtualization に適した状態であることを確認してください。

イメージのダウンロードまたは場所の特定

このチュートリアルでは、例として Fedora Cloud イメージを使用します。自身の qcow2 イメージに置き換えて実行できます。

# Download Fedora Cloud image (example)
curl -LO https://download.fedoraproject.org/pub/fedora/linux/releases/43/Cloud/x86_64/images/Fedora-Cloud-Base-Generic-43-1.6.x86_64.qcow2

# Verify the image
ls -lh Fedora-Cloud-Base-Generic-43-1.6.x86_64.qcow2

イメージ詳細の確認 (オプション)

ローカルに qemu-img がインストールされている場合は、イメージを調査できます。

qemu-img info Fedora-Cloud-Base-Generic-43-1.6.x86_64.qcow2

出力例:

image: Fedora-Cloud-Base-Generic-43-1.6.x86_64.qcow2
file format: qcow2
virtual size: 5 GiB (5368709120 bytes)
disk size: 420 MiB

Virtual size に注意してください。DataVolume を作成する際は、少なくともこの容量以上のストレージを指定する必要があります。

ステップ 2: namespace の作成

インポートする VM 用の namespace を作成します。

oc create namespace imported-vms

ステップ 3: virtctl を使用した qcow2 イメージのアップロード

virtctl を使用して qcow2 イメージを直接アップロードします。PVC は自動的に作成されます。

virtctl image-upload pvc fedora-imported-disk \
  --image-path=./Fedora-Cloud-Base-Generic-43-1.6.x86_64.qcow2 \
  --size=10Gi \
  --namespace=imported-vms \
  --insecure \
  --force-bind

コマンドパラメーターの説明:

  • pvc fedora-imported-disk - 作成される PVC の名前

  • --image-path - ローカルの qcow2 ファイルへのパス

  • --size - 作成する PVC のサイズ (qcow2 イメージの Virtual size 以上である必要があります)

  • --namespace - 対象の namespace

  • --insecure - TLS 検証をスキップ (自己署名証明書を使用する場合)

  • --force-bind - PVC の即時バインドを強制 (WaitForFirstConsumer モードの StorageClass で必須)

重要: --force-bind フラグは、volumeBindingMode: WaitForFirstConsumer を使用する StorageClass (AWS EBS、Azure Disk、その他のクラウドプロバイダーで一般的) を使用する場合に必須です。このフラグがないと、PVC が保留 (pending) 状態のままとなり、アップロードが開始されません。

アップロードの進行状況の出力:

PVC imported-vms/fedora-imported-disk created
Uploading data to https://cdi-uploadproxy-openshift-cnv.apps...

 420.00 MiB / 420.00 MiB [=================================] 100.00% 1m30s

Uploading data completed successfully, waiting for processing to complete
Processing completed successfully
アップロード時間はイメージのサイズとネットワーク速度に依存します。1GB のイメージであれば、通常 1〜3 分程度かかります。

アップロード進行状況の監視

別のターミナルで、PVC のステータスを確認することでアップロードプロセスを監視できます。

oc get pvc fedora-imported-disk -n imported-vms --watch

アップロード中、PVC が Pending から Bound へ移行するのがわかります。

NAME                   STATUS    VOLUME                                     CAPACITY   ACCESS MODES
fedora-imported-disk   Pending
fedora-imported-disk   Bound     pvc-xxxxx                                  10Gi       RWO

必要に応じて cdi-upload Pod のログを確認してください。

oc get pods -n imported-vms
oc logs -n imported-vms cdi-upload-fedora-imported-disk -f

ステップ 4: インポートしたブートボリュームを使用した VM の作成

イメージのアップロードが完了したので、その PVC をブートディスクとして使用する VM を作成します。

この例の cloud-init パスワードはデモ目的のみです。本番環境では、常に強力で一意のパスワードを使用するか、SSH キー認証を使用してください。

vm-from-imported-qcow2.yaml をダウンロード

apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: fedora-imported-vm
  namespace: imported-vms
  labels:
    app: fedora-imported
spec:
  runStrategy: RerunOnFailure
  template:
    metadata:
      labels:
        kubevirt.io/domain: fedora-imported-vm
    spec:
      domain:
        cpu:
          cores: 2
        devices:
          disks:
            - disk:
                bus: virtio
              name: rootdisk
            - disk:
                bus: virtio
              name: cloudinitdisk
          interfaces:
            - masquerade: {}
              name: default
          rng: {}
        machine:
          type: pc-q35-rhel9.4.0
        memory:
          guest: 4Gi
      networks:
        - name: default
          pod: {}
      volumes:
        - name: rootdisk
          persistentVolumeClaim:
            claimName: fedora-imported-disk
        - name: cloudinitdisk
          cloudInitNoCloud:
            userData: |-
              #cloud-config
              user: fedora
              password: fedora123
              chpasswd: { expire: false }
              ssh_pwauth: true

VM マニフェストを適用します。

oc apply -f vm-from-imported-qcow2.yaml

VM を起動します。

virtctl start fedora-imported-vm -n imported-vms

ステップ 5: VM が実行中であることを確認

VM の起動を監視します。

oc get vmi -n imported-vms --watch

VM が起動し、実行中であることを示す出力:

NAME                 AGE   PHASE       IP             NODENAME    READY
fedora-imported-vm   15s   Scheduling                             False
fedora-imported-vm   30s   Scheduled                  worker-01   False
fedora-imported-vm   45s   Running     10.128.2.54    worker-01   True

VM コンソールにアクセスします。

virtctl console fedora-imported-vm -n imported-vms

cloud-init で設定した資格情報 (ユーザー: fedora、パスワード: fedora123) でログインします。

インポートしたイメージからシステムが起動したことを確認します。

# Check OS version
cat /etc/os-release

# Check disk configuration
lsblk

Ctrl+] でコンソールを終了します。

その他のインポート方法

virtctl image-upload は最もシンプルな方法ですが、ユースケースに応じて他にも手法があります。

方法 2: HTTP ソースを指定した DataVolume

qcow2 イメージに HTTP/HTTPS 経由でアクセスできる場合、DataVolume を使用して CDI に自動ダウンロードおよびインポートさせることができます。この方法は、公開されているクラウドイメージや、社内 Web サーバーでホストされているイメージを使用する場合に非常に有効です。

公式の Fedora Cloud イメージを使用する例:

datavolume-http-import.yaml をダウンロード

apiVersion: cdi.kubevirt.io/v1beta1
kind: DataVolume
metadata:
  name: fedora-http-imported
  namespace: imported-vms
  annotations:
    cdi.kubevirt.io/storage.bind.immediate.requested: "true"
spec:
  source:
    http:
      url: "https://download.fedoraproject.org/pub/fedora/linux/releases/43/Cloud/x86_64/images/Fedora-Cloud-Base-Generic-43-1.6.x86_64.qcow2"
  storage:
    resources:
      requests:
        storage: 10Gi
アノテーション cdi.kubevirt.io/storage.bind.immediate.requested: "true" は PVC の即時バインドを強制します。これは WaitForFirstConsumer モードの StorageClass を使用する場合に必須です。

DataVolume を適用すると、CDI が自動的にイメージをダウンロードしてインポートします。

oc apply -f datavolume-http-import.yaml
oc get dv -n imported-vms --watch

ダウンロードの進行状況を監視します。

NAME                   PHASE              PROGRESS   RESTARTS   AGE
fedora-http-imported   ImportScheduled    N/A                   5s
fedora-http-imported   ImportInProgress   12.5%                 15s
fedora-http-imported   ImportInProgress   67.3%                 45s
fedora-http-imported   Succeeded          100.0%                1m30s

DataVolume が Succeeded になったら、それを参照する VM を作成できます。

volumes:
  - name: rootdisk
    dataVolume:
      name: fedora-http-imported

ヒント: この方法は手動のアップロードが不要なため、自動化や CI/CD パイプラインに最適です。適切な資格情報を設定すれば S3 URL も使用できます。

方法 3: ContainerDisk

バージョン管理されたイミュータブルなイメージを作成するには、qcow2 をコンテナイメージとしてパッケージ化します。

Containerfile を作成します。

FROM scratch
ADD Fedora-Cloud-Base-Generic-43-1.6.x86_64.qcow2 /disk/

ビルドしてプッシュします。

podman build -t quay.io/youruser/fedora-disk:v1 .
podman push quay.io/youruser/fedora-disk:v1

VM spec で使用します。

volumes:
  - name: rootdisk
    containerDisk:
      image: quay.io/youruser/fedora-disk:v1
ContainerDisk は一時的なものです。変更は VM 停止時に失われるため、個別の Persistent Volume をアタッチしない限り保持されません。

方法 4: DataVolumeTemplate とアップロードソースを用いた VM

この方法は、DataVolumeTemplate を使用して、VM 作成とアップロード機能を組み合わせます。DataVolume は VM spec 内にインラインで定義され、VM 作成時に自動的に作成されます。

用途: - VM とそのストレージを単一のマニフェストで定義したい - GitOps や宣言的なワークフローを使用している - DataVolume のライフサイクルを VM に連動させたい

vm-with-upload-datavolume.yaml をダウンロード

apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: vm-with-upload
  namespace: imported-vms
spec:
  dataVolumeTemplates:
    - apiVersion: cdi.kubevirt.io/v1beta1
      kind: DataVolume
      metadata:
        name: vm-with-upload-disk
      spec:
        source:
          upload: {}
        storage:
          resources:
            requests:
              storage: 10Gi
  runStrategy: RerunOnFailure
  template:
    metadata:
      labels:
        kubevirt.io/domain: vm-with-upload
    spec:
      domain:
        cpu:
          cores: 2
        devices:
          disks:
            - disk:
                bus: virtio
              name: rootdisk
          interfaces:
            - masquerade: {}
              name: default
          rng: {}
        machine:
          type: pc-q35-rhel9.4.0
        memory:
          guest: 4Gi
      networks:
        - name: default
          pod: {}
      volumes:
        - dataVolume:
            name: vm-with-upload-disk
          name: rootdisk

VM を作成します。これにより VM と DataVolume の両方が作成されます。

oc apply -f vm-with-upload-datavolume.yaml

DataVolume は作成されますが、ディスクにデータがないため VM はまだ起動しません。ここでイメージをアップロードします。

virtctl image-upload dv vm-with-upload-disk \
  --image-path=./Fedora-Cloud-Base-Generic-43-1.6.x86_64.qcow2 \
  --size=10Gi \
  --namespace=imported-vms \
  --insecure \
  --force-bind

アップロードが完了したら、VM を起動します。

virtctl start vm-with-upload -n imported-vms

メリット: - 単一マニフェストで VM とストレージの両方を定義できる - DataVolume のライフサイクルが VM とともに管理される - Infrastructure-as-Code ワークフローに適している

デメリット: - PVC を個別に作成するよりも複雑 - VM 作成後にアップロードを行う必要がある - DataVolume/virtctl の互換性問題の影響を受ける可能性がある

ベストプラクティス

イメージの準備

  • イメージ整合性の検証 - アップロード前にチェックサムを確認

  • イメージサイズの最適化 - virt-sparsify を使用して qcow2 ファイルサイズを削減

  • 機密データの削除 - 資格情報やマシン固有の設定をクリーンアップ

  • cloud-init のインストール - 適切な初期化のために cloud-init がインストールされていることを確認

ストレージのサイジング

  • 拡張性を考慮 - VM 操作を見越して、Virtual size よりも多くのストレージを割り当て

  • シンプロビジョニング - 利用可能な場合、シンプロビジョニングをサポートするストレージクラスを使用

  • 使用状況の監視 - 定期的に PVC の使用状況を追跡

セキュリティ

  • イメージスキャン - インポート前に qcow2 イメージの脆弱性をスキャン

  • TLS の利用 - 可能であれば --insecure フラグを外し、適切な証明書を設定

  • アクセス制御 - RBAC を使用してイメージアップロード権限を制御

  • 暗号化ストレージ - 保存時の暗号化をサポートするストレージクラスを検討

パフォーマンス

  • ローカルアップロード - 速度を向上させるため、クラスターネットワーク内からアップロード

  • 並列インポート - 帯域幅が許す限り、複数のイメージを同時にインポート

  • ネットワーク配置 - 最適な転送速度のため、アップロード元とクラスターを近接させる

トラブルシューティング

アップロードが "Waiting for PVC upload pod to be ready" で停止する

アップロードが Pod を待機したままになり、PVC が "WaitForFirstConsumer" ステータスになる場合は、StorageClass の binding mode の問題です。

PVC のステータスを確認します。

oc get pvc -n imported-vms
oc describe pvc fedora-imported-disk -n imported-vms

イベントに "waiting for first consumer to be created before binding" と表示されている場合、StorageClass に volumeBindingMode: WaitForFirstConsumer が設定されています。

解決策: virtctl コマンドに --force-bind フラグを追加します。

virtctl image-upload pvc fedora-imported-disk \
  --image-path=./image.qcow2 \
  --size=10Gi \
  --namespace=imported-vms \
  --insecure \
  --force-bind

スタックした PVC を削除してから再度実行してください。

oc delete pvc fedora-imported-disk -n imported-vms

その後、--force-bind をつけて再試行します。

アップロードが "Unable to get PVC Prime name from PVC" で失敗する

このエラーは、DataVolume ベースのアップロードを使用する特定の CDI バージョンで発生する可能性があります。解決策は、代わりに PVC メソッドを使用することです (このチュートリアルで採用している方法です) 。

# Use PVC upload (not DataVolume)
virtctl image-upload pvc <pvc-name> \
  --image-path=./image.qcow2 \
  --size=10Gi \
  --namespace=imported-vms \
  --insecure

一般的な原因: * CDI Operator の問題: cdi-deployment と cdi-operator Pod が実行されているか確認 * Storage Class の問題: StorageClass がボリュームをプロビジョニングできることを確認

CDI Pod の状態を確認します。

oc get pods -n openshift-cnv | grep cdi

アップロードがスタックする、または非常に低速

CDI upload proxy Pod の状態を確認します。

oc get pods -n openshift-cnv | grep cdi-uploadproxy
oc logs -n openshift-cnv <cdi-uploadproxy-pod>

ワークステーションからクラスターへのネットワーク接続を確認してください。

PVC サイズ不足エラー

--size パラメーターは、qcow2 イメージの Virtual size よりも大きくする必要があります。

qemu-img info image.qcow2 | grep "virtual size"

サイズ不足でアップロードが失敗した場合は、PVC を削除して、より大きなサイズで再試行します。

oc delete pvc fedora-imported-disk -n imported-vms

# Retry upload with larger --size parameter
virtctl image-upload pvc fedora-imported-disk \
  --image-path=./image.qcow2 \
  --size=20Gi \
  --namespace=imported-vms \
  --insecure

VM がインポートしたイメージから起動しない

VM のイベントとログを確認します。

oc describe vm fedora-imported-vm -n imported-vms
oc get events -n imported-vms --field-selector involvedObject.name=fedora-imported-vm

コンソールにアクセスして起動メッセージを確認します。

virtctl console fedora-imported-vm -n imported-vms

一般的な原因: * イメージが破損している - チェックサムを確認 * マシンの種類が誤っている - VM spec で machine.type を調整 * ブートローダーがない - イメージに適切なブート設定があるか確認

クリーンアップ

このチュートリアルで作成したリソースを削除するには以下を実行します。

# Delete the VM
oc delete vm fedora-imported-vm -n imported-vms

# Delete the PVC
oc delete pvc fedora-imported-disk -n imported-vms

# Delete the namespace
oc delete namespace imported-vms
PVC を削除すると、インポートしたイメージデータは完全に削除されます。必要に応じてバックアップがあることを確認してください。
