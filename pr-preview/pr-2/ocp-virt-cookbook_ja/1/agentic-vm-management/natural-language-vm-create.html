自然言語による仮想マシンの作成

このチュートリアルでは、vm-create エージェントスキルを使用して、自然言語コマンドで仮想マシンを作成する方法を説明します。エージェントは、VM 要件に関する人間が判読可能な説明を解釈し、不足しているパラメーターを対話形式の質問を通じて収集し、適切なインスタンスタイプ、OS の選択、ストレージ設定、スケジューリングを備えた完全な KubeVirt VirtualMachine リソースに変換します。

前提条件

  • AI エージェントによる VM 管理の開始 チュートリアルを完了していること (スキルパックがインストール済み、MCP サーバーが設定済み、クラスターへの接続が確認済みであること)

  • OpenShift Virtualization がインストールされた OpenShift クラスター

  • KUBECONFIG 環境変数が設定され、有効な kubeconfig ファイルを参照していること

  • VirtualMachine リソースを作成する権限を持つ namespace

このチュートリアルで使用する namespace がまだ存在しない場合は作成します。

oc create namespace my-vms
oc create namespace development

仕組み

vm-create スキルは、6 つのステップからなるワークフローに従います。

  1. 要件の収集 — エージェントは対話型の質問を通じて VM パラメーターを収集します。単一のプロンプトですべてを指定することも (例: "Create a Fedora VM named web-01 in namespace dev")、エージェントに必要な詳細を 1 つずつ質問させることもできます。指定しなかったパラメーターには適切なデフォルト値が使用されます。

  2. 競合の確認 — エージェントは、ターゲット namespace 内に同じ名前の VM がまだ存在していないことを検証します。競合が見つかった場合は、別の名前を選択するか、既存の VM を削除するか、キャンセルするかを選択できます。

  3. 確認用の構成の提示 — エージェントは、使用されるすべてのパラメーターを示す概要テーブルを表示します。リソースが作成される前に、確認、キャンセル、または個々の値を変更できます。

  4. VM の作成 — 明示的な確認の後、エージェントは vm_create MCP ツールを呼び出して VirtualMachine リソースを作成します。

  5. 検証と診断 — エージェントは VM のステータスを確認します。スケジューリングまたはストレージのエラー (例: ErrorUnschedulable、ErrorDataVolumeNotReady) が発生した場合、エージェントはトラブルシューティングナレッジベースを自動的に参照し、根本原因を診断して、承認用の回避策を提案します。

  6. ステータスのレポート — エージェントは VM が正常に作成されたかどうかをレポートし、デフォルトの認証情報や接続方法を含むアクセス手順を提供します。

サンプルシナリオ 3: マルチノードクラスターでのエラー診断

このシナリオでは、エージェントの自動エラー診断機能について説明します。これには、 Worker Node に taint が設定されている (例: virtualization=true:NoSchedule) マルチノードクラスターが必要です。taint のないシングルノードクラスターでは、VM は正常にスケジュールされ、このエラーは発生しません。

この例では、VM 作成時にスケジューリングエラーが発生した場合の動作と、エージェントがそれを診断および解決する方法を示します。

  1. IDE チャットで以下を入力します。

    Create a Fedora VM named fedora-db with 4 vCPUs and 16GB RAM in the production namespace, memory-optimized, with 100GB storage, and autostart

  2. エージェントはリクエストを m1 (メモリ最適化) パフォーマンスプロファイルの xlarge サイズにマッピングし、確認テーブルを表示します。

├──────────────┼──────────────┼────────────────────────────────────┤

Confirm: yes / no / modify?

 1) Apply workaround (add toleration and restart)
 2) Manual fix (I'll show you the oc patch command)
 3) Cancel (delete the VM)

インスタンスタイプの解決

OS の選択

エージェントは複数の Linux オペレーティングシステムをサポートしています。自然言語で OS を指定すると (例:「Fedora VM を作成して」)、エージェントは openshift-virtualization-os-images namespace にあるゴールデンイメージから適切なコンテナディスクイメージを選択します。

コンテナディスクイメージは、DataSource 参照から vm_create ツールによって自動的に解決されます。必要に応じてカスタムコンテナディスクイメージの URL を指定することもできますが、エージェントは続行する前にイメージソースが信頼できることを確認するよう警告します。

ストレージ設定

vm-create スキルは、以下のストレージオプションをサポートしています。

ディスクサイズ 説明

30Gi (デフォルト)

ほとんどのワークロードに適しています

50Gi

中規模のストレージ要件

100Gi

大規模な要件 — データベース、アプリケーションデータ

カスタム

任意のサイズを指定 (例: "200Gi")

エージェントは自動的に以下を実行します。

  • クラスター内の利用可能な StorageClass を照会します

  • デフォルト StorageClass (storageclass.kubernetes.io/is-default-class でアノテーションされているもの) を特定します

  • StorageClass の機能 (ボリュームバインディングモード、CSI プロビジョナー) を分析します

  • 適切なサイズの DataVolume をバックエンドとする PersistentVolumeClaim を作成します

クラスターで利用可能な StorageClass を確認できます。

oc get sc
NAME    PROVISIONER RECLAIMPOLICY VOLUMEBINDINGMODE  ALLOWVOLUMEEXPANSION AGE
lvms-vg1 (default) topolvm.io Delete   WaitForFirstConsumer true     17d

ネットワークのセットアップ

デフォルトでは、エージェントはクラスターのデフォルト Pod ネットワークに接続された VM を作成します。これにより、ほとんどのユースケースで基本的な接続性が提供されます。

クラスターにセカンダリーネットワークアタッチメント定義が設定されている場合、自然言語プロンプトで追加のネットワークインターフェースを要求できます (例: "create a VM with a secondary network on vlan-100")。エージェントはネットワーク設定を vm_create ツールに渡します。

Human-in-the-Loop による確認

すべての VM 作成には明示的な確認ステップが含まれます。エージェントが承認なしにクラスターリソースを作成することはありません。

  1. エージェントは、プロンプト、対話型の質問、クラスターのデフォルトから、すべてのパラメーターを収集します。

  2. 使用されるすべての値を示す設定テーブルが表示されます。

  3. 次のいずれかを選択します。

    • yes — 作成を続行します

    • no — 操作をキャンセルする

    • modify — 特定のパラメーターを変更する (例: "modify: change storage to 50Gi")

  4. 変更後、更新された表が表示され、再度確認を行います。

この安全モデルにより、意図しないリソース消費を防ぎ、作成される対象を完全に把握できるようになります。

自動エラー診断

VM の作成後にエラー状態になった場合、エージェントは組み込みのトラブルシューティングナレッジベースを使用して問題を自動的に診断します。

スケジューリングエラー (ErrorUnschedulable)

最も一般的な 3 つの原因は次のとおりです。

  1. ノードの taint (最も一般的) — Worker Node に、VM が許容 (tolerate) していない taint (例: virtualization=true:NoSchedule) が設定されています。エージェントは必要な toleration を VM spec に追加して再起動できます。

  2. リソース不足 — 要求された VM サイズに対して、クラスター内のいずれのノードにも十分な CPU、メモリ、またはストレージがありません。エージェントは、VM サイズの縮小またはノードのリソース空き状況の確認を提案します。

  3. Node selector mismatch — VM はクラスター内に存在しない特定のノードラベルを必要としています。エージェントはセレクターを削除するか、ノードへのラベルの追加を提案できます。

ストレージエラー (ErrorDataVolumeNotReady)

一般的なストレージの問題は以下のとおりです。

  • DataVolume still provisioning — 大容量ディスクのインポートには数分かかる場合があります。エージェントは進捗状況を監視し、プロビジョニングが完了したときに報告します。

  • StorageClass not found — 要求された StorageClass が存在しません。エージェントは利用可能なオプションを一覧表示し、有効な StorageClass を使用して VM を再作成することを提案します。

  • ストレージクォータ不足 — namespace のクォータで、要求されたディスクサイズが許可されていません。エージェントは現在のクォータ使用状況を報告し、代替案を提示します。

いずれの場合も、エージェントは推奨される解決策とともに明確な診断結果を提示し、修正アクションを実行する前にユーザーの決定を待ちます。

VM へのアクセス

VM が作成されて実行されたら、いくつかの方法を使用して接続できます。

方法 コマンド

シリアルコンソール

virtctl console <vm-name> -n <namespace>

VNC コンソール

OpenShift Console → Virtualization → VirtualMachines → VM を選択 → Console タブ

SSH

VirtualMachineInstance から VM の IP を取得し、ssh <user>@<ip> を実行

ポートフォワーディング

virtctl port-forward vmi/<vm-name> -n <namespace> 8080:80

VM の IP アドレスを確認するには:

oc get vmi fedora-vm -n my-vms -o jsonpath='{.status.interfaces[0].ipAddress}'
10.128.0.102

デフォルトの認証情報

各 OS イメージにはデフォルトのユーザーアカウントが用意されています。コンソールアクセスはすぐに利用できます。SSH を使用する場合は、パスワードを設定するか SSH 鍵を挿入する必要があります。

# シリアルコンソール経由で接続し、パスワードを設定
virtctl console fedora-vm -n my-vms
# ログイン後:
sudo passwd fedora
オペレーティングシステム デフォルトのユーザー名

Fedora

fedora

RHEL

cloud-user

CentOS Stream

centos

クリーンアップ

VM と関連ストレージを削除するには:

oc delete vm <vm-name> -n <namespace>

VirtualMachine リソースを削除すると、関連付けられている DataVolume および PersistentVolumeClaim も削除されます。このチュートリアルで作成したすべての VM を削除するには:

oc delete vm fedora-vm -n my-vms
oc delete vm fedora-dev -n development

自然言語を使用することもできます。「Delete VM fedora-vm in namespace my-vms」と入力すると、エージェントは削除前の名前確認セーフティチェックを含む vm-delete スキルを使用します。
