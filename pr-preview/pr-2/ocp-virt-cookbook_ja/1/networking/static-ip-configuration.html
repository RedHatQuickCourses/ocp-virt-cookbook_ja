VM への静的 IP の設定

概要

本チュートリアルでは、OpenShift Virtualization において仮想マシン (VM) に静的 IP アドレスを割り当てるために利用可能な手法について説明します。DHCP はデフォルトかつ最もシンプルな手法ですが、外部システムとの統合、コンプライアンス、レガシーアプリケーションの要件などの理由から、予測可能で固定された IP アドレスを必要とするワークロードは多く存在します。

以下の 5 つの異なる手法を用いて静的 IP を設定する方法を学習します。

  • cloud-init networkData — 初回起動時にネットワークを設定 (Linux VM)

  • 固定 IP を持つ UDN プライマリネットワーク — OVN-Kubernetes によるクラスター管理の IP 割り当て

  • DHCP 予約 — 外部 DHCP サーバーで MAC アドレスに固定 IP を紐付け

  • nmcli を使用した QEMU guest agent — guest agent 経由で起動後に静的 IP を適用

  • Sysprep (Windows VM) — unattend.xml を通じてネットワークを設定

それぞれの方法には、自動化、柔軟性、運用負荷の面で異なるトレードオフがあります。環境に最適なものを選択してください。

学習目標

  • OpenShift Virtualization で静的 IP を割り当てる際のトレードオフの理解

  • cloud-init networkData を使用して初回起動時に静的 IP を設定する方法

  • 固定 IP を持つ UDN プライマリネットワークを使用してクラスター管理のアドレス指定を行う方法

  • 固定 MAC アドレスを使用して DHCP 予約を行う方法

  • QEMU guest agent と nmcli を使用して起動後に静的 IP を適用する方法

  • Sysprep を使用して Windows VM の静的 IP を設定する方法

  • 環境に応じた適切な手法の選択

トレードオフと考慮事項

静的 IP を割り当てる前に、以下の影響を理解しておく必要があります。

クラスター管理のネットワーク機能の喪失

セカンダリーネットワークに静的 IP を割り当てると、VM はデフォルトの Pod ネットワークに依存する OpenShift の Services や Routes へのアクセスを失う可能性があります。クラスター接続性を維持するために、プライマリインターフェース (Pod ネットワークに接続) は DHCP で割り当てられたアドレスを保持するようにしてください。

OpenShift クラスターが割り当て済みアドレスを認識しない問題

静的 IP は OVN-Kubernetes IPAM をバイパスします。クラスターはこれらのアドレスを追跡しないため、外部で適切に管理されていないと IP 競合が発生する可能性があります。IP アドレスのインベントリを維持するか、外部の IPAM ソリューションを使用してください。

運用上のオーバーヘッド

静的 IP の割り当ては、VM の作成、移動、削除のたびに手動 (または外部 IPAM 経由) で追跡・更新する必要があります。予約を伴う DHCP を使用すると、この負担を軽減できます。

静的 IP が適している場合

  • 固定アドレスを必要とするレガシーなワークロード

  • IP を直接参照する外部システム (ファイアウォール、ロードバランサー、監視システム) との統合

  • 対象ネットワーク上に DHCP サーバーが存在しない環境

  • アドレスの追跡可能性に関する規制やコンプライアンス要件がある環境

DHCP または OVN-Kubernetes IPAM を優先すべき場合

  • 一時的な VM、または頻繁に再作成される VM

  • 信頼性の高い DHCP インフラストラクチャが存在する環境

  • Kubernetes の Services および DNS を通じてのみ通信するワークロード

前提条件

  • OpenShift Virtualization Operator がインストールされた OpenShift 4.18 以上

  • CLI ツール: oc、virtctl

  • 少なくとも 1 つの設定済みネットワーク (プライマリ Pod ネットワーク)

  • セカンダリーネットワークを使用する場合: NetworkAttachmentDefinition (NAD) が設定済みであること (Localnet VLAN チュートリアルを参照)

  • DHCP 予約を使用する場合: 外部 DHCP サーバーへの管理者アクセス権

  • ネットワークに関する基本的な知識 (IP アドレッシング、サブネット、ゲートウェイ、DNS)

手法 1: cloud-init networkData

cloud-init は、VM 起動時に実行される業界標準の初期化ツールです。cloudInitNoCloud ボリューム内の networkData フィールドは、Netplan 互換のバージョン 2 形式を使用して、専用のネットワーク設定を提供します。

これは OpenShift Virtualization における Linux VM の最も一般的な手法です。

仕組み

  1. VM が起動し、cloud-init が NoCloud データソースから networkData を読み取ります。

  2. cloud-init は、ユーザー空間のサービスが開始される前にネットワーク設定を適用します。

  3. 設定は再起動後も保持されます。

設定形式

cloud-init のネットワーク設定はバージョン 2 (Netplan) 形式を使用します。バージョン 2 形式は、デバイスタイプとして ethernets、bonds、bridges、vlans をサポートしています。各デバイスには addresses、dhcp4/dhcp6、routes、nameservers(addresses および search を含む)、mtu、match(macaddress、name、driver) オプションを含めることができます。

基本的な形式は以下の通りです。

networkData: |
  version: 2
  ethernets:
    enp1s0:
      dhcp4: true
    enp2s0:
      dhcp4: false
      dhcp6: false
      addresses:
        - 192.168.100.50/24
      nameservers:
        addresses:
          - 192.168.100.1

この例では、enp1s0(プライマリ Pod ネットワークインターフェース) は DHCP を使用し、enp2s0(セカンダリーインターフェース) は静的 IP を受け取ります。

デフォルトゲートウェイの設定

gateway4 または gateway6 フィールドは使用しないでください。これらは Netplan 0.103 および cloud-init 23.1 以降で非推奨となっています。代わりに routes を使用してください。

networkData: |
  version: 2
  ethernets:
    enp2s0:
      dhcp4: false
      addresses:
        - 192.168.100.50/24
      routes:
        - to: 192.168.100.0/24
          via: 192.168.100.1
      nameservers:
        addresses:
          - 192.168.100.1
        search:
          - example.com

この例では、search フィールドで DNS 検索ドメインを追加する方法と、routes リストで特定のルートを追加する方法も示しています。デフォルトゲートウェイのルートには to: default を使用してください (プライマリインターフェースにデフォルトルートが存在しない場合、セカンダリーインターフェースでのみ使用します)。

優先順位

  1. networkData 設定 (最優先)

  2. データソースのネットワーク設定

  3. DHCP へのフォールバック (デフォルト)

KubeVirt でのインターフェース命名

KubeVirt は、ゲスト VM 内部で予測可能なネットワークインターフェース命名規則を使用します。インターフェースは PCI スロットに基づいて順番に命名されます。

  • enp1s0 — 最初のインターフェース (通常は Pod ネットワーク)

  • enp2s0 — 2 番目のインターフェース (最初のセカンダリーネットワーク)

  • enp3s0 — 3 番目のインターフェース (2 番目のセカンダリーネットワーク)

eth0 のようなレガシーな名前は使用しないでください。VM spec で定義されたインターフェースの順序と一致する、予測可能な名前 (enpXs0) を使用してください。

重要なフォーマット規則

cloudInitNoCloud ボリュームで networkData を提供する際は、以下の規則に注意してください。

network: キーでラップしない

KubeVirt の networkData フィールドは、設定が直接 version: 2 で始まることを期待しています。トップレベルの network: ラッパーは追加しないでください。その形式はスタンドアロンの構成ファイル用であり、NoCloud データソースの networkData フィールドでは使用しません。

常に userData を含める

userData も設定されていない限り、cloud-init は networkData を解析しません。最小限の userData ヘッダー (#cloud-config) でも十分です。本チュートリアルのすべての例には userData が含まれています。

Secret 参照よりもインラインの networkData を優先

一部の設定において networkDataSecretRef が cloud-init によって適用されないという既知の問題があります。安定した動作のために、インラインの networkData フィールドまたは networkDataBase64 を使用してください。

静的 IP が適用される場所

静的 IP 設定はセカンダリーネットワークインターフェースのみに適用されます。プライマリインターフェースは masquerade 経由で Pod ネットワークに接続し、クラスターから自動的に IP を受け取るため、静的 IP を割り当てないでください。masquerade ブリッジは内部サブネット (10.0.2.0/24) 上で動作し、NAT によって Pod IP に変換されます。これを別のサブネットの静的アドレスで上書きすると、接続が切断されます。

本チュートリアルのすべての例では、プライマリインターフェース (enp1s0) を DHCP のままにし、セカンダリーインターフェース (enp2s0 以降) に静的 IP を設定します。

シナリオ: プライマリ DHCP + セカンダリー静的 IP

これが標準的なアプローチです。プライマリインターフェースは Pod ネットワーク上で DHCP を使用し、VLAN またはブリッジネットワーク上のセカンダリーインターフェースが静的 IP を取得します。

前提条件: セカンダリーネットワークが設定されていることを確認してください (例: localnet VLAN 100 の NetworkAttachmentDefinition (NAD))。設定手順については Localnet VLAN チュートリアル を参照してください。

本チュートリアル用の namespace を作成します。

手法 2: 固定 IP を持つ UDN プライマリネットワーク

Layer2 トポロジーを持つユーザー定義ネットワーク (UDN) は、安定した IP アドレス割り当てのためのクラスターで管理された手段を提供します。UDN が ipam.lifecycle: Persistent を持つ namespace のプライマリネットワークとして設定されている場合、OVN-Kubernetes は定義されたサブネットから IP を割り当て、IPAMClaim カスタムリソースを使用して VM の再起動、停止/開始サイクル、ライブマイグレーションを通じて IP を維持します。

このアプローチにより、手動の静的 IP 設定や外部 DHCP サーバーが不要になります。クラスターが IP 割り当てを処理し、各 VM が割り当てられたアドレスを保持することを保証します。

仕組み

  1. k8s.ovn.org/primary-user-defined-network ラベルを持つ namespace を作成します。

  2. Layer2 トポロジー、サブネット、ipam.lifecycle: Persistent を持つ UserDefinedNetwork リソースを定義します。

  3. その namespace にデプロイされた VM は、cloud-init の networkData や DHCP 予約を必要とせず、サブネットから自動的に固定 IP を受け取ります。

本手法の使用場面

  • 手動設定なしでクラスター管理の IP 割り当てを行いたい場合

  • VM が再起動やライブマイグレーションを通じて同じ IP を保持する必要がある場合

  • 外部 DHCP サーバーの維持やマニフェストへの IP 埋め込みを避けたい場合

  • カスタムサブネットを用いた namespace 範囲のネットワーク分離が必要な場合

namespace の設定、UDN の作成、VM のデプロイ、接続性検証を含む完全なウォークスルーについては、UDN を使用した Layer2 プライマリネットワークの設定 を参照してください。

手法 3: DHCP 予約

DHCP 予約 (静的 DHCP または固定アドレス DHCP とも呼ばれます) は、DHCP の自動化と静的 IP 割り当ての予測可能性を兼ね備えています。DHCP サーバーが特定の MAC アドレスを固定 IP にマッピングするため、VM は常に同じアドレスを受け取ります。

仕組み

  1. VM spec で VM のネットワークインターフェースに固定 MAC アドレスを割り当てます。

  2. 外部 DHCP サーバー上で、その MAC アドレスを特定の IP にマッピングする予約を作成します。

  3. VM が起動し、DHCP 要求を送信すると、予約されたアドレスを受け取ります。

本手法の使用場面

  • 既存の DHCP インフラストラクチャがあり、中央集権的な IP 管理を行いたい場合

  • ネットワーク設定を VM マニフェストに埋め込みたくない場合

  • VM のポータビリティが必要な場合 (IP はマニフェストではなく MAC に追従します)

静的 MAC アドレスの割り当て

DHCP 予約を使用するには、VM インターフェースに固定 MAC アドレスを設定する必要があります。これを行わないと、KubeVirt は起動のたびにランダムな MAC を割り当てるため、予約が機能しません。

fedora-dhcp-reserved-vm.yaml をダウンロード

apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: fedora-dhcp-reserved-vm
  namespace: static-ip-demo
spec:
  dataVolumeTemplates:
    - apiVersion: cdi.kubevirt.io/v1beta1
      kind: DataVolume
      metadata:
        name: fedora-dhcp-reserved-vm-disk
      spec:
        sourceRef:
          kind: DataSource
          name: fedora
          namespace: openshift-virtualization-os-images
        storage:
          resources:
            requests:
              storage: 30Gi
  runStrategy: RerunOnFailure
  template:
    metadata:
      labels:
        kubevirt.io/domain: fedora-dhcp-reserved-vm
    spec:
      domain:
        cpu:
          cores: 2
        devices:
          disks:
            - disk:
                bus: virtio
              name: rootdisk
            - disk:
                bus: virtio
              name: cloudinitdisk
          interfaces:
            - masquerade: {}
              name: default
            - bridge: {}
              name: vlan-network
              macAddress: "02:00:00:01:00:01"
          rng: {}
        machine:
          type: pc-q35-rhel9.4.0
        memory:
          guest: 4Gi
      networks:
        - name: default
          pod: {}
        - name: vlan-network
          multus:
            networkName: localnet-vlan-100
      volumes:
        - dataVolume:
            name: fedora-dhcp-reserved-vm-disk
          name: rootdisk
        - cloudInitNoCloud:
            userData: |-
              #cloud-config
              user: fedora
              password: fedora123
              chpasswd: { expire: False }
              ssh_pwauth: True
          name: cloudinitdisk

cloud-init 手法との主な違いは、セカンダリーインターフェース上の macAddress フィールドです。DHCP サーバーが IP 割り当てを処理するため、networkData は不要です。

DHCP サーバーの設定

外部 DHCP サーバー上で、MAC アドレスに対する予約を作成します。正確な設定は使用している DHCP ソフトウェアによって異なります。

ISC DHCP の例 (dhcpd.conf):

host fedora-dhcp-reserved-vm {
  hardware ethernet 02:00:00:01:00:01;
  fixed-address 192.168.100.60;
}

dnsmasq の例:

dhcp-host=02:00:00:01:00:01,192.168.100.60,fedora-dhcp-reserved-vm

予約の設定後、VM をデプロイします。

oc apply -f fedora-dhcp-reserved-vm.yaml

検証

VM にアクセスし、IP が予約と一致していることを確認します。

virtctl console fedora-dhcp-reserved-vm -n static-ip-demo

VM 内部:

ip addr show enp2s0

DHCP 予約が適用されている場合、出力は固定 MAC 上の予約済み IP を表示します。

想定される出力
3: enp2s0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1400 qdisc fq_codel state UP group default qlen 1000
    link/ether 02:00:00:01:00:01 brd ff:ff:ff:ff:ff:ff
    inet 192.168.100.60/24 brd 192.168.100.255 scope global dynamic enp2s0
       valid_lft 3600sec preferred_lft 3600sec

DHCP サーバーが応答しない場合、インターフェースはリンクローカル IPv6 アドレスのみを持つことになります。固定 MAC 02:00:00:01:00:01 は、macAddress フィールドが正しく適用されていることを確認します。

02: で始まる MAC アドレスはローカル管理範囲にあるため、ハードウェアベンダーが割り当てた MAC と競合することはありません。

ライブマイグレーションに関する考慮事項

静的 IP を持つ VM を他のノードにライブマイグレーションする場合、動作はネットワークタイプに依存します。

  • ブリッジベースのセカンダリーネットワーク (localnet、Linux Bridge): VM はマイグレーション中も MAC アドレスと IP を保持します。ネットワークファブリックが MAC モビリティをサポートしている必要があります (例: スイッチが MAC アドレステーブルを更新する必要がある)。cloud-init、DHCP 予約、または nmcli を通じて割り当てられた静的 IP は、マイグレーション後も保持されます。

  • SR-IOV ネットワーク: SR-IOV でのライブマイグレーションには追加の設定が必要であり、同じネットワークパスが保持されない場合があります。詳細については OpenShift Virtualization ライブマイグレーションのドキュメント を参照してください。

プライマリ Pod ネットワークインターフェースは、マイグレーション後に新しい Pod IP を受け取りますが、masquerade モードを使用する場合、これはゲスト OS に対して透過的です。

手法 4: nmcli を使用した QEMU guest agent

QEMU guest agent を使用すると、ホスト (KubeVirt) は実行中の VM と通信できます。このチャネルを使用して、ゲスト内部の標準ツールである nmcli を使用し、VM 起動後にネットワークを設定できます。

本手法は、既に実行中の VM でネットワーク設定を変更する必要がある場合や、cloud-init が使用できない、または実用的でない場合に便利です。

仕組み

  1. VM が対象インターフェース上で DHCP を使用するか、IP なしで起動します。

  2. VM 内で QEMU guest agent が開始されます。

  3. VM コンソール (または SSH) に接続し、nmcli を使用して静的 IP を適用します。

  4. NetworkManager が設定を保存するため、設定は再起動後も保持されます。

前提条件

  • VM イメージに qemu-guest-agent パッケージが含まれている必要があります (ほとんどの Red Hat および Fedora イメージにはデフォルトで含まれています)。

  • guest agent が VM 内で実行されている必要があります。

静的 IP の適用

まず、セカンダリーインターフェースで DHCP を使用するか、またはそのインターフェースに対して networkData を設定せずに VM をデプロイします。

VM に接続します (例: 手法 2 でデプロイした DHCP 予約済み VM)。

virtctl console fedora-dhcp-reserved-vm -n static-ip-demo

guest agent が実行されていることを確認します。

systemctl status qemu-guest-agent

guest agent が実行されていない場合は、起動して有効にします。

sudo systemctl enable --now qemu-guest-agent

現在のネットワーク接続をリスト表示します。

nmcli connection show

対象インターフェースの接続名を特定します (例: enp2s0 または Wired connection 2)。

静的 IP 設定を適用します。

sudo nmcli connection modify "Wired connection 2" \
  ipv4.method manual \
  ipv4.addresses 192.168.100.70/24 \
  ipv4.dns 192.168.100.1

更新された設定を有効化します。

sudo nmcli connection up "Wired connection 2"

VM 内部で結果を検証します。

ip addr show enp2s0

VirtualMachineInstance ステータスを使用して VM 外からも検証できます。

oc get vmi fedora-dhcp-reserved-vm -n static-ip-demo -o jsonpath='{.status.interfaces[*].ipAddress}'

設定は NetworkManager によって保存され、VM の再起動後も保持されます。

本手法の使用場面

  • 実行中の VM に対するデプロイ後のネットワーク変更

  • cloud-init が使用されていなかった他のプラットフォームからマイグレーションされた VM

  • 一時的または動的なネットワーク再構成

  • cloud-init 設定を上書きする必要があるトラブルシューティングのシナリオ

VM がもともと cloud-init の networkData で設定されていた場合、再起動時に cloud-init が nmcli の変更を上書きする可能性があります (cloud-init の設定に依存します)。これを防ぐには、VM spec から networkData を削除するか、対象インターフェースを管理しないように cloud-init を設定してください。

手法 5: Windows VM 向け Sysprep

Windows 仮想マシンでは、unattend.xml 応答ファイルを使用した Microsoft Sysprep により、Windows の初期セットアップ (OOBE) または specialize パス中に静的 IP 設定を提供できます。

仕組み

  1. ネットワーク設定を含む unattend.xml ファイルを作成します。

  2. そのファイルが sysprep ボリュームを通じて VM に注入されます。

  3. Windows はセットアップ中に応答ファイルを読み取り、ネットワーク設定を適用します。

unattend.xml のネットワークセクションの例

以下のスニペットは、specialize パス中に Ethernet として識別されるセカンダリーネットワークインターフェースに静的 IP を設定します。マルチ NIC の Windows VM では、インターフェースの Identifier がターゲットネットワークに接続されているアダプターと一致することを確認してください。確認にはデバイスマネージャーまたは PowerShell の Get-NetAdapter を使用してください。

<?xml version="1.0" encoding="utf-8"?>
<unattend xmlns="urn:schemas-microsoft-com:unattend">
  <settings pass="specialize">
    <component name="Microsoft-Windows-TCPIP"
               processorArchitecture="amd64"
               publicKeyToken="31bf3856ad364e35"
               language="neutral"
               versionScope="nonSxS"
               xmlns:wcm="http://schemas.microsoft.com/WMIConfig/2002/State">
      <Interfaces>
        <Interface wcm:action="add">
          <Identifier>Ethernet</Identifier>
          <Ipv4Settings>
            <DhcpEnabled>false</DhcpEnabled>
          </Ipv4Settings>
          <UnicastIpAddresses>
            <IpAddress wcm:action="add" wcm:keyValue="1">192.168.100.80/24</IpAddress>
          </UnicastIpAddresses>
          <Routes>
            <Route wcm:action="add">
              <Identifier>0</Identifier>
              <NextHopAddress>192.168.100.1</NextHopAddress>
              <Prefix>0.0.0.0/0</Prefix>
            </Route>
          </Routes>
        </Interface>
      </Interfaces>
    </component>
    <component name="Microsoft-Windows-DNS-Client"
               processorArchitecture="amd64"
               publicKeyToken="31bf3856ad364e35"
               language="neutral"
               versionScope="nonSxS"
               xmlns:wcm="http://schemas.microsoft.com/WMIConfig/2002/State">
      <Interfaces>
        <Interface wcm:action="add">
          <Identifier>Ethernet</Identifier>
          <DNSServerSearchOrder>
            <IpAddress wcm:action="add" wcm:keyValue="1">8.8.8.8</IpAddress>
          </DNSServerSearchOrder>
        </Interface>
      </Interfaces>
    </component>
  </settings>
</unattend>

応答ファイルの注入

unattend.xml を ConfigMap に保存し、VM spec で sysprep ボリュームとして参照します。Sysprep を使用した Windows VM デプロイの完全なウォークスルーについては、Sysprep を使用した Windows VM 作成に関する OpenShift ドキュメント を参照してください。

応答ファイルを含む ConfigMap を作成します。

oc create configmap windows-sysprep --from-file=unattend.xml -n static-ip-demo

VM spec で参照します。

volumes:
  - name: sysprep
    sysprep:
      configMap:
        name: windows-sysprep

そして、対応するディスクを追加します。

devices:
  disks:
    - cdrom:
        bus: sata
      name: sysprep

本手法の使用場面

  • 静的 IP を必要とする Windows Server VM

  • 応答ファイルを使用した自動化された Windows デプロイメント

  • VMware や Hyper-V から Windows ワークロードを移行する環境

Sysprep は Windows の初期セットアップ中にのみ実行されます。Windows VM のデプロイ後の IP 変更については、PowerShell リモートアクセスまたは RDP を使用して手動でネットワークを設定してください。

一般的な問題と解決策

network: キーでラップされた networkData

問題: network: キーでラップされていたため、cloud-init が networkData を無視しました。

解決策: KubeVirt の cloudInitNoCloud ボリュームでは、networkData フィールドは直接 version: 2 で始まる必要があります。トップレベルの network: ラッパーは追加しないでください。正しい形式は network:\n version: 2\n ethernets:\n …​ ではなく、version: 2\nethernets:\n …​ です。

インターフェース名が一致しない

問題: networkData で enp1s0 ではなく eth0 を使用した。

解決策: ゲスト OS 内部で表示される予測可能なインターフェース名を使用してください。最新の Linux ディストリビューション (RHEL 8+、Fedora、Ubuntu 16.04+) は enp1s0、enp2s0 などを使用します。順序は VM spec 内のインターフェース順序と一致します。

セカンダリーインターフェースで接続できない

問題: 静的インターフェースで DHCP を無効にするのを忘れた。

解決策: cloud-init の networkData で静的 IP を使用する場合は、常に dhcp4: false および dhcp6: false を設定してください。

複数のデフォルトルートによる接続問題

問題: プライマリインターフェースとセカンダリーインターフェースの両方にデフォルトルートを設定した。

解決策: デフォルトルートはプライマリインターフェース (通常は enp1s0) のみに設定してください。セカンダリーインターフェースにデフォルトルートを設定しないでください。

cloud-init 設定が適用されない

問題: YAML または cloud-init 設定の構文エラー。

解決策: VM 内部の /var/log/cloud-init.log で cloud-init ログを確認してください。YAML のインデントを検証し、cloud-init status を使用してエラーがないか確認してください。

セカンダリーネットワークで DNS が解決されない

問題: セカンダリーインターフェースでネームサーバーが設定されていない、または誤っている。

解決策: そのインターフェース用の networkData に適切なネームサーバーを追加してください。セカンダリーインターフェースが隔離されたネットワーク上にある場合、外部 DNS は不要な場合があります。

非推奨の gateway4 フィールドが警告を生成または失敗する

問題: networkData で gateway4: 192.168.100.1 を使用すると、新しい cloud-init バージョン (23.1 以降) で非推奨警告が発生する、または失敗する。

解決策: gateway4 を routes エントリに置き換えてください。代わりに routes: [{to: default, via: 192.168.100.1}] を使用してください。gateway4 および gateway6 フィールドは、Netplan 0.103 で非推奨となりました。

DHCP 予約が機能しない

問題: DHCP 予約があるにもかかわらず、VM が起動のたびに異なる IP を受け取る。

解決策: VM interface spec で macAddress フィールドが設定されていることを確認してください。固定 MAC がないと、KubeVirt は起動するたびにランダムな MAC を割り当てます。また、DHCP サーバーの予約が MAC アドレスと正確に一致していることを確認してください。

詳細な cloud-init トラブルシューティングについては、cloud-init トラブルシューティングガイド を参照してください。
