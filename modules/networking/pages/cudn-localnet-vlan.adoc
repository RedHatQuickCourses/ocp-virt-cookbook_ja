= OpenShift Virtualization における ClusterUserDefinedNetwork を使用した VLAN 対応の Localnet セカンダリーネットワークの構成
:navtitle: CUDN を使用した VLAN 対応の localnet セカンダリーネットワーク

本チュートリアルでは、OpenShift Virtualization において、ClusterUserDefinedNetwork (CUDN) を使用して VLAN タグ付けを行う Localnet セカンダリーネットワークを構成する方法を解説します。このアプローチでは、物理ネットワークインフラへの直接アクセスと、複数の namespace にまたがる VLAN セグメンテーションを提供し、Pod ネットワークの接続性を維持したまま、仮想マシン (VM) が特定の VLAN タグ付きネットワークと通信できるようにします。CUDN は一元的な管理と namespace 間のネットワーク可用性を提供するため、一貫した VLAN ベースのネットワークインフラを必要とするエンタープライズ環境に最適です。

== 前提条件

* **NMState Operator**: クラスター内にインストールされ、実行されていること
* **NMState CR**: Operator が実行された後に、nmstate インスタンスが作成されていること
* **Worker Node**: bridge mapping は Worker Node に適用されること
* **VLAN インフラストラクチャ**: 物理ネットワークインフラが VLAN タグ付けをサポートしていること
* **スイッチ構成**: OpenShift Worker Node に接続された物理スイッチポートが、複数の VLAN タグ付きトラフィックストリームを処理するために**トランクモード**で構成されていること

検証済みバージョン:
----
OpenShift 4.19
----

== ネットワーク構成要件

=== 物理スイッチ構成: トランクモード (TRUNK MODE)

Localnet VLAN 構成が正しく機能するためには、OpenShift Worker Node に接続された物理スイッチポートを**トランクモードで構成する必要があります**:

* **トランクモード**: スイッチポートが複数の VLAN のトラフィックを伝送できるようにする
* **VLAN タグ付け**: 各 VLAN は一意の VLAN ID (例: 100, 200, 300) によって識別される
* **マルチネットワーク**: 複数の VLAN ベースのセカンダリーネットワークをサポートするために不可欠

== ステップ 1: VM namespace の作成

VLAN 構成の Localnet セカンダリーネットワークを使用する VM 用の namespace を作成します。ClusterUserDefinedNetwork (CUDN) を使用すると、同一のネットワークを複数の namespace で利用可能にできます。

[source,bash,role=execute]
----
# 1 つ目の namespace を作成
oc apply -f - <<EOF
apiVersion: v1
kind: Namespace
metadata:
  name: vm-guests-vlan-prod
EOF

# 2 つ目の namespace を作成
oc apply -f - <<EOF
apiVersion: v1
kind: Namespace
metadata:
  name: vm-guests-vlan-dev
EOF
----

== ステップ 2: 追加 NIC 上へのカスタム OVS ブリッジの作成

まず、プライマリクラスターネットワークから VLAN トラフィックを分離するために、追加の物理ネットワークインターフェース (NIC) 上にカスタム OVS ブリッジを作成します。

[source,bash,role=execute]
----
oc apply -f - <<EOF
apiVersion: nmstate.io/v1
kind: NodeNetworkConfigurationPolicy
metadata:
  name: br-vlan-creation
spec:
  nodeSelector:
    node-role.kubernetes.io/worker: ''
  desiredState:
    interfaces:
    - name: enp11s0f0np0  # Replace with your physical interface name
      type: ethernet
      state: up
      ipv4:
        enabled: false
      ipv6:
        enabled: false
      description: "Physical interface for VLAN localnet"
    - name: br-vlan
      type: ovs-bridge
      state: up
      bridge:
        port:
        - name: enp11s0f0np0
      description: "OVS bridge for VLAN traffic"
EOF
----

NOTE: `enp11s0f0np0` は、使用する追加の物理インターフェース名に置き換えてください。利用可能なインターフェースは、以下のコマンドを実行して確認できます。

[source,bash,role=execute]
----
oc debug node/<node-name> -- ip link show
----

ブリッジの作成を確認します。

[source,bash,role=execute]
----
oc get nncp br-vlan-creation
# 想定される出力: STATUS: Available
----

== ステップ 3: bridge mapping の構成

論理ネットワークインターフェース名 `localnet-vlan` を Worker Node 上の `br-vlan` OVS ブリッジに接続する bridge mapping を構成します。このマッピングにより、どの物理ブリッジインターフェースが VLAN サポート付きの Localnet トラフィックを処理するかを OVN-Kubernetes に伝えます。

[source,bash,role=execute]
----
oc apply -f - <<EOF
apiVersion: nmstate.io/v1
kind: NodeNetworkConfigurationPolicy
metadata:
  name: cudn-localnet-vlan-bridge-mapping
spec:
  nodeSelector:
    node-role.kubernetes.io/worker: ''  
  desiredState:
    ovn:
      bridge-mappings:
      - localnet: localnet-vlan
        bridge: br-vlan
        state: present
EOF
----

== ステップ 4: VLAN 対応の ClusterUserDefinedNetwork 作成

複数の namespace にまたがるセカンダリーネットワーク接続のために、VLAN タグ付けを伴う Localnet トポロジーを構成する ClusterUserDefinedNetwork を作成します。

[source,bash,role=execute]
----
oc apply -f - <<EOF
apiVersion: k8s.ovn.org/v1
kind: ClusterUserDefinedNetwork
metadata:
  name: cudn-localnet-vlan-100
spec:
  namespaceSelector: 
    matchExpressions: 
    - key: kubernetes.io/metadata.name
      operator: In 
      values: ["vm-guests-vlan-prod", "vm-guests-vlan-dev"]
  network:
    topology: Localnet 
    localnet:
      role: Secondary 
      physicalNetworkName: localnet-vlan
      vlanID: 100
      ipam:
        mode: Disabled
EOF
----

**構成の詳細**:

* `vlanID: 100`: ネットワークセグメンテーション用に VLAN タグ 100 を指定
* `physicalNetworkName`: bridge mapping の論理ネットワークインターフェース名 (`localnet-vlan`) を参照
* `role: Secondary`: セカンダリーネットワークとして定義 (VM は Pod ネットワークをプライマリとして保持)
* `namespaceSelector`: このネットワークを使用できる namespace を定義
* **IPAM Disabled**: IP アドレスは cloud-init (静的) または外部 DHCP サーバーを介して構成する必要がある

== ステップ 5: VLAN ネットワーク接続と静的 IP を持つ VM のデプロイ

構成済みの namespace の 1 つに、Pod ネットワークと VLAN タグ付き Localnet セカンダリーネットワークの両方に接続する VM を作成します。

WARNING: 本例の cloud-init パスワードはデモ目的のみです。本番環境では必ず強力で一意のパスワードを使用するか、SSH 鍵認証を使用してください。

[source,bash,role=execute]
----
oc apply -f - <<EOF
apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: fedora-cudn-vlan-vm
  namespace: vm-guests-vlan-prod
  labels:
    app: fedora-cudn-vlan-vm
spec:
  runStrategy: Always
  dataVolumeTemplates:
  - metadata:
      name: fedora-cudn-vlan-volume
    spec:
      pvc:
        accessModes:
        - ReadWriteOnce
        resources:
          requests:
            storage: 33Gi
      sourceRef:
        kind: DataSource
        name: fedora
        namespace: openshift-virtualization-os-images
  template:
    metadata:
      labels:
        app: fedora-cudn-vlan-vm
    spec:
      domain:
        devices:
          disks:
          - name: datavolumedisk
            disk:
              bus: virtio
          - name: cloudinitdisk
            disk:
              bus: virtio
          interfaces:
          - name: default
            bridge: {}
          - name: cudn_vlan_network
            bridge: {}
        resources:
          requests:
            memory: 2Gi
            cpu: 1
      networks:
      - name: default
        pod: {}
      - name: cudn_vlan_network
        multus:
          networkName: cudn-localnet-vlan-100
      volumes:
      - name: datavolumedisk
        dataVolume:
          name: fedora-cudn-vlan-volume
      - name: cloudinitdisk
        cloudInitNoCloud:
          networkData: |
            version: 2
            ethernets:
              enp2s0:
                addresses: ["192.168.100.10/24"]
          userData: |
            #cloud-config
            user: fedora
            password: fedora
            chpasswd: { expire: False }
            packages:
            - python3
            - tcpdump
            - net-tools
            write_files:
            - path: /root/index.html
              content: |
                <h1>Welcome to OpenShift Virtualization CUDN VLAN Network!</h1>
                <p>VLAN ID: 100</p>
                <p>Static IP: 192.168.100.10/24</p>
                <p>Network: CUDN Localnet</p>
                <p>Namespace: vm-guests-vlan-prod</p>
              permissions: '0644'
            runcmd:
            - nohup python3 -m http.server 8080 --directory /root > /dev/null 2>&1 &
EOF
----

== ステップ 7: VLAN ネットワーク接続の確認

VM コンソールにアクセスし、namespace 間での VLAN 構成を含むデュアルネットワーク接続を確認します。

[source,bash,role=execute]
----
# 本番 namespace の VM を確認
oc get vm -n vm-guests-vlan-prod
oc get vmi -n vm-guests-vlan-prod

# 開発 namespace の VM を確認
oc get vm -n vm-guests-vlan-dev
oc get vmi -n vm-guests-vlan-dev

# 本番 VM のコンソールにアクセス (認証情報: fedora/fedora、cloud-init 経由)
virtctl console -n vm-guests-vlan-prod fedora-cudn-vlan-vm

# 開発 VM のコンソールにアクセス (認証情報: fedora/fedora、cloud-init 経由)
virtctl console -n vm-guests-vlan-dev fedora-cudn-vlan-vm-dev
----

各 VM コンソール内で、VLAN ネットワーク構成を確認します。

[source,bash]
----
# ネットワークインターフェースの確認 - プライマリ (Pod ネットワーク) とセカンダリー (VLAN ネットワーク)
ip addr show

# ルーティングテーブルの確認
ip route show

# 想定される出力例 (プライマリネットワーク、DHCP 経由):
default via 10.128.0.1 dev enp1s0 proto dhcp src 10.128.0.174 metric 100

# 外部接続のテスト
ping 8.8.8.8

# Web サービスが実行中であることを確認
curl localhost:8080

# VLAN インターフェースの静的 IP 割り当てを確認
ip addr show enp2s0
# 想定される値: inet 192.168.100.10/24 (本番) または 192.168.100.20/24 (開発)

# VM 間の VLAN インターフェース接続をテスト
# 本番 VM (192.168.100.10) から開発 VM へ ping:
ping 192.168.100.20

# VLAN タグ付けの確認 (tcpdump が利用可能な場合)
# セカンダリーインターフェース上の VLAN タグ付きトラフィックを表示
sudo tcpdump -i enp2s0 -nn vlan 100
----

== ステップ 8: namespace 間接続のテスト

異なる namespace にある VM が、共有された CUDN VLAN ネットワーク上で通信できることを確認します。

[source,bash]
----
# 本番 VM (192.168.100.10) から開発 VM への接続をテスト
ping 192.168.100.20

# namespace 間の Web サービス接続をテスト
curl 192.168.100.20:8080

# 開発 VM (192.168.100.20) から本番 VM への接続をテスト
ping 192.168.100.10
curl 192.168.100.10:8080
----

== トラブルシューティング

OVS ブリッジおよび bridge mapping のトラブルシューティング (CUDN 固有の確認手順を含む) については、xref:ovs-bridge-troubleshooting.adoc#_clusteruserdefinednetwork_cudn_verification[OVS ブリッジ検証トラブルシューティングガイド]を参照してください。

=== 一般的な問題

==== VLAN トラフィックが VM に到達しない

* 物理スイッチの構成が VLAN タグ付けをサポートしているか確認
* Worker Node 上の bridge mapping 構成を確認
* VLAN ID がネットワークインフラと一致していることを確認
* カスタム OVS ブリッジ (`br-vlan`) が作成されているか確認: `oc get nncp br-vlan-creation`
* 物理インターフェースがブリッジに接続されているか確認

==== IP アドレス割り当ての問題

* cloud-init の networkData で静的 IP が正しく構成されているか確認
* インターフェース名が一致しているか確認 (2 番目のインターフェースには enp2s0 など)
* VM 内の cloud-init ログを確認: `cat /var/log/cloud-init.log`

==== ネットワーク接続の問題

* 物理ネットワークが構成された VLAN をサポートしているか確認
* 物理ネットワークから VLAN サブネットへの接続性をテスト
* 物理スイッチポートがトランクモードであることを確認

==== namespace 間の問題

* CUDN 構成の namespace セレクターを確認
* 両方の namespace が values 配列にリストされているか確認
* ターゲット namespace で NAD が自動作成されているか確認

==== CUDN 固有の問題

* CUDN の `physicalNetworkName` が bridge mapping の論理名 (`localnet-vlan`) と一致しているか確認
* 選択された namespace で CUDN によって作成された NAD を確認: `oc get network-attachment-definitions -A | grep cudn-localnet-vlan-100`
* IPAM モードが正しく設定されているか確認 (cloud-init 経由の静的 IP の場合は `Disabled`)

=== 確認コマンド

[source,bash,role=execute]
----
# ClusterUserDefinedNetwork のステータスを確認
oc get clusteruserdefinednetwork

# Worker Node 上の bridge mapping を確認
oc get nncp cudn-localnet-vlan-bridge-mapping -o yaml

# 両方の namespace の VM ネットワークステータスを確認
oc get vmi -n vm-guests-vlan-prod -o yaml | grep -A 10 networks
oc get vmi -n vm-guests-vlan-dev -o yaml | grep -A 10 networks

# トラブルシューティング用に OVN-Kubernetes のログを確認
oc logs -n openshift-ovn-kubernetes -l app=ovnkube-node

# namespace 間の CUDN ネットワークアタッチメントを確認
oc get network-attachment-definitions -A | grep cudn-localnet-vlan-100
----

== CUDN と NetworkAttachmentDefinition の比較

|===
| 機能 | CUDN | NetworkAttachmentDefinition

| **スコープ**
| クラスター全体、複数の namespace
| namespace 固有

| **管理**
| 一元的な構成
| namespace ごとの構成

| **VLAN サポート**
| ネイティブな vlanID パラメーター
| ネイティブな vlanID パラメーター

| **IP 管理**
| 静的/Disabled モード
| IPAM 経由の静的/DHCP

| **ユースケース**
| エンタープライズ、一貫したネットワーク
| アプリケーション固有のネットワーク
|===

== まとめ

本チュートリアルでは、以下の内容を学習しました。

* 追加の物理 NIC 上にカスタム OVS ブリッジを作成し、VLAN トラフィック用の bridge mapping を構成する方法
* 複数の namespace にまたがる VLAN タグ付きの `ClusterUserDefinedNetwork` を作成する方法
* CUDN VLAN セカンダリーネットワーク上で、cloud-init を使用して静的 IP アドレスを持つ VM をデプロイする方法
* 同じ CUDN VLAN ネットワークを共有する VM 間で、namespace 間の接続性を確認する方法
* VLAN ベースのネットワークにおける CUDN と NetworkAttachmentDefinition のアプローチの違い
