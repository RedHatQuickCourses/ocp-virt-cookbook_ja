= Localnetネットワーク用のOVS bridge作成のトラブルシューティング
:navtitle: Localnetネットワークのトラブルシューティング

検証済みバージョン:
----
OpenShift 4.20
----

このガイドは、OpenShift Virtualization において、Localnet セカンダリネットワーク用の OVS (Open vSwitch) bridgeが正しく作成および構成されていることを確認するのに役立ちます。

== OVS bridgeとLinux bridgeの理解

**重要**: OVS bridge の動作は Linux bridge とは異なります。

* **OVS bridge**は、`ovs-vsctl`コマンドを使用して確認できます。
* **OVS bridge**は、`ip addr show`や`ip link show`では通常のネットワークインターフェースとして表示されない場合があります。
* これは**正常かつ想定された動作**です。OVS bridgeは標準的なLinuxネットワークデバイスではなく、OVSデータベース内に存在するためです。

== 検証プロセス

=== ステップ 1: NodeNetworkConfigurationPolicy のステータス確認

まず、NNCPが適用され、正常に構成されていることを確認します。

[source,bash,role=execute]
----
# すべてのNNCPを一覧表示
oc get nncp

# 特定のNNCPのステータスを確認
oc get nncp br-vlan-creation
----

**期待される出力:**

----
NAME               STATUS      REASON
br-vlan-creation   Available   SuccessfullyConfigured
----

=== ステップ 2: NNCPの詳細情報の取得

NNCPの完全な構成とステータスを確認します。

[source,bash,role=execute]
----
oc get nncp br-vlan-creation -o yaml
----

**出力内の以下の重要な指標に注目してください:**

[source,yaml]
----
status:
  conditions:
  - lastHeartbeatTime: "2025-10-06T20:38:57Z"
    lastTransitionTime: "2025-10-06T20:38:57Z"
    message: 1/1 nodes successfully configured
    reason: SuccessfullyConfigured
    status: "True"
    type: Available
  - reason: SuccessfullyConfigured
    status: "False"
    type: Degraded
----

* `Available: True` かつ `SuccessfullyConfigured` = 構成が適用済み
* `Degraded: False` = 問題は検出されていない
* `message: X/X nodes successfully configured` = すべてのノードが正常に構成されている

=== ステップ 3: OVS bridge の確認

**これがOVS bridgeを確認するための正しい方法です:**

[source,bash,role=execute]
----
# ノード名を取得
oc get nodes

# すべてのOVS bridgeを一覧表示
oc debug node/<node-name> -- chroot /host ovs-vsctl list-br
----

**出力例:**

----
Starting pod/ocplab01-debug-k7bfc ...
To use host binaries, run `chroot /host`
br-ex
br-int
br-vlan

Removing debug pod ...
----

このリストに `br-vlan` が表示されていれば、bridgeは正常に作成されています。

=== ステップ 4: bridge構成の詳細確認

OVS構成を確認して、bridgeポートとインターフェースを表示します。

[source,bash,role=execute]
----
oc debug node/<node-name> -- chroot /host ovs-vsctl show
----

**出力例 (関連部分):**

----
Bridge br-vlan
    Port enp11s0f0np0
        Interface enp11s0f0np0
            type: system
----

**確認項目:**

* bridge名 (`br-vlan`) が出力にあること
* 物理インターフェース (例: `enp11s0f0np0`) がポートとしてリストされていること
* 物理インターフェースのインターフェースタイプが `system` であること

=== ステップ 5: 物理インターフェースのステータス確認

物理インターフェースがbridgeに接続されており、UP状態であることを確認します。

[source,bash,role=execute]
----
oc debug node/<node-name> -- chroot /host ip link show <interface-name>
----

**出力例:**

----
4: enp11s0f0np0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc mq master ovs-system state UP mode DEFAULT group default qlen 1000
    link/ether e8:eb:d3:13:06:16 brd ff:ff:ff:ff:ff:ff
----

**確認項目:**

* `UP,LOWER_UP` - インターフェースが動作可能であること
* `master ovs-system` - インターフェースがOVSによって管理されていること
* `state UP` - インターフェースの状態がアップしていること

=== ステップ 6: "ip addr show br-vlan" が失敗する理由

**これは正常な動作です:**

[source,bash,role=execute]
----
oc debug node/<node-name> -- chroot /host ip addr show br-vlan
----

**期待される結果:**

----
Device "br-vlan" does not exist.
----

**理由:**

* OVS bridgeは通常のLinuxネットワークデバイスとしてではなく、OVSデータベース内に存在するためです。
* 内部インターフェースを持たない限り、標準の `ip` コマンド出力には表示されません。
* これはbridgeの作成失敗を意味するものではありません。
* OVS bridge を確認する際は、必ず `ovs-vsctl` コマンドを使用してください。

== よくある問題と解決策

=== 問題 1: ovs-vsctl list-br に　bridge　が表示されない

**事象:**

* NNCPは `Available: True` を示しているが、bridgeが `ovs-vsctl list-br` に表示されない

**トラブルシューティング:**

[source,bash,role=execute]
----
# NNCPの条件を確認
oc get nncp br-vlan-creation -o jsonpath='{.status.conditions[?(@.type=="Available")]}' | jq

# NMState Operatorのログを確認
oc logs -n openshift-nmstate -l app=kubernetes-nmstate-operator

# 問題のあるノードネットワーク状態があるか確認
oc get nns -A
----

**一般的な原因:**

* 物理インターフェース名の不一致 (`ip link show` で確認)
* ノード上でOVSが正しく実行されていない
* NMState Operatorの問題

=== 問題 2: 物理インターフェースがbridgeに接続されていない

**事象:**

* bridgeは存在するが、`ovs-vsctl show` でインターフェースがポートとして表示されない

**トラブルシューティング:**

[source,bash,role=execute]
----
# bridge上のすべてのポートを一覧表示
oc debug node/<node-name> -- chroot /host ovs-vsctl list-ports br-vlan

# インターフェースのステータスを確認
oc debug node/<node-name> -- chroot /host ip link show <interface-name>

# NNCP構成に正しいインターフェース名があるか確認
oc get nncp br-vlan-creation -o yaml | grep -A 5 "name: <interface-name>"
----

**解決策:**

. NNCP内の物理インターフェース名が正しいことを確認します。
. インターフェースが別の bridge によって既に使用されていないか確認します。
. インターフェースが存在し、ノードで使用可能であることを確認します。

=== 問題 3: NodeSelector の不一致

**事象:**

* NNCPは成功しているが、bridgeが存在しない

**トラブルシューティング:**

[source,bash,role=execute]
----
# ノードラベルを確認
oc get nodes --show-labels

# NNCP NodeSelectorを確認
oc get nncp br-vlan-creation -o jsonpath='{.spec.nodeSelector}'
----

**一般的な問題:**

* Single Node OpenShift (SNO) ノードには `control-plane,master,worker` のロールがある
* `node-role.kubernetes.io/worker: ""` セレクターを持つNNCPは引き続き一致する
* NNCPステータスが "X/X nodes successfully configured" を示しているか確認する

=== 問題 4: bridge は作成されたが機能していない

**事象:**

* bridgeは存在し、インターフェースも接続されているが、トラフィックが流れない

**トラブルシューティング:**

[source,bash,role=execute]
----
# インターフェースのキャリアステータスを確認
oc debug node/<node-name> -- chroot /host cat /sys/class/net/<interface-name>/carrier

# インターフェースエラーを確認
oc debug node/<node-name> -- chroot /host ethtool -S <interface-name>

# 物理リンクがアップしているか確認
oc debug node/<node-name> -- chroot /host ethtool <interface-name> | grep "Link detected"
----

**一般的な原因:**

* 物理ケーブルが接続されていない
* スイッチポートが無効になっている、または構成が間違っている
* インターフェースの速度/デュプレックスの不一致

== Localnet用 bridge mapping の確認

OVS bridgeを作成した後、OVN-Kubernetesへのbridge mappingが正しく機能していることを確認する必要があります。

=== bridge mapping とは何か

bridge mapping は、**論理ネットワーク名** (NetworkAttachmentDefinitionsで使用) を**物理　OVS bridge**に接続します。例えば:

* 論理名: `localnet-vlan`
* 物理bridge: `br-vlan`
* mapping: `localnet-vlan:br-vlan`

=== ステップ 1: bridge mapping の NNCP ステータス確認

bridge mapping の NNCP が正常に適用されたか確認します:

[source,bash,role=execute]
----
# すべてのNNCPを一覧表示
oc get nncp | grep mapping

# NNCP の特定の bridge mapping を確認
oc get nncp localnet-vlan-bridge-mapping
----

**期待される出力:**

----
localnet-vlan-bridge-mapping   Available   SuccessfullyConfigured
----

=== ステップ 2: bridge mapping の詳細構成を取得

[source,bash,role=execute]
----
oc get nncp localnet-vlan-bridge-mapping -o yaml
----

**出力内の以下の重要なセクションに注目してください:**

[source,yaml]
----
spec:
  desiredState:
    ovn:
      bridge-mappings:
      - bridge: br-vlan
        localnet: localnet-vlan
        state: present
  nodeSelector:
    node-role.kubernetes.io/worker: ""
status:
  conditions:
  - message: 1/1 nodes successfully configured
    reason: SuccessfullyConfigured
    status: "True"
    type: Available
----

=== ステップ 3: ノード上の OVN bridge mapping を確認

これが**非常に重要な検証作業**です。OVN-Kubernetes に bridge mapping が構成されているか確認します:

[source,bash,role=execute]
----
oc debug node/<node-name> -- chroot /host ovs-vsctl get Open_vSwitch . external_ids:ovn-bridge-mappings
----

**期待される出力:**

----
"localnet-vlan:br-vlan,physnet:br-ex"
----

**意味:**

* `localnet-vlan:br-vlan` = カスタム mapping
* `physnet:br-ex` = デフォルトのOpenShift mapping
* 複数の mapping がある場合はカンマで区切られます

=== ステップ 4: 全ての OVS External ID の確認

すべての OVS external ID を取得して、完全な構成を確認します:

[source,bash,role=execute]
----
oc debug node/<node-name> -- chroot /host ovs-vsctl list Open_vSwitch | grep -A 2 external_ids
----

**出力例:**

----
external_ids        : {hostname=ocplab01, ovn-bridge-mappings="localnet-vlan:br-vlan,physnet:br-ex", ovn-bridge-remote-probe-interval="0", ovn-enable-lflow-cache="true", ovn-encap-ip="192.168.2.241", ovn-encap-type=geneve, ovn-is-interconn="true", ovn-memlimit-lflow-cache-kb="1048576", ovn-monitor-all="true", ovn-ofctrl-wait-before-clear="0", ovn-remote="unix:/var/run/ovn/ovnsb_db.sock", ovn-remote-probe-interval="180000", ovn-set-local-ip="true", rundir="/var/run/openvswitch", system-id="1b41fc3f-f597-4cd9-b508-e8247c209d97"}
----

**確認事項:**

* `ovn-bridge-mappings` にmappingが含まれていること
* `hostname` がノードと一致すること
* `ovn-encap-type=geneve` が存在すること

=== ステップ 5: 物理インターフェースの接続確認

物理インターフェースが bridge に接続されていることを確認します:

[source,bash,role=execute]
----
oc debug node/<node-name> -- chroot /host ovs-vsctl list-ports br-vlan
----

**期待される出力:**

----
enp11s0f0np0
----

これで、物理インターフェースが bridge 上のポートであり、トラフィックを送信できる状態であることが確認できます。

== bridge mapping の問題のトラブルシューティング

=== 問題 1: bridge mapping が OVN のExternal ID にない

**事象:**

* NNCPは成功しているが、`ovs-vsctl get Open_vSwitch . external_ids:ovn-bridge-mappings` に mapping が含まれていない

**トラブルシューティング:**

[source,bash,role=execute]
----
# NNCP が適用されたか確認
oc get nncp localnet-vlan-bridge-mapping -o yaml

# NMState Operator を再起動
oc delete pod -n openshift-nmstate -l app=kubernetes-nmstate-operator

# NMState ハンドラーのログを確認
oc logs -n openshift-nmstate -l component=kubernetes-nmstate-handler
----

**一般的な原因:**

* bridge が作成される前に NNCP が適用された
* NMState ハンドラーが正常に動作していない
* OVS サービスの不具合

**解決策:**

bridge が存在することを確認した後、bridge mapping の NNCP を削除して再作成してください。

=== 問題 2: mapping内のbridge名が間違っている

**事象:**

* bridge mapping は存在するが、間違ったbridge名を使用している

**検証:**

[source,bash,role=execute]
----
# 存在するbridgeを確認
oc debug node/<node-name> -- chroot /host ovs-vsctl list-br

# mappingが参照しているものを確認
oc get nncp localnet-vlan-bridge-mapping -o jsonpath='{.spec.desiredState.ovn.bridge-mappings[0].bridge}'
----

**解決策:**

mappingNNCP内のbridge名が、実際のOVS bridge名と完全に一致していることを確認してください。

=== 問題 3: 論理名の不一致

**事象:**

* bridge mapping が存在するにもかかわらず、VM がネットワークに接続できない

**検証:**

[source,bash,role=execute]
----
# bridge mapping内の論理名を確認
oc get nncp localnet-vlan-bridge-mapping -o jsonpath='{.spec.desiredState.ovn.bridge-mappings[0].localnet}'

# NetworkAttachmentDefinition または ClusterUserDefinedNetwork (CUDN) が同じ名前を参照しているか確認
oc get network-attachment-definitions <nad-name> -n <namespace> -o yaml
----

**解決策:**

bridge mapping 内の論理ネットワーク名は、NetworkAttachmentDefinition または ClusterUserDefinedNetwork 構成で使用されている名前と一致する必要があります。

=== 問題 4: 複数の mapping の競合

**事象:**

* 複数の  bridge mapping が構成されているが、トラフィックが間違った bridge に送信される

**検証:**

[source,bash,role=execute]
----
# すべての bridge mapping を一覧表示
oc debug node/<node-name> -- chroot /host ovs-vsctl get Open_vSwitch . external_ids:ovn-bridge-mappings
----

**期待される形式:**

----
"mapping1:bridge1,mapping2:bridge2,mapping3:bridge3"
----

**解決策:**

各論理ネットワーク名がユニークであり、正しい bridge に mappingさ れていることを確認してください。OVN は最初の一致する mapping を使用します。

== 完全な検証チェックリスト

このチェックリストを使用して、OVS bridge と bridge mappingが 正しく構成されているかを確認してください:

=== bridge作成

* [ ] NNCPステータスが `Available: True` かつ `SuccessfullyConfigured` になっていること
* [ ] NNCPメッセージがすべてのノードで正常に構成されたことを示していること
* [ ] `ovs-vsctl list-br` にbridge名が含まれていること
* [ ] `ovs-vsctl show` で物理インターフェースがポートとしてbridgeに表示されていること
* [ ] 物理インターフェースが `UP,LOWER_UP` ステータスであること
* [ ] 物理インターフェースが `master ovs-system` であること
* [ ] 物理リンクがキャリア状態であること (ケーブル接続済み)
* [ ] NMState Operator ログにエラーがないこと

=== bridge mapping

* [ ] bridge mapping NNCP が `Available: True` であること
* [ ] `ovs-vsctl get Open_vSwitch . external_ids:ovn-bridge-mappings` にmappingが含まれていること
* [ ] mapping 形式が正しいこと: `logical-name:bridge-name`
* [ ] 論理ネットワーク名が NetworkAttachmentDefinition (NAD) / CUDN で使用するものと一致していること
* [ ] mapping 内の bridge 名が実際の OVS bridge と一致していること
* [ ] 物理インターフェースが bridge に接続されていること (`ovs-vsctl list-ports`)
* [ ] 他の bridge mapping との競合がないこと

== ClusterUserDefinedNetwork (CUDN) の検証

NetworkAttachmentDefinition の代わりに ClusterUserDefinedNetwork を使用する場合、追加の検証手順が必要です。

=== ステップ 1: CUDN リソースの確認

ClusterUserDefinedNetwork が正常に作成されたか確認します:

[source,bash,role=execute]
----
# すべての CUDN を一覧表示
oc get clusteruserdefinednetwork

# 詳細な CUDN 情報を取得
oc get clusteruserdefinednetwork <cudn-name> -o yaml
----

**期待される出力:**

----
NAME                     AGE
cudn-localnet-vlan-100   5m
----

=== ステップ 2: CUDN 構成の確認

CUDN spec を確認して、適切な構成であることを確かめます:

[source,bash,role=execute]
----
oc get clusteruserdefinednetwork cudn-localnet-vlan-100 -o yaml
----

**確認すべき重要なフィールド:**

[source,yaml]
----
spec:
  namespaceSelector: 
    matchExpressions: 
    - key: kubernetes.io/metadata.name
      operator: In 
      values: ["vm-guests-vlan-prod", "vm-guests-vlan-dev"]
  network:
    topology: Localnet 
    localnet:
      role: Secondary 
      physicalNetworkName: localnet-vlan  # bridge mappingの論理名と一致すること
      vlanID: 100
      ipam:
        mode: Disabled  # ニーズに応じてStaticなども可
----

=== ステップ 3: 自動作成された NetworkAttachmentDefinition の確認

CUDNは選択されたnamespace内に自動的にNetworkAttachmentDefinitionを作成します:

[source,bash,role=execute]
----
# すべてのnamespaceのNADを一覧表示
oc get network-attachment-definitions -A | grep <cudn-name>

# 特定のnamespaceを確認
oc get network-attachment-definitions -n <namespace>
----

**期待される出力:**

----
NAMESPACE             NAME                     AGE
vm-guests-vlan-dev    cudn-localnet-vlan-100   5m
vm-guests-vlan-prod   cudn-localnet-vlan-100   5m
----

=== ステップ 4: physicalNetworkName がbridge mappingと一致することを確認

CUDN内の `physicalNetworkName` は、bridge mapping内の論理ネットワーク名と一致する必要があります:

[source,bash,role=execute]
----
# CUDNのphysicalNetworkNameを取得
oc get clusteruserdefinednetwork <cudn-name> -o jsonpath='{.spec.network.localnet.physicalNetworkName}'

# bridge mappingの論理名を取得
oc get nncp <bridge-mapping-nncp> -o jsonpath='{.spec.desiredState.ovn.bridge-mappings[0].localnet}'

# OVN内で一致することを確認
oc debug node/<node-name> -- chroot /host ovs-vsctl get Open_vSwitch . external_ids:ovn-bridge-mappings
----

**すべてが同じ名前 (例: `localnet-vlan`) を示す必要があります。**

=== ステップ 5: namespaceを跨いだネットワーク可用性の確認

異なるnamespaceのVMが両方ともCUDNを使用できるかテストします:

[source,bash,role=execute]
----
# 最初のnamespaceのVMを確認
oc get vmi -n vm-guests-vlan-prod -o jsonpath='{.items[*].status.interfaces[?(@.name=="cudn_vlan_network")].ipAddress}'

# 2番目のnamespaceのVMを確認
oc get vmi -n vm-guests-vlan-dev -o jsonpath='{.items[*].status.interfaces[?(@.name=="cudn_vlan_network")].ipAddress}'
----

VMがCUDNネットワークに接続されていれば、両方ともIPアドレスが返されるはずです。

=== CUDN 固有のよくある問題

. **選択したnamespaceにNADが作成されない**:
   * **事象**: CUDNは存在するが、`oc get network-attachment-definitions -n <namespace>` に何も表示されない
   * **原因**: namespace セレクターが namespace ラベルと一致しない
   * **解決策**: namespace ラベルが CUDN セレクターと一致することを確認する
+
[source,bash,role=execute]
----
# namespaceラベルを確認
oc get namespace <namespace-name> -o jsonpath='{.metadata.labels}'

# CUDN セレクターを確認
oc get clusteruserdefinednetwork <cudn-name> -o jsonpath='{.spec.namespaceSelector}'
----

. **VMが "failed bridge mapping validation" で失敗する**:
   * **事象**: CUDN が存在するにもかかわらず、VM Pod が失敗する
   * **原因**: CUDN 内の `physicalNetworkName` がbridge mappingの論理名と一致しない
   * **解決策**: 完全一致 (大文字小文字を区別) することを確認する
+
[source,bash,role=execute]
----
# 名前の比較
oc get clusteruserdefinednetwork <cudn-name> -o jsonpath='{.spec.network.localnet.physicalNetworkName}'
oc get nncp <bridge-mapping-nncp> -o jsonpath='{.spec.desiredState.ovn.bridge-mappings[0].localnet}'
----

. **IPAMモードの問題**:
   * **事象**: VMが期待通りのIPアドレスを取得できない
   * **原因**: IPAMモードの構成ミス、またはcloud-initが機能していない
   * **cloud-init経由の固定IP**: CUDN で `ipam.mode: Disabled` に設定
   * **OVN IPAMの場合**: `staticIPAMConfig` を含めて `ipam.mode: Static` に設定
   * **検証**:
+
[source,bash,role=execute]
----
# IPAMモードを確認
oc get clusteruserdefinednetwork <cudn-name> -o jsonpath='{.spec.network.localnet.ipam.mode}'

# VM内のcloud-initログを確認
virtctl console -n <namespace> <vm-name>
# VM内: cat /var/log/cloud-init.log
----

== Localnet VLAN ネットワークのトラブルシューティング

=== よくある問題

. **VLANトラフィックがVMに到達しない**:
   * 物理スイッチの構成がVLANタグ付けをサポートしているか確認
   * ワーカーノード上のbridge mapping構成を確認
   * VLAN IDがネットワークインフラと一致しているか確認
   * 物理NICが接続されており、UP状態であることを確認
   * OVS bridgeが物理インターフェースをポートとして含んでいるか確認

. **IPアドレスの割り当て問題**:
   * DHCPサーバーがVLANネットワーク上で使用可能か確認

. **ネットワーク接続の問題**:
   * 物理ネットワークが構成済みのVLANをサポートしているか確認
   * 物理ネットワークからVLANサブネットへの接続をテスト
   * 物理スイッチポートがトランクモードになっているか確認

. **カスタムbridge作成の問題**:
   * 注意: OVS bridgeは `ip addr show` に表示されません。代わりに `ovs-vsctl list-br` を使用してください。
   * 物理インターフェース名が正しいことを確認してください。
   * NMState Operator が正常に動作しているか確認してください。

. **bridge mappingが機能しない**:
   * mapping内のbridge名が作成済みのbridgeと一致しているか確認
   * OVN bridge mappingを確認: `ovs-vsctl get Open_vSwitch . external_ids:ovn-bridge-mappings`
   * mapping内のlocalnet名がNAD構成と一致しているか確認

. **VM Pod が "failed bridge mapping validation" エラーで失敗する**:
   * **事象**: VM Pod が次のエラーで失敗する: `failed to find OVN bridge-mapping for network: "localnet-vlan-100"`
   * **原因**: NetworkAttachmentDefinition に `physicalNetworkName` パラメーターがない
   * **解決策**: NAD が bridge mapping の論理名と一致する `"physicalNetworkName": "localnet-vlan"` を含んでいるか確認する
   * **検証**: NADを更新した後、`oc delete` と `oc apply` で再作成する

=== 検証コマンド

[source,bash,role=execute]
----
# NetworkAttachmentDefinitionのステータスを確認
oc get network-attachment-definitions -n vm-guests-vlan

# すべてのNodeNetworkConfigurationPoliciesを確認
oc get nncp

# bridge 作成ステータスを確認 (カスタムbridge使用時)
oc get nncp br-vlan-creation -o yaml

# ワーカーノード上のbridge mappingを確認
oc get nncp localnet-vlan-bridge-mapping -o yaml

# ワーカーノード上の物理インターフェースステータスを確認
oc debug node/<worker-node-name> -- chroot /host ip link show ens224

# OVS bridge構成を確認
oc debug node/<worker-node-name> -- chroot /host ovs-vsctl show

# OVNbridge mappingを確認
oc debug node/<worker-node-name> -- chroot /host ovs-vsctl get Open_vSwitch . external_ids:ovn-bridge-mappings

# カスタムbridge上のすべてのポートを一覧表示
oc debug node/<worker-node-name> -- chroot /host ovs-vsctl list-ports br-vlan

# VMネットワークステータスを確認
oc get vmi -n vm-guests-vlan -o yaml | grep -A 10 networks

# トラブルシューティングのためにOVN-Kubernetesログを表示
oc logs -n openshift-ovn-kubernetes -l app=ovnkube-node

# bridge作成が失敗した場合に NMState Operator ログを確認
oc logs -n openshift-nmstate -l app=kubernetes-nmstate-operator
----

== まとめ

このガイドでは、以下のことを学びました:

* OVS bridge と Linux bridge の違い、および `ip addr show` 出力に表示されない理由
* `ovs-vsctl` を使用して、OVS bridge の作成、物理インターフェースの接続、bridge ポート構成を検証する方法
* 論理ネットワーク名を物理 OVS bridge に接続する OVN bridge mappingを検証する方法
* bridge の欠落、インターフェース接続の失敗、論理名の不一致など、一般的な問題をトラブルシューティングする方法
* ClusterUserDefinedNetwork (CUDN) リソース、自動作成された NAD、namespaceを 跨いだネットワークの可用性を検証する方法
