= OpenShift Virtualization Infrastructure の配置戦略
:navtitle: Infrastructure 配置戦略

== 概要

OpenShift Virtualization のインフラストラクチャコンポーネント (virt-controller、virt-api、virt-handler、CDI) は、`openshift-cnv` namespace 内の Pod として実行されます。本番環境では、これらのインフラストラクチャコンポーネントがどこで実行されるかを制御する必要があります。例えば、仮想化インフラストラクチャ用に特定のノードを専用化する、VM ワークロードとインフラストラクチャを分離する、あるいはゾーン間での高可用性を最適化するといったケースです。

本チュートリアルでは、HyperConverged カスタムリソースを使用して、OpenShift Virtualization インフラストラクチャコンポーネントのノード配置を構成する方法について説明します。

=== 学習内容

* OpenShift Virtualization インフラストラクチャコンポーネントの仕組み
* HyperConverged CR を介したインフラストラクチャ配置の構成方法
* Infrastructure Pod の NodeSelector と Affinity の設定
* クラスターサイズ別の一般的な配置パターン
* インフラストラクチャ専用ノードでの Taint と Toleration の使用方法

== 前提条件

* OpenShift Virtualization がインストールされた OpenShift 4.18 以上
* HyperConverged CR を編集するためのクラスター管理者権限
* インストール済みの `oc` CLI ツール
* 複数の Worker Node (適切な配置構成のために推奨) 

== インフラストラクチャコンポーネントの理解

OpenShift Virtualization のインフラストラクチャには、いくつかの主要コンポーネントが含まれます。

[cols="1,2,1",options="header"]
|===
|コンポーネント |目的 |デプロイメントタイプ

|virt-controller
|VM のライフサイクルとオーケストレーションを管理
|Deployment (2 レプリカ)

|virt-api
|仮想化リソース用の API サーバーを提供
|Deployment (2 レプリカ)

|virt-handler
|各ノード上の VM インスタンスを管理
|DaemonSet

|cdi-controller
|ディスクインポート用の Containerized Data Importer を管理
|Deployment (1 レプリカ)

|cdi-uploadproxy
|Web コンソール経由の VM ディスクアップロードを処理
|Deployment (1 レプリカ)

|cdi-apiserver
|CDI API エンドポイントを提供
|Deployment (1 レプリカ)

|hco-webhook
|HyperConverged CR の変更を検証
|Deployment (1 レプリカ)
|===

== HyperConverged カスタムリソース

インフラストラクチャの配置は、HyperConverged CR を通じて構成されます。

[source,bash,role=execute]
----
# 現在の HyperConverged 設定を表示
oc get hyperconverged kubevirt-hyperconverged -n openshift-cnv -o yaml
----

HyperConverged CR は、2 つの主要な配置構成を提供します。

[cols="1,2",options="header"]
|===
|フィールド |制御対象

|`spec.infra.nodePlacement`
|Control plane コンポーネント: virt-api、virt-controller、cdi-controller、cdi-uploadproxy

|`spec.workloads.nodePlacement`
|ノード単位のコンポーネント: virt-handler DaemonSet
|===

IMPORTANT: HyperConverged CR は、OpenShift Virtualization Operator によって管理されます。変更はクラスター全体に適用され、すべてのインフラストラクチャコンポーネントに自動的に反映されます。

== 配置の構成オプション

=== NodeSelector の使用

NodeSelector は、ラベルに基づいた単純な配置を提供します。

[source,bash,role=execute]
----
# 仮想化インフラストラクチャ用にノードにラベルを付与
oc label node ip-10-0-24-89.ec2.internal node-role.kubernetes.io/infra=
oc label node ip-10-0-43-58.ec2.internal node-role.kubernetes.io/infra=
----

HyperConverged CR を編集します。

[source,bash,role=execute]
----
oc edit hyperconverged kubevirt-hyperconverged -n openshift-cnv
----

NodeSelector の構成を追加します。

[source,yaml]
----
apiVersion: hco.kubevirt.io/v1beta1
kind: HyperConverged
metadata:
  name: kubevirt-hyperconverged
  namespace: openshift-cnv
spec:
  infra:
    nodePlacement:
      nodeSelector:
        node-role.kubernetes.io/infra: ""
  workloads:
    nodePlacement:
      nodeSelector:
        node-role.kubernetes.io/worker: ""
----

この構成により以下が実現されます。

* **Control plane コンポーネント** (virt-api、virt-controller、CDI) は、`node-role.kubernetes.io/infra` ラベルを持つノードでのみ実行されます。
* **virt-handler DaemonSet**は、`node-role.kubernetes.io/worker` ラベルを持つすべてのノードで実行されます。

=== NodeAffinity の使用

より複雑な配置ルールには、NodeAffinity を使用します。

[source,yaml]
----
apiVersion: hco.kubevirt.io/v1beta1
kind: HyperConverged
metadata:
  name: kubevirt-hyperconverged
  namespace: openshift-cnv
spec:
  infra:
    nodePlacement:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: node-role.kubernetes.io/infra
                operator: Exists
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 100
            preference:
              matchExpressions:
              - key: topology.kubernetes.io/zone
                operator: In
                values:
                - us-east-1a
                - us-east-1b
----

この構成により以下が実現されます。

* インフラストラクチャノードを**必須**とする (ハード制約) 
* 特定の可用性ゾーンを**優先**する (ソフト制約) 

=== Taint されたノードへの Toleration の使用

通常のワークロードがインフラストラクチャノードで実行されないように、インフラストラクチャノードに Taint を付けます。

[source,bash,role=execute]
----
# インフラストラクチャノードに Taint を付与
oc adm taint node ip-10-0-24-89.ec2.internal node-role.kubernetes.io/infra=:NoSchedule
oc adm taint node ip-10-0-43-58.ec2.internal node-role.kubernetes.io/infra=:NoSchedule
----

対応する Toleration を HyperConverged CR に追加します。

[source,yaml]
----
apiVersion: hco.kubevirt.io/v1beta1
kind: HyperConverged
metadata:
  name: kubevirt-hyperconverged
  namespace: openshift-cnv
spec:
  infra:
    nodePlacement:
      nodeSelector:
        node-role.kubernetes.io/infra: ""
      tolerations:
      - key: node-role.kubernetes.io/infra
        operator: Exists
        effect: NoSchedule
  workloads:
    nodePlacement:
      nodeSelector:
        node-role.kubernetes.io/worker: ""
----

これで、一致する Toleration (Virtualization Infrastructure) を持つ Pod のみが、Taint されたインフラストラクチャノードで実行可能になります。

=== 高可用性のための Pod Anti-Affinity の使用

可用性を高めるために、インフラストラクチャコンポーネントをゾーン間で分散させます。

[source,yaml]
----
apiVersion: hco.kubevirt.io/v1beta1
kind: HyperConverged
metadata:
  name: kubevirt-hyperconverged
  namespace: openshift-cnv
spec:
  infra:
    nodePlacement:
      affinity:
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 100
            podAffinityTerm:
              labelSelector:
                matchLabels:
                  kubevirt.io: virt-api
              topologyKey: topology.kubernetes.io/zone
          - weight: 100
            podAffinityTerm:
              labelSelector:
                matchLabels:
                  kubevirt.io: virt-controller
              topologyKey: topology.kubernetes.io/zone
----

これにより、virt-api と virt-controller の複数のレプリカが確実に異なるゾーンへ分散されます。

== 一般的なデプロイメントパターン

=== パターン 1: 小規模クラスター (3-6 ノード)

インフラストラクチャと VM ワークロードを同じ Worker Node で実行します。

[source,yaml]
----
apiVersion: hco.kubevirt.io/v1beta1
kind: HyperConverged
metadata:
  name: kubevirt-hyperconverged
  namespace: openshift-cnv
spec:
  infra:
    nodePlacement:
      nodeSelector:
        node-role.kubernetes.io/worker: ""
  workloads:
    nodePlacement:
      nodeSelector:
        node-role.kubernetes.io/worker: ""
----

**使用例**: 開発環境、テスト環境、あるいはノードの専用化がコスト効率的ではない小規模な本番クラスター

=== パターン 2: 専用インフラストラクチャを持つ中規模クラスター

インフラストラクチャを VM ワークロードから分離します。

[source,bash,role=execute]
----
# インフラストラクチャノードにラベルを付与
oc label node ip-10-0-24-89.ec2.internal node-role.kubernetes.io/infra=
oc label node ip-10-0-43-58.ec2.internal node-role.kubernetes.io/infra=

# インフラストラクチャノードに Taint を付与
oc adm taint node ip-10-0-24-89.ec2.internal node-role.kubernetes.io/infra=:NoSchedule
oc adm taint node ip-10-0-43-58.ec2.internal node-role.kubernetes.io/infra=:NoSchedule

# VM 用に Worker Node にラベルを付与
oc label node ip-10-0-82-27.ec2.internal kubevirt.io/schedulable=true
----

HyperConverged の構成:

[source,yaml]
----
apiVersion: hco.kubevirt.io/v1beta1
kind: HyperConverged
metadata:
  name: kubevirt-hyperconverged
  namespace: openshift-cnv
spec:
  infra:
    nodePlacement:
      nodeSelector:
        node-role.kubernetes.io/infra: ""
      tolerations:
      - key: node-role.kubernetes.io/infra
        operator: Exists
        effect: NoSchedule
  workloads:
    nodePlacement:
      nodeSelector:
        kubevirt.io/schedulable: "true"
----

**使用例**: VM ワークロードのリソース競合から隔離された、予測可能なインフラストラクチャパフォーマンスを求める本番クラスター

=== パターン 3: 大規模なマルチゾーン高可用性

Anti-Affinity を使用して、インフラストラクチャをゾーン間で分散します。

[source,yaml]
----
apiVersion: hco.kubevirt.io/v1beta1
kind: HyperConverged
metadata:
  name: kubevirt-hyperconverged
  namespace: openshift-cnv
spec:
  infra:
    nodePlacement:
      nodeSelector:
        node-role.kubernetes.io/infra: ""
      affinity:
        nodeAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 100
            preference:
              matchExpressions:
              - key: topology.kubernetes.io/zone
                operator: In
                values:
                - us-east-1a
                - us-east-1b
                - us-east-1c
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 100
            podAffinityTerm:
              labelSelector:
                matchLabels:
                  kubevirt.io: virt-api
              topologyKey: topology.kubernetes.io/zone
          - weight: 100
            podAffinityTerm:
              labelSelector:
                matchLabels:
                  kubevirt.io: virt-controller
              topologyKey: topology.kubernetes.io/zone
      tolerations:
      - key: node-role.kubernetes.io/infra
        operator: Exists
        effect: NoSchedule
  workloads:
    nodePlacement:
      nodeSelector:
        kubevirt.io/schedulable: "true"
----

**使用例**: ゾーンレベルのフォールトトレランスを必要とする、厳格な可用性 SLA を持つエンタープライズ本番環境

== 構成変更の適用

=== HyperConverged CR を直接編集

[source,bash,role=execute]
----
oc edit hyperconverged kubevirt-hyperconverged -n openshift-cnv
----

=== HyperConverged CR にパッチを適用

[source,bash,role=execute]
----
oc patch hyperconverged kubevirt-hyperconverged -n openshift-cnv --type=merge -p '
{
  "spec": {
    "infra": {
      "nodePlacement": {
        "nodeSelector": {
          "node-role.kubernetes.io/infra": ""
        }
      }
    }
  }
}'
----

=== 変更の適用確認

Infrastructure Pod の再スケジュールを監視します。

[source,bash,role=execute]
----
# Pod の変更をリアルタイムで監視
oc get pods -n openshift-cnv -w

# 変更が反映された後に新しい配置を確認
oc get pods -n openshift-cnv -o wide

# 特定コンポーネントの配置を確認
oc get pods -n openshift-cnv -l kubevirt.io=virt-api -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.nodeName}{"\n"}{end}'
----

想定される動作:

* Infrastructure Pod が終了され、一致するノード上で再作成されます。
* virt-handler DaemonSet は、NodeSelector の変更に基づいて Pod を追加/削除します。
* 変更は通常 2〜5 分以内に完了します。

== モニタリングと検証

=== Pod の分散状況を確認

[source,bash,role=execute]
----
# Pod をノード別にグループ化
oc get pods -n openshift-cnv -o jsonpath='{range .items[*]}{.spec.nodeName}{"\t"}{.metadata.name}{"\n"}{end}' | sort | column -t

# ノードあたりの Pod 数を集計
oc get pods -n openshift-cnv -o jsonpath='{range .items[*]}{.spec.nodeName}{"\n"}{end}' | sort | uniq -c
----

=== Toleration を確認

[source,bash,role=execute]
----
# virt-api pod に正しい Toleration が設定されているか確認
oc get pods -n openshift-cnv -l kubevirt.io=virt-api -o jsonpath='{.items[0].spec.tolerations}' | jq
----

=== NodeAffinity の適用状況を確認

[source,bash,role=execute]
----
# virt-controller の NodeAffinity を表示
oc get pods -n openshift-cnv -l kubevirt.io=virt-controller -o jsonpath='{.items[0].spec.affinity}' | jq
----

== トラブルシューティング

=== Infrastructure Pod が保留 (Pending) 状態でスタックする

**問題**: 配置構成を変更した後、Infrastructure Pod が Pending 状態のままになる。

**調査**:

[source,bash,role=execute]
----
# Pod のイベントを確認
oc describe pod <pod-name> -n openshift-cnv

# スケジューリングエラーを検索
oc get events -n openshift-cnv --sort-by='.lastTimestamp' | grep -i failedscheduling
----

**一般的な原因**:

* NodeSelector や Affinity rule に一致するノードがない
* ノードに Taint が付いているが、Toleration がない
* 一致するノードのリソースが不足している

**解決策**:

[source,bash,role=execute]
----
# ノードに必要なラベルがあるか確認
oc get nodes -L node-role.kubernetes.io/infra

# ノードの Taint を確認
oc get nodes -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.taints}{"\n"}{end}'

# ノードのキャパシティを確認
oc describe nodes | grep -A 5 "Allocated resources"
----

=== virt-handler がすべてのノードで実行されない

**問題**: virt-handler DaemonSet の Pod が一部のノードで欠落している。

**調査**:

[source,bash,role=execute]
----
# virt-handler DaemonSet のステータスを確認
oc get daemonset virt-handler -n openshift-cnv

# 期待数と現在の Pod 数を比較
oc describe daemonset virt-handler -n openshift-cnv | grep -E "Desired|Current|Ready"
----

**解決策**: `spec.workloads.nodePlacement` Selector がノードに一致しているか確認します。

[source,bash,role=execute]
----
# workloads の NodeSelector を表示
oc get hyperconverged kubevirt-hyperconverged -n openshift-cnv -o jsonpath='{.spec.workloads.nodePlacement}' | jq

# ノードがセレクターに一致するか確認
oc get nodes --selector=<label-from-workloads-nodeSelector>
----

=== 構成変更が適用されない

**問題**: HyperConverged CR を編集したが、Infrastructure Pod が変更されない。

**HyperConverged CR ステータスの確認**:

[source,bash,role=execute]
----
# HyperConverged のステータスを表示
oc get hyperconverged kubevirt-hyperconverged -n openshift-cnv -o yaml | grep -A 10 status:

# 検証エラーを確認
oc get events -n openshift-cnv --sort-by='.lastTimestamp' | grep HyperConverged
----

**強制的に同期させる**:

[source,bash,role=execute]
----
# アノテーションを追加して reconciliation をトリガー
oc annotate hyperconverged kubevirt-hyperconverged -n openshift-cnv reconcile-trigger="$(date +%s)" --overwrite
----

== ベストプラクティス

1. **インフラストラクチャキャパシティの計画**: インフラストラクチャノードには、virt-controller、virt-api、CDI コンポーネントのために十分な CPU とメモリが必要です (ノードあたり最低 4 vCPU、8GB RAM を推奨) 。

2. **複数のインフラストラクチャノードを使用する**: Control plane コンポーネントの高可用性を確保するため、少なくとも 2 つのインフラストラクチャノードを実行してください。

3. **大規模クラスターではワークロードを分離する**: 専用のインフラストラクチャノードにより、VM ワークロードのリソース競合が Virtualization Control plane に影響を与えるのを防ぎます。

4. **ゾーントポロジーを活用する**: Node/PodAffinity を使用して、インフラストラクチャを可用性ゾーン全体に分散させ、フォールトトレランスを向上させます。

5. **インフラストラクチャの健全性を監視する**: Infrastructure Pod の障害やリソース枯渇に対するアラートを設定します。

6. **配置変更をテストする**: 本番環境に適用する前に、開発/ステージング環境で構成変更をテストします。

7. **ノードロールを文書化する**: どのノードがどの役割を果たすかを明確にラベル付けし、文書化します。

== クリーンアップ

デフォルトの配置 (すべての Worker Node) に戻すには、以下の手順を行います。

[source,bash,role=execute]
----
# HyperConverged CR を編集し nodePlacement セクションを削除
oc patch hyperconverged kubevirt-hyperconverged -n openshift-cnv --type=json -p='[
  {"op": "remove", "path": "/spec/infra/nodePlacement"},
  {"op": "remove", "path": "/spec/workloads/nodePlacement"}
]'

# インフラストラクチャノードのラベルを削除
oc label node ip-10-0-24-89.ec2.internal node-role.kubernetes.io/infra-
oc label node ip-10-0-43-58.ec2.internal node-role.kubernetes.io/infra-

# Taint が適用されている場合は削除
oc adm taint node ip-10-0-24-89.ec2.internal node-role.kubernetes.io/infra:NoSchedule-
oc adm taint node ip-10-0-43-58.ec2.internal node-role.kubernetes.io/infra:NoSchedule-
----
