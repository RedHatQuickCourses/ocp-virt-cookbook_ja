= Selector および Affinity rule による VM ノードの配置
:navtitle: ノードの配置と Affinity

== 概要

ノードの配置は、どの OpenShift クラスターノードで仮想マシンを実行するかを制御します。デフォルトでは、Kubernetes スケジューラーが利用可能なノード全体に VM を自動的に配置しますが、特定のハードウェアを持つノードで特定の VM を実行する、ワークロードを分離する、あるいはパフォーマンスや可用性の理由から VM 同士を近くに配置したり遠ざけたりするなど、より詳細な制御が必要になることがよくあります。

このチュートリアルでは、OpenShift Virtualization における VM 配置を制御するための、NodeSelector、NodeAffinity、PodAffinity/Anti-Affinity rule について説明します。

=== 学習内容

* 単純なノード配置に NodeSelector を使用する方法
* NodeAffinity rule (必須 (required)、優先 (preferred)) の設定方法
* VM の共存を制御するために PodAffinity/Anti-Affinity を使用する方法
* ノードにラベルを付け、配置を確認する方法
* 一般的な配置パターンとトラブルシューティング

== 前提条件

* OpenShift 4.18 以降と OpenShift Virtualization がインストールされていること
* ノードにラベルを付けるためのクラスター管理者権限
* `oc` および `virtctl` CLI ツールがインストールされていること
* クラスター内に複数の Worker Node があること (意味のある配置を行うため) 

== ノード配置オプションの理解

OpenShift Virtualization には、VM の実行場所を制御するための 3 つの主要なメカニズムがあります。

[cols="1,2,2",options="header"]
|===
|メカニズム |ユースケース |利点

|NodeSelector
|特定のラベルを持つノードに VM を配置する
|シンプルで理解しやすい

|NodeAffinity
|必須 (required) /優先 (preferred) ルールを用いた複雑なノード選択
|柔軟性が高く、複数の条件をサポート

|PodAffinity/Anti-Affinity
|他の VM や Pod に関連付けて VM を配置する
|VM の共存パターンを制御する
|===

IMPORTANT: VM の配置ルールは、その VM を実行する基盤となる `virt-launcher` Pod に適用されます。Kubernetes スケジューラーは、Pod をノードに配置する際にこれらのルールを評価します。

=== ノードへのカスタムラベルの追加

特性 (ハードウェア、場所、ワークロードの種類) に基づいてノードにラベルを付けます。

[source,bash,role=execute]
----
# Get worker node names
WORKER1=$(oc get nodes -l node-role.kubernetes.io/worker -o jsonpath='{.items[0].metadata.name}')
WORKER2=$(oc get nodes -l node-role.kubernetes.io/worker -o jsonpath='{.items[1].metadata.name}')
WORKER3=$(oc get nodes -l node-role.kubernetes.io/worker -o jsonpath='{.items[2].metadata.name}')

# Label nodes by environment
oc label node $WORKER1 env=development
oc label node $WORKER2 env=production

# Label nodes by GPU type
oc label node $WORKER1 gpu=nvidia-t4
oc label node $WORKER2 gpu=nvidia-a100

# Label nodes by disk type
oc label node $WORKER1 storage=ssd
oc label node $WORKER3 storage=nvme

# Label nodes by workload type
oc label node $WORKER1 workload=database
----

ラベルを確認します。

[source,bash,role=execute]
----
WORKER1=$(oc get nodes -l node-role.kubernetes.io/worker -o jsonpath='{.items[0].metadata.name}')
oc get node $WORKER1 -o jsonpath='{.metadata.labels}' | jq
----

出力例:
[source,json]
----
{
  "beta.kubernetes.io/arch": "amd64",
  "beta.kubernetes.io/os": "linux",
  "env": "development",
  "gpu": "nvidia-t4",
  "kubernetes.io/arch": "amd64",
  "kubernetes.io/hostname": "ip-10-0-24-89.ec2.internal",
  "kubernetes.io/os": "linux",
  "node-role.kubernetes.io/worker": "",
  "storage": "ssd",
  "workload": "database"
}
----

[source,bash,role=execute]
----
WORKER1=$(oc get nodes -l node-role.kubernetes.io/worker -o jsonpath='{.items[0].metadata.name}')
oc label node $WORKER1 gpu-

== NodeSelector の使用

NodeSelector は、ノードラベルを正確に一致させることで VM の配置を制御する最もシンプルな方法です。

=== チュートリアル用 namespace の作成

まず、チュートリアルのリソースを配置するための namespace を作成します。

[source,bash,role=execute]
----
oc create namespace vm-placement
----

=== 基本的な NodeSelector の例

`storage=ssd` というラベルを持つノードでのみ実行される VM を作成します。

WARNING: この例の cloud-init パスワードはデモ目的のみです。本番環境では常に強力で一意なパスワードや SSH 鍵認証を使用してください。

xref:attachment$node-placement-affinity/vm-node-selector.yaml[Download vm-node-selector.yaml]

[source,yaml]
----
apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: database-vm
  namespace: vm-placement
spec:
  runStrategy: Manual
  template:
    metadata:
      labels:
        app: database
    spec:
      nodeSelector:
        storage: ssd  # VM will only run on nodes with storage=ssd label
      domain:
        cpu:
          cores: 2
        memory:
          guest: 4Gi
        devices:
          disks:
          - name: rootdisk
            disk:
              bus: virtio
          - name: cloudinitdisk
            disk:
              bus: virtio
      volumes:
      - name: rootdisk
        containerDisk:
          image: quay.io/containerdisks/fedora:43
      - name: cloudinitdisk
        cloudInitNoCloud:
          userData: |
            #cloud-config
            user: fedora
            password: fedora
            chpasswd: { expire: False }
----

VM に適用して起動します。

[source,bash,role=execute]
----
oc apply -f vm-node-selector.yaml
virtctl start database-vm -n vm-placement
----

=== ノード配置の確認

VM がどのノードで実行されているかを確認します。

[source,bash,role=execute]
----
oc get vmi database-vm -n vm-placement -o wide
----

出力例:
[source,text]
----
NAME          AGE   PHASE     IP             NODENAME   READY
database-vm   45s   Running   10.128.0.200   ocplab02   True
----

ノードに必要なラベルがあることを確認します。

[source,bash,role=execute]
----
oc get vmi database-vm -n vm-placement -o jsonpath='{.status.nodeName}' | xargs oc get node -L storage
----

出力例:
[source,text]
----
NAME       STATUS   ROLES    AGE   VERSION   STORAGE
ip-10-0-24-89.ec2.internal   Ready    worker   30d   v1.30.0   ssd
----

=== 複数のラベル選択

NodeSelector は複数のラベルをサポートしています (すべて一致する必要があります) 。

[source,yaml]
----
spec:
  template:
    spec:
      nodeSelector:
        storage: ssd
        env: production
        gpu: nvidia-t4
----

VM は、指定された値を持つこれら 3 つすべてのラベルを持つノードでのみ実行されます。

== NodeAffinity の使用

NodeAffinity は、必須 (required) および優先 (preferred) ルールにより、より柔軟なノード選択を提供します。

=== NodeAffinity の必須 (required) 設定

required Affinity (ハード要件) は、一致するノードが存在しない場合にスケジュールを防止します。

xref:attachment$node-placement-affinity/vm-node-affinity-required.yaml[Download vm-node-affinity-required.yaml]

[source,yaml]
----
apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: gpu-workload-vm
  namespace: vm-placement
spec:
  runStrategy: Manual
  template:
    metadata:
      labels:
        app: ml-training
    spec:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: gpu
                operator: In
                values:
                - nvidia-t4
                - nvidia-a100
              - key: env
                operator: In
                values:
                - production
      domain:
        cpu:
          cores: 4
        memory:
          guest: 8Gi
        devices:
          disks:
          - name: rootdisk
            disk:
              bus: virtio
          - name: cloudinitdisk
            disk:
              bus: virtio
      volumes:
      - name: rootdisk
        containerDisk:
          image: quay.io/containerdisks/fedora:43
      - name: cloudinitdisk
        cloudInitNoCloud:
          userData: |
            #cloud-config
            user: fedora
            password: fedora
            chpasswd: { expire: False }
----

ポイント:

* **requiredDuringSchedulingIgnoredDuringExecution**: 一致するノードが存在しない場合、VM は起動しません。
* **matchExpressions**: `In`、`NotIn`、`Exists`、`DoesNotExist`、`Gt`、`Lt` などの演算子をサポートします。
* **nodeSelectorTerms**: 複数の項は OR 関係 (いずれかの項が一致すればよい) になります。
* 1 つの項の中にある複数の **matchExpressions** は AND 関係 (すべて一致する必要がある) になります。

=== NodeAffinity の優先 (preferred) 設定

preferred Affinity (ソフト要件) は、一致するノードへの配置を試みますが、必要に応じて他のノードを使用することも可能です。

xref:attachment$node-placement-affinity/vm-node-affinity-preferred.yaml[Download vm-node-affinity-preferred.yaml]

[source,yaml]
----
apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: web-vm
  namespace: vm-placement
spec:
  runStrategy: Manual
  template:
    metadata:
      labels:
        app: webserver
    spec:
      affinity:
        nodeAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 100
            preference:
              matchExpressions:
              - key: storage
                operator: In
                values:
                - nvme
          - weight: 50
            preference:
              matchExpressions:
              - key: storage
                operator: In
                values:
                - ssd
      domain:
        cpu:
          cores: 2
        memory:
          guest: 2Gi
        devices:
          disks:
          - name: rootdisk
            disk:
              bus: virtio
          - name: cloudinitdisk
            disk:
              bus: virtio
      volumes:
      - name: rootdisk
        containerDisk:
          image: quay.io/containerdisks/fedora:43
      - name: cloudinitdisk
        cloudInitNoCloud:
          userData: |
            #cloud-config
            user: fedora
            password: fedora
            chpasswd: { expire: False }
----

ポイント:

* **preferredDuringSchedulingIgnoredDuringExecution**: スケジューラーは一致するノードを優先しますが、他へ配置することもできます。
* **weight**: 1〜100。ウェイトが高いほど優先順位が高くなります。
* 複数の preference (優先条件) は加算方式であり、それぞれのスコアが合算されます。

=== 必須 (required) および優先 (preferred) Affinity の組み合わせ

[source,yaml]
----
spec:
  template:
    spec:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: env
                operator: In
                values:
                - production
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 100
            preference:
              matchExpressions:
              - key: storage
                operator: In
                values:
                - nvme
----

この VM はプロダクションノードで実行される必要がありますが、NVMe ストレージを持つノードが好ましいことを意味します。

== PodAffinity と Anti-Affinity の使用

PodAffinity および Anti-Affinity は、他の VM や Pod に関連付けて VM の配置を制御し、共存や分離のパターンを実現します。

=== PodAffinity: VM を一緒に実行する

PodAffinity を使用して、VM を同じノード上または同じアベイラビリティーゾーン内で実行します。

xref:attachment$node-placement-affinity/vm-pod-affinity.yaml[Download vm-pod-affinity.yaml]

[source,yaml]
----
apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: web-frontend-vm
  namespace: vm-placement
spec:
  runStrategy: Manual
  template:
    metadata:
      labels:
        app: web-frontend
        tier: frontend
    spec:
      affinity:
        podAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchExpressions:
              - key: app
                operator: In
                values:
                - database
            topologyKey: kubernetes.io/hostname
      domain:
        cpu:
          cores: 2
        memory:
          guest: 2Gi
        devices:
          disks:
          - name: rootdisk
            disk:
              bus: virtio
          - name: cloudinitdisk
            disk:
              bus: virtio
      volumes:
      - name: rootdisk
        containerDisk:
          image: quay.io/containerdisks/fedora:43
      - name: cloudinitdisk
        cloudInitNoCloud:
          userData: |
            #cloud-config
            user: fedora
            password: fedora
            chpasswd: { expire: False }
----

この VM は、`app=database` ラベルを持つ Pod/VM と同じノード (`topologyKey: kubernetes.io/hostname`) で実行されます。

一般的なトポロジーキー:

[cols="1,2",options="header"]
|===
|トポロジーキー |効果

|`kubernetes.io/hostname`
|同一物理ノード

|`topology.kubernetes.io/zone`
|同一アベイラビリティーゾーン

|`topology.kubernetes.io/region`
|同一リージョン
|===

=== PodAnti-Affinity: VM を分離する

高可用性を確保するために、PodAnti-Affinity を使用してノード間に VM を分散させます。

xref:attachment$node-placement-affinity/vm-pod-anti-affinity.yaml[Download vm-pod-anti-affinity.yaml]

[source,yaml]
----
apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: cache-vm-01
  namespace: vm-placement
spec:
  runStrategy: Manual
  template:
    metadata:
      labels:
        app: redis-cache
        role: cache
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchExpressions:
              - key: app
                operator: In
                values:
                - redis-cache
            topologyKey: kubernetes.io/hostname
      domain:
        cpu:
          cores: 2
        memory:
          guest: 4Gi
        devices:
          disks:
          - name: rootdisk
            disk:
              bus: virtio
          - name: cloudinitdisk
            disk:
              bus: virtio
      volumes:
      - name: rootdisk
        containerDisk:
          image: quay.io/containerdisks/fedora:43
      - name: cloudinitdisk
        cloudInitNoCloud:
          userData: |
            #cloud-config
            user: fedora
            password: fedora
            chpasswd: { expire: False }
----

これにより、複数のキャッシュ VM が同じノードで実行されることがなくなり、可用性が向上します。

=== preferred PodAnti-Affinity

厳格な制約なしでベストエフォート型の分散を行う場合:

[source,yaml]
----
spec:
  template:
    spec:
      affinity:
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 100
            podAffinityTerm:
              labelSelector:
                matchExpressions:
                - key: app
                  operator: In
                  values:
                  - redis-cache
              topologyKey: kubernetes.io/hostname
----

=== 複数の Affinity rule の組み合わせ

[source,yaml]
----
spec:
  template:
    spec:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: env
                operator: In
                values:
                - production
        podAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 100
            podAffinityTerm:
              labelSelector:
                matchExpressions:
                - key: tier
                  operator: In
                  values:
                  - database
              topologyKey: kubernetes.io/hostname
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchExpressions:
              - key: app
                operator: In
                values:
                - web-frontend
            topologyKey: kubernetes.io/hostname
----

この VM は以下のように配置されます:

* プロダクションノードで実行されなければならない
* データベース階層の VM があるノードで実行されることが望ましい
* 他の Web フロントエンド VM があるノードでは実行してはならない

== 一般的な配置パターン

=== パターン 1: 高可用性データベースクラスタ

データベース VM を複数のノードに分散させる:

[source,yaml]
----
apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: postgres-vm-01
  labels:
    app: postgres-cluster
    instance: "01"
spec:
  template:
    metadata:
      labels:
        app: postgres-cluster
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchLabels:
                app: postgres-cluster
            topologyKey: kubernetes.io/hostname
----

各データベース VM レプリカは異なるノードで実行され、単一ノードの障害がクラスター全体に影響を与えるのを防ぎます。

=== パターン 2: GPU ワークロードの分離

GPU ワークロード専用のノードを割り当てる:

[source,yaml]
----
spec:
  template:
    spec:
      nodeSelector:
        gpu: "true"
      tolerations:
      - key: "nvidia.com/gpu"
        operator: "Exists"
        effect: "NoSchedule"
----

NodeSelector と Taints/Toleration を組み合わせて、GPU ノードを GPU ワークロード専用として予約します。

=== パターン 3: 低遅延アプリケーションスタック

アプリケーション階層を同じノード上に共存させる:

[source,yaml]
----
# Backend VM
spec:
  template:
    metadata:
      labels:
        app: trading-platform
        tier: backend
    spec:
      affinity:
        podAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchExpressions:
              - key: tier
                operator: In
                values:
                - cache
                - database
            topologyKey: kubernetes.io/hostname
----

=== パターン 4: 環境の分離

開発用 VM がプロダクションノードで実行されないようにする:

[source,yaml]
----
spec:
  template:
    spec:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: env
                operator: In
                values:
                - development
----

== Web コンソールによる配置の確認

. **Virtualization** -> **VirtualMachines** に移動します。
. VM をクリックして詳細を表示します。
. **Configuration** タブをクリックします。
. **Scheduling** サブタブに移動します。
. 設定された NodeSelector、Affinity、Toleration が表示されます。
. **Overview** タブで、VM がどのノードで実行されているかを確認します。

== トラブルシューティング

=== VM が保留 (Pending) 状態でスタックしている

**問題**: VM が保留状態のまま起動しません。

**調査**:

[source,bash,role=execute]
----
# Check VM status
oc get vm -n vm-placement

# Check VMI events
oc describe vmi <vm-name> -n vm-placement
----

次のようなイベントを探します:

[source,text]
----
Warning  FailedScheduling  0/3 nodes are available: 3 node(s) didn't match Pod's node affinity/selector
----

**考えられる原因**:

* NodeSelector または required Affinity rule に一致するノードが存在しない。
* 一致するすべてのノードが満杯 (CPU/メモリ不足) 。
* ノード上の Taint によりスケジュールが許可されていない。

**解決策**:

[source,bash,role=execute]
----
# Verify node labels exist
oc get nodes -L storage,env,gpu

# Check if nodes have required labels
oc get nodes --selector=storage=ssd

# Review VM placement constraints
oc get vm <vm-name> -n vm-placement -o yaml | grep -A 20 "affinity:"
----

一致するノードがない場合、以下のいずれかを行います:

* ノードに必要なラベルを追加する。
* 配置制約を緩和する。
* required Affinity を preferred Affinity に変更する。

=== VM が意図しないノードで実行されている

**問題**: VM が preferred Affinity と一致しないノードで実行されています。

**説明**: preferred Affinity はソフト制約です。以下の場合はスケジューラーがそれを無視することがあります:

* 優先設定に一致するノードがない。
* 一致するノードにリソースがない。
* 他の VM の優先順位の方が高い。

**確認**:

[source,bash,role=execute]
----
# Check where VM is running
oc get vmi <vm-name> -n vm-placement -o jsonpath='{.status.nodeName}'

# Check that node's labels
oc get node <node-name> --show-labels
----

**解決策**:

* 配置が重要であれば、preferred Affinity を required Affinity に変更する。
* 優先ルールのウェイトを増やす。
* 一致するノードに十分なリソースがあることを確認する。

=== Anti-Affinity が機能しない

**問題**: Anti-Affinity ルールを持つ複数の VM が同じノードで実行されています。

**調査**:

[source,bash,role=execute]
----
# List all VMs and their nodes
oc get vmi -n vm-placement -o wide

# Check anti-affinity configuration
oc get vm <vm-name> -n vm-placement -o yaml | grep -A 15 "podAntiAffinity:"
----

**一般的な問題**:

* **ラベルの不一致**: Anti-Affinity のラベル Selector が VM ラベルと一致していない。
* **間違ったトポロジーキー**: ホスト名の代わりにゾーンを使用している。
* **優先 (preferred) vs 必須 (required)**: preferred を使用している場合、必要に応じて同じノードへの配置が許可される。
* **ノード不足**: すべてのレプリカの Anti-Affinity を満たすのに十分なノードがない。

**解決策**:

ラベルが一致しているか確認します:

[source,bash,role=execute]
----
# Check VM labels
oc get vm <vm-name> -n vm-placement -o jsonpath='{.spec.template.metadata.labels}' | jq

# Verify anti-affinity selector matches those labels
oc get vm <vm-name> -n vm-placement -o yaml | grep -A 5 "labelSelector:"
----

=== NodeSelector が無視される

**問題**: VM が指定されたラベルを持たないノードで実行されています。

**NodeSelector が正しく定義されているか確認します**:

[source,bash,role=execute]
----
# View VM spec
oc get vm <vm-name> -n vm-placement -o yaml | grep -A 5 "nodeSelector:"

# Verify it's under spec.template.spec, not just spec
oc get vm <vm-name> -n vm-placement -o jsonpath='{.spec.template.spec.nodeSelector}' | jq
----

**よくある間違い**: YAML 内の間違ったレベルに `nodeSelector` を記述してしまうこと:

[source,yaml]
----
# WRONG - nodeSelector at VM spec level
spec:
  nodeSelector:    # This is ignored!
    storage: ssd
  template:
    spec:
      domain:
        ...

# CORRECT - nodeSelector at pod spec level
spec:
  template:
    spec:
      nodeSelector:  # This works!
        storage: ssd
      domain:
        ...
----

== クリーンアップ

このチュートリアルで作成したリソースを削除します:

[source,bash,role=execute]
----
# Delete VMs
oc delete vm --all -n vm-placement

# Remove custom node labels from all workers
WORKER1=$(oc get nodes -l node-role.kubernetes.io/worker -o jsonpath='{.items[0].metadata.name}')
WORKER2=$(oc get nodes -l node-role.kubernetes.io/worker -o jsonpath='{.items[1].metadata.name}')
WORKER3=$(oc get nodes -l node-role.kubernetes.io/worker -o jsonpath='{.items[2].metadata.name}')

oc label node $WORKER1 storage- env- gpu- workload-
oc label node $WORKER2 storage- env- gpu-
oc label node $WORKER3 storage-
----

クリーンアップを確認します:

[source,bash,role=execute]
----
oc get vm -n vm-placement
oc get nodes --show-labels | grep -E "storage|workload"
----

== まとめ

このチュートリアルでは以下を学習しました:

* NodeSelector、NodeAffinity、PodAffinity/Anti-Affinity の違い
* 配置制御のためにノードにラベルを付ける方法
* 単純な配置制約に NodeSelector を使用する方法
* 必須 (required)、優先 (preferred) NodeAffinity ルールの設定方法
* VM の共存や分離のために PodAffinity/Anti-Affinity を使用する方法
* HA、パフォーマンス、分離のための一般的な配置パターン
* 配置の問題をトラブルシューティングする方法
