= 仮想マシンの内部 DNS 解決
:navtitle: VM の内部 DNS

== 概要

本チュートリアルでは、OpenShift Virtualization において、クラスター内通信のために仮想マシンを安定した DNS 名で探索可能にする方法を説明します。Kubernetes Service を使用して VM の DNS ベースのサービス探索を有効にし、IP アドレスをハードコードすることなく Pod から VM へ、また VM から VM への通信を実現する方法を学びます。

== 学習目標

* Kubernetes Service を使用して VM を公開する方法
* VM の DNS 解決をテストする方法
* OpenShift Virtualization で VM の DNS クエリがどのように解決されるか

== 前提条件

* OpenShift Virtualization Operator がインストールされた OpenShift 4.18 以降
* インストール済みの CLI ツール: `oc`、`virtctl`
* Kubernetes Service と DNS に関する基本的な知識

== パート 1: デプロイ、公開、テスト

=== ステップ 1: namespace の作成

このチュートリアル用の専用 namespace を作成します。

[source,bash,role=execute]
----
oc new-project myapp
----

=== ステップ 2: Fedora VM のデプロイ

Fedora VM をデプロイします。

WARNING: この例の cloud-init パスワードはデモ目的のみのものです。本番環境では、常に強力で一意のパスワードまたは SSH 鍵認証を使用してください。

xref:attachment$internal-dns-for-vms/fedora-app-vm.yaml[fedora-app-vm.yaml をダウンロード]

[source,bash,role=execute]
----
oc apply -f - <<EOF
apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: fedora-app-vm
  namespace: myapp
  labels:
    app: myapp
spec:
  runStrategy: Always
  dataVolumeTemplates:
    - metadata:
        name: fedora-app-vm-volume
      spec:
        sourceRef:
          kind: DataSource
          name: fedora
          namespace: openshift-virtualization-os-images
        storage:
          resources:
            requests:
              storage: 30Gi
  template:
    metadata:
      labels:
        kubevirt.io/domain: fedora-app-vm
        app: myapp
    spec:
      domain:
        devices:
          disks:
            - disk:
                bus: virtio
              name: rootdisk
            - disk:
                bus: virtio
              name: cloudinitdisk
          interfaces:
            - name: default
              masquerade: {}
        resources:
          requests:
            memory: 2Gi
      networks:
        - name: default
          pod: {}
      volumes:
        - dataVolume:
            name: fedora-app-vm-volume
          name: rootdisk
        - cloudInitNoCloud:
            userData: |-
              #cloud-config
              user: fedora
              password: fedora
              chpasswd: { expire: false }
              ssh_pwauth: true
          name: cloudinitdisk
EOF
----

VM が実行状態になるまで待ちます。

[source,bash]
----
watch 'oc get vm,vmi,dv -n myapp'
----

VM が `Running` かつ `Ready: True` になるまで待ち、完了したら `Ctrl+C` を押します。

=== ステップ 3: VM 用 Service の作成

VM をターゲットにする Headless Service を作成します。

xref:attachment$internal-dns-for-vms/headless-service.yaml[headless-service.yaml をダウンロード]

[source,bash,role=execute]
----
oc apply -f - <<EOF
apiVersion: v1
kind: Service
metadata:
  name: myapp-service
  namespace: myapp
spec:
  clusterIP: None
  selector:
    kubevirt.io/domain: fedora-app-vm
  ports:
    - name: ssh
      protocol: TCP
      port: 22
      targetPort: 22
EOF
----

Service と EndpointSlice を確認します。

[source,bash,role=execute]
----
oc get svc myapp-service -n myapp
oc get endpointslice -n myapp -l kubernetes.io/service-name=myapp-service
----

期待される出力:

Service は `TYPE: ClusterIP` で `CLUSTER-IP: None` (headless service) と表示されるはずです。

EndpointSlice の ENDPOINTS 列には、VM の Pod IP アドレスが表示されるはずです。

=== ステップ 4: DNS 解決と接続性のテスト

DNS 解決と接続性をテストするためにデバッグ用 Pod を作成します。

[source,bash,role=execute]
----
oc apply -f - <<EOF
apiVersion: v1
kind: Pod
metadata:
  name: debug-dns
  namespace: myapp
spec:
  containers:
  - name: debug
    image: registry.access.redhat.com/ubi9/ubi
    command: ["sleep", "3600"]
    securityContext:
      allowPrivilegeEscalation: false
      runAsNonRoot: true
      runAsUser: 1000
      capabilities:
        drop:
        - ALL
      seccompProfile:
        type: RuntimeDefault
  restartPolicy: Never
EOF

# Podの準備ができるまで待機
oc wait --for=condition=Ready pod/debug-dns -n myapp --timeout=60s

# DNS解決をテスト
oc exec -n myapp debug-dns -- getent hosts myapp-service.myapp.svc.cluster.local

# クリーンアップ
oc delete pod debug-dns -n myapp
----

期待される結果:

* DNS 解決によって VM の Pod IP アドレスが返されます (例: `10.128.0.169 myapp-service.myapp.svc.cluster.local`) 

これは、Service の DNS 名が VM の IP アドレスに正しく解決されていることを確認するものです。

== パート 2: 仕組みの理解

=== DNS 解決フロー

Pod または VM が Service を DNS 名でクエリする場合、以下のフローが発生します。

[source,text]
----
┌───────────────────────────────────────────────────────────────┐
│ OpenShift Cluster                                             │
│                                                               │
│  [Client VM/Pod]                                              │
│         │                                                     │
│         │ 1. DNS Query: myapp-service.myapp.svc...            │
│         │                                                     │
│         ↓                                                     │
│  [/etc/resolv.conf]                                           │
│   nameserver 172.30.0.10                                      │
│   search myapp.svc.cluster.local svc.cluster.local            │
│         │                                                     │
│         │ 2. Send query to DNS server                         │
│         ↓                                                     │
│  ┌──────────────┐                                             │
│  │   CoreDNS    │                                             │
│  │ 172.30.0.10  │                                             │
│  └──────┬───────┘                                             │
│         │                                                     │
│         │ 3. Lookup Service record                            │
│         ↓                                                     │
│  ┌──────────────────────────────────────────────┐             │
│  │ Service: myapp-service                       │             │
│  │ Type: Headless                               │             │
│  │ Selector: kubevirt.io/domain=fedora-app-vm   │             │
│  └──────┬───────────────────────────────────────┘             │
│         │                                                     │
│         │ 4. Return VM Pod IP                                 │
│         ↓                                                     │
│  [Client receives: 10.128.2.45]                               │
│         │                                                     │
│         │ 5. Connect to VM                                    │
│         ↓                                                     │
│  ┌──────────────────────┐                                     │
│  │  fedora-app-vm       │                                     │
│  │  IP: 10.128.2.45     │                                     │
│  └──────────────────────┘                                     │
│                                                               │
└───────────────────────────────────────────────────────────────┘
----

=== 解説

**ステップ 1: DNS クエリの開始**

クライアント (他の VM や Pod) が `myapp-service.myapp.svc.cluster.local` に接続する必要があります。クライアントが DNS クエリを開始します。

**ステップ 2: CoreDNS へのクエリ送信**

クライアントは `/etc/resolv.conf` ファイルを読み取り、そこに記載されているクラスター DNS サービス (通常は `172.30.0.10`) に DNS クエリを送信します。

**ステップ 3: CoreDNS による Service レコードの参照**

CoreDNS はクラスター内のすべての Kubernetes Service のデータベースを保持しています。CoreDNS は `myapp` namespace の `myapp-service` という Service を検索します。

**ステップ 4: Service が VM の Pod IP を返却**

Service が Headless (`clusterIP: None`) であるため、CoreDNS は EndpointSlice から VM の Pod の実際の IP アドレスを返します。通常の ClusterIP Service の場合は、代わりに Service の仮想 IP が返されます。

**ステップ 5: 接続の確立**

クライアントは IP アドレスを受け取り、その VM への直接接続を確立します。

=== 主要なポイント

* **DNS には Service が必要**: 仮想マシンは CoreDNS に自動的には登録されません。Kubernetes Service のみが DNS レコードを作成します。
* **VM 名は DNS 名ではない**: VM の `metadata.name` は Kubernetes のリソース識別子であり、DNS 名ではありません。ネットワークアクセスには使用できません。
* **Service 名が DNS 名になる**: Service の `metadata.name` が、`<service-name>.<namespace>.svc.cluster.local` として CoreDNS に登録されます。
* **Headless Service は VM の IP を返す**: Headless Service (`clusterIP: None`) は VM の Pod IP を直接返すため、VM 間での直接通信が可能になります。
* **通常の Service は負荷分散を提供する**: 通常の ClusterIP Service は安定した仮想 IP を提供し、複数の VM 間でトラフィックを分散できます。
* **検索ドメインにより短い名前が使用可能**: `/etc/resolv.conf` の `search` ドメインにより、同じ namespace 内の Service にアクセスする際、完全修飾ドメイン名 (FQDN) の代わりに `myapp-service` のような短い名前を使用できます。

=== 確認コマンド

**Service および EndpointSlice の確認:**

[source,bash,role=execute]
----
# Serviceの詳細表示
oc get svc myapp-service -n myapp

# EndpointSliceの確認 (VMのPod IPが表示されるはずです)
oc get endpointslice -n myapp -l kubernetes.io/service-name=myapp-service

# Serviceの全詳細を表示
oc describe svc myapp-service -n myapp
----

=== 一般的な問題

**問題: DNS 解決で結果が返されない**

**調査:**

[source,bash,role=execute]
----
oc get svc myapp-service -n myapp
oc get endpointslice -n myapp -l kubernetes.io/service-name=myapp-service
----

**一般的な原因:**

* Service のセレクターが VM のラベルと一致していない
* VM が実行されていない (EndpointSlice にエントリがない)
* namespace が間違っている

**解決策:**

1. Service のセレクターが VM の `kubevirt.io/domain` ラベルと完全に一致しているか確認する
2. VM が実行中であることを確認する: `oc get vmi -n myapp`
3. Service と VM の両方が同じ namespace にあることを確認する

**問題: namespace をまたいだ DNS 解決が失敗する**

**調査:**

[source,bash,role=execute]
----
# 別のnamespaceにデバッグ用Podを作成
oc new-project test-namespace 2>/dev/null || true

oc apply -f - <<EOF
apiVersion: v1
kind: Pod
metadata:
  name: debug-cross-ns
  namespace: test-namespace
spec:
  containers:
  - name: debug
    image: registry.access.redhat.com/ubi9/ubi
    command: ["sleep", "300"]
    securityContext:
      allowPrivilegeEscalation: false
      runAsNonRoot: true
      runAsUser: 1000
      capabilities:
        drop:
        - ALL
      seccompProfile:
        type: RuntimeDefault
  restartPolicy: Never
EOF

# 待機してテスト
oc wait --for=condition=Ready pod/debug-cross-ns -n test-namespace --timeout=60s
oc exec -n test-namespace debug-cross-ns -- \
  getent hosts myapp-service.myapp.svc.cluster.local

# クリーンアップ
oc delete pod debug-cross-ns -n test-namespace
----

**一般的な原因:**

* FQDN ではなく短い名前を使用している
* NetworkPolicy によって namespace をまたぐトラフィックがブロックされている

**解決策:**

1. namespace をまたぐ場合は常に FQDN を使用する: `<service>.<namespace>.svc.cluster.local`
2. 制限的な NetworkPolicy が設定されていないか確認する

== まとめ

本チュートリアルでは、以下の内容を学習しました。

* DNS ベースの探索のために、Headless Kubernetes Service を通じて VM を公開する方法
* クラスター内で CoreDNS が Service 名を VM の Pod IP アドレスに解決する方法
* Headless Service (直接 VM IP) と ClusterIP Service (負荷分散付きの仮想 IP) の違い
* FQDN 形式の `getent hosts` を使用してデバッグ用 Pod から DNS 解決をテストする方法
* DNS に Service が必要な理由や、検索ドメインにより短い名前の解決が可能になる仕組みなどの重要な概念
