= Linux 仮想マシンへのリモートアクセス
:navtitle: Linux 仮想マシンへのリモートアクセス

== 概要

本チュートリアルでは、OpenShift Virtualization で実行されている Linux 仮想マシンにアクセスするためのさまざまな手法を解説します。各手法は、迅速なトラブルシューティングから本番環境グレードのアクセスパターンまで、それぞれのユースケースに適しています。

== アクセス手法とユースケース

[cols="1,2,1"]
|===
|手法 |ユースケース |SSH 鍵の必要性

|コンソール
|初期設定、トラブルシューティング
|不要

|VNC
|GUI アクセス
|不要

|virtctl SSH
|迅速な管理者アクセス
|必要

|NodePort Service
|外部アクセス
|必要

|ポート転送
|開発、テスト
|必要

|セカンダリーネットワーク
|従来のインフラストラクチャ
|必要
|===

== 前提条件

* OpenShift Virtualization Operator がインストールされた OpenShift 4.18 以降
* CLI ツール: `oc`、`virtctl`、`kubectl`
* 実行中の Linux VM が少なくとも 1 台あること (本チュートリアルで作成します) 
* SSH およびネットワークに関する基本的な知識

== セットアップ: テスト用 VM のデプロイ

namespace を作成し、Fedora VM をデプロイします。

[source,bash,role=execute]
----
oc create namespace vm-access-demo
----

SSH を有効にして VM を作成します。

WARNING: この例の cloud-init パスワードはデモ目的でのみ使用しています。本番環境では、常に強力で一意のパスワードを使用するか、SSH 公開鍵認証を使用してください。

xref:attachment$remote-access-linux-vms/fedora-access-vm.yaml[fedora-access-vm.yaml をダウンロード]

[source,yaml]
----
apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: fedora-access-vm
  namespace: vm-access-demo
spec:
  dataVolumeTemplates:
    - apiVersion: cdi.kubevirt.io/v1beta1
      kind: DataVolume
      metadata:
        name: fedora-access-vm-disk
      spec:
        sourceRef:
          kind: DataSource
          name: fedora
          namespace: openshift-virtualization-os-images
        storage:
          resources:
            requests:
              storage: 30Gi
  runStrategy: RerunOnFailure
  template:
    metadata:
      labels:
        kubevirt.io/domain: fedora-access-vm
    spec:
      domain:
        cpu:
          cores: 2
        devices:
          disks:
            - disk:
                bus: virtio
              name: rootdisk
            - disk:
                bus: virtio
              name: cloudinitdisk
          interfaces:
            - masquerade: {}
              name: default
          rng: {}
        machine:
          type: pc-q35-rhel9.4.0
        memory:
          guest: 4Gi
      networks:
        - name: default
          pod: {}
      volumes:
        - dataVolume:
            name: fedora-access-vm-disk
          name: rootdisk
        - cloudInitNoCloud:
            userData: |-
              #cloud-config
              user: fedora
              password: fedora123
              chpasswd: { expire: false }
              ssh_pwauth: true
              ssh_authorized_keys:
                - ssh-rsa AAAAB3NzaC1yc2EAAAADAQABAAABAQC... your-public-key-here
          name: cloudinitdisk
----

Note: `your-public-key-here` は実際の SSH 公開鍵に置き換えるか、テスト用にパスワード認証を使用してください。

VM をデプロイします。

[source,bash,role=execute]
----
oc apply -f fedora-access-vm.yaml
----

VM が準備完了になるまで待機します。

[source,bash,role=execute]
----
oc get vmi -n vm-access-demo
----

== 手法 1: virtctl によるコンソールアクセス

最も基本的なアクセス手法であり、VM への直接的なコンソールアクセスを提供します。

=== コンソールへのアクセス

[source,bash,role=execute]
----
virtctl console fedora-access-vm -n vm-access-demo
----

=== コンソールの終了

`Ctrl+]` を押して終了します。

=== 使用すべきケース

* VM の初期設定および構成
* ネットワーク接続がない場合のトラブルシューティング
* VM が SSH に応答しない場合
* ネットワークが切断された際の緊急アクセス

=== 制限事項

* コピー/ペースト機能がない (限定的) 
* スクロールバック不可
* テキストベースのインターフェースのみ
* 一度に 1 つのセッションのみ

== 手法 2: VNC アクセス

グラフィカルデスクトップ環境を持つ VM 用です。

=== VNC セッションの開始

[source,bash,role=execute]
----
virtctl vnc fedora-access-vm -n vm-access-demo
----

これにより、VM のディスプレイに接続する VNC ビューアが起動します。

=== 使用すべきケース

* デスクトップ Linux VM へのアクセス
* GUI アプリケーションの実行
* GUI を必要とするソフトウェアのインストール
* 表示関連の問題のトラブルシューティング

=== 前提条件

* ローカルに VNC ビューアがインストールされていること
* デスクトップ環境 (GNOME、KDE など) がインストールされた VM

== 手法 3: virtctl による SSH アクセス

`virtctl` コマンドを使用した迅速な SSH アクセスです。この手法は、内部的にポート転送を使用して VM の SSH ポートに接続します。

=== 前提条件

* VM に SSH 鍵が構成されていること (cloud-init 経由) 
* VM で SSH サービスが実行されていること

=== SSH 経由での接続

[source,bash,role=execute]
----
virtctl ssh fedora@fedora-access-vm -n vm-access-demo
----

=== ホスト鍵チェックのスキップ (テスト用) 

[source,bash,role=execute]
----
virtctl ssh fedora@fedora-access-vm -n vm-access-demo --local-ssh-opts="-o StrictHostKeyChecking=no"
----

=== 使用すべきケース

* 迅速な管理者アクセス
* 開発およびテスト
* 一時的なアクセスのニーズ
* `oc` や `kubectl` を通じてクラスターへのアクセス権がある場合

=== 制限事項

* クラスターへのアクセスが必要
* ポート転送を使用するため、わずかなレイテンシが発生する場合がある

== 手法 4: NodePort Service による直接 SSH 接続

NodePort Service を使用して SSH ポートを外部に公開します。

=== NodePort Service の作成

xref:attachment$remote-access-linux-vms/ssh-nodeport-service.yaml[ssh-nodeport-service.yaml をダウンロード]

[source,yaml]
----
apiVersion: v1
kind: Service
metadata:
  name: fedora-ssh-nodeport
  namespace: vm-access-demo
spec:
  type: NodePort
  selector:
    kubevirt.io/domain: fedora-access-vm
  ports:
    - protocol: TCP
      port: 22
      targetPort: 22
      nodePort: 30022
----

Service を適用します。

[source,bash,role=execute]
----
oc apply -f fedora-ssh-nodeport.yaml
----

=== Service の確認

[source,bash,role=execute]
----
oc get svc fedora-ssh-nodeport -n vm-access-demo
----

=== SSH 経由での接続

クラスターノードの IP を取得します。

[source,bash,role=execute]
----
oc get nodes -o wide
----

NodePort を使用して接続します。

[source,bash,role=execute]
----
ssh fedora@<node-ip> -p 30022
----

=== 使用すべきケース

* 外部アクセスが必要な場合
* ロードバランサーがないシンプルなデプロイメント
* 開発/テストクラスター
* 迅速な外部アクセス設定

=== セキュリティ上の考慮事項

* すべてのクラスターノードの SSH ポートを公開する
* 強力な認証を使用すること (SSH 鍵のみを推奨) 
* ファイアウォールルールを検討すること
* 本番環境には推奨されない
* 不正なアクセス試行を監視すること

== 手法 5: ポート転送による SSH アクセス

`kubectl` または `oc port-forward` を使用した一時的な SSH アクセスです。

=== VM Pod の検索

[source,bash,role=execute]
----
oc get pods -n vm-access-demo
----

出力:

[source,text]
----
NAME                                   READY   STATUS    RESTARTS   AGE
virt-launcher-fedora-access-vm-xxxxx   2/2     Running   0          10m
----

=== SSH ポートの転送

[source,bash,role=execute]
----
oc port-forward -n vm-access-demo virt-launcher-fedora-access-vm-xxxxx 2222:22
----

=== SSH 経由での接続 (別のターミナルで) 

[source,bash,role=execute]
----
ssh fedora@localhost -p 2222
----

=== 使用すべきケース

* 迅速な一時的アクセス
* 開発およびテスト
* 特定の VM のトラブルシューティング
* NodePort やロードバランサーが利用できない場合

=== 制限事項

* ポート転送を維持し続ける必要がある
* 一度に 1 つの接続のみ
* 本番環境には適さない
* アクティブなターミナルセッションが必要

== 手法 6: セカンダリーネットワーク経由の直接ネットワークアクセス

bridge ネットワークや localnet ネットワーク上の VM に対して、IP 経由で直接アクセスします。

=== 前提条件

* VM がセカンダリーネットワーク (bridge、localnet、VLAN) に接続されていること
* 現在の場所からネットワークに到達可能であること
* 固定 IP が構成されているか、予約済みアドレスを持つ DHCP が利用可能であること

=== セカンダリーネットワークを持つ VM

xref:attachment$remote-access-linux-vms/fedora-vlan-access-vm.yaml[fedora-vlan-access-vm.yaml をダウンロード]

[source,yaml]
----
apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: fedora-vlan-vm
  namespace: vm-access-demo
spec:
  dataVolumeTemplates:
    - apiVersion: cdi.kubevirt.io/v1beta1
      kind: DataVolume
      metadata:
        name: fedora-vlan-vm-disk
      spec:
        sourceRef:
          kind: DataSource
          name: fedora
          namespace: openshift-virtualization-os-images
        storage:
          resources:
            requests:
              storage: 30Gi
  runStrategy: RerunOnFailure
  template:
    metadata:
      labels:
        kubevirt.io/domain: fedora-vlan-vm
    spec:
      domain:
        cpu:
          cores: 2
        devices:
          disks:
            - disk:
                bus: virtio
              name: rootdisk
            - disk:
                bus: virtio
              name: cloudinitdisk
          interfaces:
            - masquerade: {}
              name: default
            - bridge: {}
              name: vlan-network
          rng: {}
        machine:
          type: pc-q35-rhel9.4.0
        memory:
          guest: 4Gi
      networks:
        - name: default
          pod: {}
        - name: vlan-network
          multus:
            networkName: localnet-vlan-100
      volumes:
        - dataVolume:
            name: fedora-vlan-vm-disk
          name: rootdisk
        - cloudInitNoCloud:
            userData: |-
              #cloud-config
              user: fedora
              password: fedora123
              chpasswd: { expire: false }
              ssh_pwauth: true
              ssh_authorized_keys:
                - ssh-rsa AAAAB3NzaC1yc2EAAAADAQABAAABAQC... your-public-key-here
            networkData: |-
              version: 2
              ethernets:
                enp1s0:
                  dhcp4: true
                enp2s0:
                  dhcp4: false
                  dhcp6: false
                  addresses:
                    - 192.168.100.100/24
          name: cloudinitdisk
----

=== SSH 経由での接続

[source,bash,role=execute]
----
ssh fedora@192.168.100.100
----

=== 使用すべきケース

* 本番環境
* 従来のインフラストラクチャパターン
* 持続的で予測可能なアクセスが必要な VM
* 既存ネットワークとの統合
* 同じネットワークセグメント上の複数の VM

=== 利点

* ネイティブなネットワークアクセス
* ポート転送のオーバーヘッドがない
* 複数の同時接続が可能
* 標準的なネットワークツールが動作する
* 従来のアーキテクチャに適合する

== SSH 鍵の構成

=== SSH 鍵の生成 (必要な場合) 

[source,bash,role=execute]
----
ssh-keygen -t rsa -b 4096 -f ~/.ssh/ocp-virt-key
----

=== cloud-init への鍵の追加

VM の `userData` セクションに含めます。

[source,yaml]
----
ssh_authorized_keys:
  - ssh-rsa AAAAB3NzaC... your-key-here
----

=== パスワード認証の無効化

本番環境では、パスワード認証と root ログインを無効にします。cloud-init 構成の `userData` セクションに以下の設定を追加します。

[source,yaml]
----
volumes:
  - cloudInitNoCloud:
      userData: |-
        #cloud-config
        user: fedora
        ssh_pwauth: false
        disable_root: true
        ssh_authorized_keys:
          - ssh-rsa AAAAB3NzaC... your-key-here
    name: cloudinitdisk
----

この構成の効果:

* `ssh_pwauth: false` - SSH のパスワード認証を無効化
* `disable_root: true` - SSH 経由の root ログインを防止
* SSH 鍵認証のみを必須とする

== 検証コマンド

=== VM ステータスの確認

[source,bash,role=execute]
----
# VirtualMachine
oc get vm -n vm-access-demo

# VirtualMachineInstance
oc get vmi -n vm-access-demo

# VMの詳細情報
oc describe vmi fedora-access-vm -n vm-access-demo
----

=== VM 内の SSH サービスの確認

コンソール経由:

[source,bash,role=execute]
----
virtctl console fedora-access-vm -n vm-access-demo
----

VM 内部にて:

[source,bash]
----
# SSHサービスの確認
sudo systemctl status sshd

# SSHがリッスンしているか確認
sudo ss -tlnp | grep :22

# ファイアウォールの確認
sudo firewall-cmd --list-all
----

=== ネットワーク接続のテスト

[source,bash]
----
# VM内部から
ping -c 3 8.8.8.8

# 外部から (同じネットワーク上にある場合) 
ping -c 3 192.168.100.100
----

== よくある問題と解決策

すべてのアクセス手法のトラブルシューティングについては、xref:remote-access-linux-troubleshooting.adoc[] を参照してください。

=== 問題: virtctl コンソールにログインプロンプトが表示されない

**原因**: VM が完全に起動していないか、表示の問題。

**解決策**: 少し待機し、VM ステータスを確認して VM が実行中であることを検証します。

=== 問題: SSH 接続が拒否される

**原因**: SSH サービスが実行されていないか、ファイアウォールでブロックされている。

**解決策**:

* sshd ステータスの確認: `sudo systemctl status sshd`
* 必要に応じて起動: `sudo systemctl start sshd`
* ファイアウォールの確認: `sudo firewall-cmd --list-services`

=== 問題: virtctl ssh 接続が失敗する

**原因**: SSH サービスが実行されていないか、認証失敗。

**解決策**: 

* VM 内で SSH サービスが実行されていることを確認
* SSH 鍵が適切に構成されていることを確認
* VM にネットワーク接続があることを確認
* ポート転送を使用してクラスター内から SSH をテスト

=== 問題: NodePort にアクセスできない

**原因**: クラスターノードのファイアウォールがポートをブロックしている。

**解決策**: ノードのファイアウォールルールを確認し、NodePort 範囲が開放されていることを確認します。

=== 問題: セカンダリーネットワークの IP に接続できない

**原因**: ネットワークに到達できないか、ルーティングの問題。

**解決策**: ネットワーク構成を検証し、ルートを確認し、VLAN/ブリッジが適切に構成されていることを確認します。

== セキュリティのベストプラクティス

=== 認証

* SSH 鍵のみを使用し、パスワード認証を無効化する
* 定期的に SSH 鍵をローテーションする
* 環境ごとに異なる鍵を使用する
* 鍵管理ポリシーを実装する

=== ネットワークセキュリティ

* 可能であれば、NodePort の公開を特定の IP に制限する
* NetworkPolicy を使用して VM へのアクセスを制限する
* VM のファイアウォールを適切に構成する
* 定期的にアクセスログを監視する

=== アクセス制御

* virtctl アクセスに RBAC を実装する
* 環境ごとに分離した namespace を使用する
* 誰がどの VM にアクセスできるかを文書化する
* 定期的なアクセス監査を実施する

== 適切なアクセス方法の選択

以下の図は、要件に基づいて適切なアクセス方法を選択するためのガイドです。

image::remote-access-decision.png[Remote Access Decision Diagram, align=center]

各判断ポイントでは、ネットワークアクセスの必要性、アクセスが一時的なものかどうか、利用可能なインフラストラクチャーに基づいて選択肢を絞り込みます。以下の表は、一般的なロールとシナリオを推奨される方法に対応付けています。

[cols="1,1,2",options="header"]
|===
|シナリオ |推奨される方法 |理由

|起動しない VM をデバッグする開発者
|コンソール (`virtctl console`)
|ネットワーク接続なしで動作します。SSH が破損している場合や、VM にネットワークがない場合の唯一の選択肢です。

|VM 上でアプリケーションをテストする開発者
|ポートフォワード (`virtctl port-forward` または `oc port-forward`)
|Service を作成しない一時的なアクセスです。ターミナルセッションが終了すると停止します。

|運用担当者/SRE による通常の管理者アクセス
|virtctl SSH (`virtctl ssh`)
|クラスター認証情報を持つユーザーにとって最もシンプルな認証アクセスです。API サーバー経由で監査ログが記録されます。

|VM にデプロイする CI/CD パイプライン
|サービスアカウントを使用した virtctl SSH
|クラスター認証情報を使用した自動 SSH アクセス。外部エンドポイントは不要です。

|外部モニタリングツール (Nagios、Zabbix、Prometheus)
|NodePort または LoadBalancer Service
|VM の再起動後も維持される安定した外部エンドポイント。利用可能な場合は MetalLB を備えた LoadBalancer を使用します。

|既存の企業ネットワークと統合された VM
|セカンダリーネットワーク (直接 SSH)
|NAT やポートフォワードを行わずに企業ネットワークから直接 L2/L3 アクセスが可能です。標準の SSH ツールが使用できます。
|===

NOTE: ニーズを満たす最もシンプルな方法から始めてください。ほとんどのユーザーは、トラブルシューティングには `virtctl console`、通常のアクセスには `virtctl ssh` のみが必要です。NodePort/LoadBalancer は、外部システムがクラスター認証情報なしで VM に到達する必要がある場合にのみ使用してください。

== クリーンアップ

本チュートリアルで作成したすべてのリソースを削除します。

[source,bash,role=execute]
----
# VMの削除
oc delete vm fedora-access-vm fedora-vlan-vm -n vm-access-demo

# サービスの削除
oc delete svc fedora-ssh-nodeport -n vm-access-demo

# namespaceの削除
oc delete namespace vm-access-demo
----
