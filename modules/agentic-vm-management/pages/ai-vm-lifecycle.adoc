= AI を活用した VM ライフサイクル操作
:navtitle: AI VM ライフサイクル操作

このチュートリアルでは、`vm-lifecycle-manager` および `vm-delete` エージェントスキルを通じて自然言語コマンドを使用し、OpenShift VirtualMachines のライフサイクルを管理する方法を説明します。人間による安全確認 (Human-in-the-loop) を行いながら VM の起動、停止、再起動、削除を行う方法や、エージェントが保護された VM や実行中の VM の削除などのエッジケースをどのように処理するかを学びます。

== 前提条件

* xref:getting-started.adoc[AI エージェントによる VM 管理の開始] チュートリアルを完了していること (スキルパックのインストール、MCP サーバーの設定、クラスター接続の確認が完了していること)
* OpenShift Virtualization がインストールされた OpenShift クラスター
* `KUBECONFIG` 環境変数が設定され、有効な kubeconfig ファイルを参照していること
* 管理対象の VM が少なくとも 1 つ(作成方法については xref:natural-language-vm-create.adoc[自然言語による仮想マシンの作成] を参照)

本チュートリアルで使用する namespace がまだ存在しない場合は作成します。

[source,bash,role=execute]
----
oc create namespace my-vms
----

管理対象の VM がない場合は、IDE チャットに次のように入力して `vm-create` スキルを使用して作成します。

----
Create a Fedora VM named lifecycle-demo in namespace my-vms
----

続行する前に、VM が存在することを確認します。

[source,bash,role=execute]
----
oc get vm -n my-vms
----

出力例:

----
NAME             AGE   STATUS    READY
lifecycle-demo   2m    Running   True
----

== 仕組み

=== vm-lifecycle-manager スキル

`vm-lifecycle-manager` スキルは、start、stop、restart 操作に対して 3 段階のワークフローに従います。

. **パラメーターの収集と確認** - エージェントは、プロンプトから VM 名、namespace、アクションを収集します。操作とその影響 (start の場合はリソース消費、stop の場合はサービス中断、restart の場合は一時的なダウンタイム) を提示し、続行する前に明示的な確認を待ちます。
. **操作の実行** - 確認後、エージェントは `vm_lifecycle` MCP ツールを呼び出して VM の RunStrategy を変更します。restart の場合、エージェントはコンポジットパターンを使用します。VM を停止し、停止したことを確認し、少し待ってから再度起動します。この 2 段階のアプローチにより、Kubernetes の resourceVersion の競合を回避します。
. **レポートと検証** - エージェントは結果を報告し、新しい RunStrategy を確認し、VM ステータスの確認や namespace 内の VM の一覧表示などの次のステップを提案します。

=== vm-delete スキル

`vm-delete` スキルは、5 段階のワークフローを通じて厳格な安全プロトコルを適用します。

. **検証** - エージェントは VM が存在することを確認し、`protected: "true"` ラベル (削除を完全にブロックする) をチェックし、VM が実行中かどうかを確認します。
. **ストレージの検出** - エージェントは、削除範囲の全容を示すために、VM に関連付けられている DataVolume および PVC を一覧表示します。
. **オプションの提示** - エージェントは削除範囲を表示し、VM のみ削除 (ストレージを保持)、VM とストレージを削除 (テスト/開発環境に推奨)、またはキャンセルの 3 つのオプションを提示します。
. **入力による確認** - 削除を確認するには、正確な VM 名を入力する必要があります。一致しない場合、操作はキャンセルされます。
. **実行とレポート** - エージェントは VM と (必要に応じて) そのストレージを削除し、削除された内容と解放されたストレージ容量をレポートします。

== サンプルシナリオ 1: 停止している VM の起動

この例では、`vm-lifecycle-manager` スキルを使用して停止している VM を起動します。

. IDE チャットで、以下を入力します。
+
----
Start VM lifecycle-demo in namespace my-vms
----
. エージェントは確認のために操作を表示します。
+
----
## VM Lifecycle Operation

| Parameter | Value            | Impact                   |
|-----------|------------------|--------------------------|
| VM Name   | `lifecycle-demo` | from user                |
| Namespace | `my-vms`         | from user                |
| Action    | `start`          | consumes resources       |

Confirm: yes/no
----
. 影響を確認し、承認します。
+
----
yes
----
. エージェントは `vm_lifecycle` を呼び出して RunStrategy を `Halted` から `Always` に変更し、VM が Running ステータスに達したことを確認します。
+
----
## VM Start Successful

**VM**: `lifecycle-demo` | **Namespace**: `my-vms` | **RunStrategy**: Always

**Impact**: Running, consuming resources (CPU/memory).
Access: virtctl console or SSH.
RunStrategy: Always (auto-restart on crash)

**Next**: "Show status of VM lifecycle-demo" or "List VMs in namespace my-vms"
----

以下のコマンドを使用して、VM が実行中であることを確認できます。

[source,bash,role=execute]
----
oc get vm lifecycle-demo -n my-vms
----

----
NAME             AGE   STATUS    READY
lifecycle-demo   10m   Running   True
----

== 例示シナリオ 2: 実行中の VM の停止

この例では、実行中の VM を正常に停止します。

. IDE チャットで次のように入力します。
+
----
Stop VM lifecycle-demo in namespace my-vms
----
. エージェントは停止操作とその影響を表示します。
+
----
## VM Lifecycle Operation

| Parameter | Value            | Impact             |
|-----------|------------------|--------------------|
| VM Name   | `lifecycle-demo` | from user          |
| Namespace | `my-vms`         | from user          |
| Action    | `stop`           | graceful shutdown  |

Confirm: yes/no
----
. 確認後、エージェントは正常なシャットダウンを実行し、RunStrategy を `Halted` に遷移させます。
+
----
## VM Stop Successful

**VM**: `lifecycle-demo` | **Namespace**: `my-vms` | **RunStrategy**: Halted

**Impact**: Stopped, resources freed. State preserved.
Start: "Start VM lifecycle-demo in namespace my-vms"
RunStrategy: Halted (stays off)

**Next**: "Show status of VM lifecycle-demo" or "List VMs in namespace my-vms"
----

VM が停止すると、VirtualMachineInstance (VMI) オブジェクトは削除されます。VirtualMachine リソースとそのストレージ (DataVolume、PVC) はそのまま保持されます。VM が `Halted` 状態の間は、コンピュートリソース (CPU、メモリ) は消費されません。

== 例示シナリオ 3: VM の再起動

再起動操作では、Kubernetes API の競合を回避するために、停止してから開始する複合パターンを使用します。

. IDE チャットで、以下を入力します。
+
----
Restart VM lifecycle-demo in namespace my-vms
----
. エージェントは一時的な中断について警告します。
+
----
## VM Lifecycle Operation

| Parameter | Value            | Impact                       |
|-----------|------------------|------------------------------|
| VM Name   | `lifecycle-demo` | from user                    |
| Namespace | `my-vms`         | from user                    |
| Action    | `restart`        | brief interruption ~1-2min   |

Confirm: yes/no
----
. 確認後、エージェントは複合再起動を実行します。
+
----
## VM Restart Successful

**VM**: `lifecycle-demo` | **Namespace**: `my-vms` | **RunStrategy**: Always

Composite restart steps completed:
1. Stopped VM -> verified status: Stopped
2. Started VM -> verified status: Running

**Impact**: Running after stop+start. Brief interruption (~1-2min).
Monitor app logs for any issues.

**Next**: "Show status of VM lifecycle-demo" or "List VMs in namespace my-vms"
----

複合再起動により、新しい Pod、新しい IP アドレス、新しい MAC アドレスを持つ新しい VirtualMachineInstance が生成されます。アプリケーションが安定したネットワーク ID に依存している場合は、Kubernetes Service を使用して基盤となる VMI を抽象化してください。

== サンプルシナリオ 4: ストレージのクリーンアップを伴う VM の削除

この例では、`vm-delete` スキルを使用して VM とその関連ストレージを削除します。

. IDE チャットに次のように入力します。
+
----
Delete VM lifecycle-demo in namespace my-vms
----
. エージェントは VM を検証し、関連するストレージを検出して、削除範囲を表示します。
+
----
## VM Deletion - Review Scope

**VM**: `lifecycle-demo` | **Namespace**: `my-vms` | **Status**: Running

**Resources**: VM `lifecycle-demo` (Age: 10m, vCPU: 1, Memory: 4Gi)
**Storage**: DataVolume `lifecycle-demo-rootdisk` (30Gi),
             PVC `lifecycle-demo-rootdisk` (30Gi) - Total: 30Gi

### Deletion Options
**1: VM Only** - Preserves storage for reuse
**2: VM + Storage** <- Recommended (test/dev) - Frees storage
**3: Cancel**

Select (1, 2, or 3):
----
. すべてのリソースを解放するためにオプション 2 を選択します。
+
----
2
----
. エージェントは確認のために、VM 名を正確に入力することを要求します。
+
----
## PERMANENT DELETION - Typed Confirmation Required

**CANNOT BE UNDONE**

**Will delete**:
- VirtualMachine: `lifecycle-demo` (namespace: `my-vms`)
- DataVolume: `lifecycle-demo-rootdisk`
- PVC: `lifecycle-demo-rootdisk`
- All data lost

Type `lifecycle-demo` to confirm: _____
----
. 正確な名前を入力します。
+
----
lifecycle-demo
----
. エージェントは実行中の VM を停止し、VM とそのストレージを削除して、結果を報告します。
+
----
## VM Deleted (Complete Cleanup)

**Deleted**: VM + DataVolume + PVC | **Freed**: 30Gi
**Impact**: Permanent removal. Cannot recover.
**Verify**: "List VMs in namespace my-vms" - VM should not appear
----

VM およびそのストレージが削除されていることを確認できます。

[source,bash,role=execute]
----
oc get vm -n my-vms
----

----
No resources found in my-vms namespace.
----

[source,bash,role=execute]
----
oc get pvc -n my-vms
----

----
No resources found in my-vms namespace.
----

== 例 5: 保護された VM の削除拒否

`protected: "true"` ラベルが設定されている VM は、確認の有無にかかわらず削除できません。これにより、重要な本番環境の VM が誤って削除されるのを防ぎます。

VM に保護ラベルを追加するには、次を実行します。

[source,bash,role=execute]
----
oc label vm <vm-name> -n <namespace> protected=true
----

ラベルが設定されていることを確認します。

[source,bash,role=execute]
----
oc get vm <vm-name> -n <namespace> --show-labels
----

保護された VM を削除しようとすると、次のようになります。

. IDE チャットで、次のように入力します。
+
----
Delete VM production-db in namespace production
----
. エージェントは保護ラベルを検出し、操作を拒否します。
+
----
Cannot Delete Protected VM

VM `production-db` has label `protected: "true"` - deletion blocked.

To remove the protection label (requires admin approval):
  oc label vm production-db -n production protected-

Operation cancelled.
----

エージェントは確認ステップに進みません。削除できるようにするには、事前に保護ラベルを手動で削除する必要があります。

== RunStrategy について

エージェントは、非推奨となった `running` フィールドに代わる VirtualMachine リソースの `runStrategy` フィールドを使用して、VM の電源状態を管理します。

[cols="1,1,3",options="header"]
|===
| アクション | RunStrategy | 動作
| start | `Always` | VM が実行され、クラッシュまたはノード障害時に自動的に再起動します
| stop | `Halted` | VM が停止し、明示的に起動されるまで停止状態を維持します
| restart | `Always` | VM が停止し、停止したことを確認した上で、自動再起動が有効な状態で起動します
|===

`Always` ストラテジーは、現在の VMI が何らかの理由 (ゲストのシャットダウン、ノードのドレイン、OOM キル) で終了した場合に、プラットフォームが新しい VMI を作成することを意味します。`Halted` ストラテジーは、VMI が作成されないことを意味します。エージェントは非推奨の `running` フィールドを設定することはなく、すべての電源状態遷移に `runStrategy` のみを使用します。

NOTE: KubeVirt は、`RerunOnFailure` (ゼロ以外の終了コードの場合のみ再起動) および `Manual` (自動アクションなし) ストラテジーもサポートしています。`vm-lifecycle-manager` スキルでは、これら 2 つの状態が最も一般的な電源管理シナリオをカバーしているため、`Always` と `Halted` を使用します。

VM の現在の RunStrategy を確認できます。

[source,bash,role=execute]
----
oc get vm lifecycle-demo -n my-vms -o jsonpath='{.spec.runStrategy}'
----

== Human-in-the-Loop による確認

どちらのスキルも、状態を変更する前に明示的なユーザー確認を必要とする安全モデルを適用します。

**ライフサイクル操作** (`vm-lifecycle-manager`):

* エージェントは、処理を続行する前に、VM 名、namespace、およびアクションとその影響を提示します。
* 操作が実行される前に、"yes" と明示的に確認する必要があります。
* 「no」と回答するか再検討した場合、操作はキャンセルされ、VM は変更されません。
* 一括操作 (複数の VM) では、VM ごとに個別の確認が必要です。

**削除操作** (`vm-delete`):

* エージェントは VM を検証し、関連するすべてのリソースを検出して、削除範囲の全容を表示します。
* VM のみの削除、VM とストレージの削除、またはキャンセルのいずれかを選択します。
* 確認するには、VM 名を正確に (大文字と小文字を区別して) 入力する必要があります。
* 不一致の場合は、操作が直ちにキャンセルされます。
* 保護された VM (ラベル `protected: "true"`) は、確認ステップの前に拒否されます。

このセーフティモデルにより、偶発的なサービス中断、リソース消費、恒久的なデータ損失を防ぎます。

== クリーンアップ

このチュートリアルで作成されたリソースを削除するには:

[source,bash,role=execute]
----
oc delete vm lifecycle-demo -n my-vms
----

または、自然言語を使用することもできます。IDE チャットに「Delete VM lifecycle-demo in namespace my-vms」と入力します。`vm-delete` スキルが、完全な安全性ワークフローを使用して削除を処理します。

namespace を削除するには:

[source,bash,role=execute]
----
oc delete namespace my-vms
----

== まとめ

* `vm-lifecycle-manager` スキルは、`runStrategy` フィールドを `Always` (実行中) と `Halted` (停止) の間で遷移させることで、VM の電源状態を管理します。
* VM を停止するとグレースフルシャットダウンが実行され、ストレージと VM の状態を保持しながらコンピュートリソースが解放されます。
* VM を起動すると RunStrategy が `Always` に設定され、クラッシュ時やノード障害時の自動再起動機能が提供されます。
* 再起動では、Kubernetes の `resourceVersion` の競合を回避するために stop-verify-start (停止・検証・開始) の複合パターンを使用します。再起動により、新しい Pod とネットワーク ID を持つ新しい VMI が生成されます。
* `vm-delete` スキルは、検証、スコープの確認、オプションの選択、名前入力による確認という複数ステップの安全策を適用します。
* 保護ラベル (`protected: "true"`) は確認ステップの前に削除をブロックするため、手動で削除する必要があります。
* 削除は 2 つのモードをサポートしています: VM のみ (再アタッチ用にストレージを保持) と VM + ストレージ (完全なクリーンアップ)。
* どちらのスキルも読み取り専用の安全性を備えており、明示的に確認するまで変更は行われません。
