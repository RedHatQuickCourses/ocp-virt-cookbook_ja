= ライブマイグレーションとクラスターのリバランス
:navtitle: VM のリバランスとライブマイグレーション

このチュートリアルでは、`vm-rebalance` エージェントスキルを通じて自然言語コマンドを使用し、クラスターノード間で仮想マシンを移行する方法を説明します。手動 (ユーザー主導) および自動 (AI 主導) で VM をリバランスする方法を学び、ライブマイグレーションとコールドマイグレーションの違いを理解し、メンテナンスのためのノードのドレインやクラスターの負荷分散の最適化などの一般的なシナリオを実践します。

== 前提条件

* xref:getting-started.adoc[Agentic VM 管理の開始] チュートリアルを完了していること (スキルパックのインストール、MCP サーバーの設定、クラスター接続の確認が完了していること)
* OpenShift Virtualization がインストールされた OpenShift クラスター
* `KUBECONFIG` 環境変数が設定され、有効な kubeconfig ファイルを指していること
* スケジューリング可能な Worker Node が少なくとも 2 つあるマルチノードクラスター
* 複数のノードに分散して実行されている少なくとも 2 つの VM (作成方法については xref:natural-language-vm-create.adoc[自然言語による仮想マシンの作成] を参照)
* ハードウェア仮想化 (KVM) をサポートする Worker Node、またはベアメタル以外の環境では HyperConverged CR でソフトウェアエミュレーションが有効になっていること
* ライブマイグレーションの場合: `ReadWriteMany` (RWX) アクセスモードをサポートする StorageClass (例: Ceph RBD、ODF、CephFS)。`ReadWriteOnce` (RWO) ストレージはコールドマイグレーションのみをサポートします
* ノード間のコールドマイグレーションの場合: Worker Node が同じ永続ストレージへのアクセスを共有している必要があります。ゾーンバインドストレージまたはノードローカルストレージでは、コールドマイグレーションが同じゾーン内のノードに制限されます

このチュートリアルで使用する namespace が存在しない場合は、作成します。

[source,bash,role=execute]
----
oc create namespace my-vms
----

使用する VM がない場合は、IDE チャットで次のように入力し、`vm-create` スキルを使用して作成します。

----
Create a Fedora VM named web-01 in namespace my-vms
----

----
Create a Fedora VM named web-02 in namespace my-vms
----

----
Create a Fedora VM named db-01 in namespace my-vms
----

続行する前に、VM が存在し実行中であることを確認します。

[source,bash,role=execute]
----
oc get vm -n my-vms
----

出力例:

----
NAME   AGE  STATUS  READY
db-01  3m  Running  True
web-01  5m  Running  True
web-02  4m  Running  True
----

VM が現在どのノードにスケジュールされているかを確認します。

[source,bash,role=execute]
----
oc get vmi -n my-vms -o custom-columns="NAME:.metadata.name,NODE:.status.nodeName,PHASE:.status.phase"
----

想定される出力:

----
NAME   NODE    PHASE
db-01  worker-02  Running
web-01  worker-01  Running
web-02  worker-01  Running
----

== 動作の仕組み

`vm-rebalance` スキルは、手動と自動の 2 つの動作モードをサポートしています。どちらのモードも、前提条件を検証し、移行計画を提示し、VM を移動する前に明示的な確認を待つという安全第一のワークフローに従います。

=== 手動リバランス

手動モードでは、移動する VM とその移動先を指定します。エージェントは 4 つのステップからなるワークフローに従います:

. **ソースとターゲットの検証** -- エージェントは VM が存在し稼働していることを確認し、ターゲットノードがスケジュール可能であること (cordon や taint が設定されていないこと) をチェックし、ターゲットノードに十分な CPU、メモリ、ストレージリソースがあることを確認します。
. **ストレージ互換性の確認** -- エージェントは VM のストレージ設定を検査し、ライブマイグレーションが可能かどうかを判断します。ReadWriteMany (RWX) ストレージを使用する VM はライブマイグレーションをサポートします。ReadWriteOnce (RWO) ストレージを使用する VM はコールドマイグレーション (停止、ストレージの移行、起動) が必要です。
. **マイグレーション計画の提示** -- エージェントはマイグレーションタイプ (ライブまたはコールド)、ソースノードおよびターゲットノード、予想される影響、推定所要時間を表示します。明示的な確認を待ちます。
. **実行と監視** -- 確認後、エージェントはマイグレーションを開始し、状態の遷移を監視して、結果を報告します。

=== 自動リバランシング

自動モードでは、エージェントはクラスター全体のリソース使用率を分析し、VM をより均等に分散するための移行計画を提案します。このワークフローには分析ステップが追加されます。

. **クラスターメトリクスの収集** -- エージェントはすべての Worker Node の CPU およびメモリ使用率データを収集し、不均衡を特定します。
. **移行計画の生成** -- メトリクスに基づいて、エージェントはどの VM をどこに移動すべきかを決定します。ストレージの互換性、ノードのキャパシティー、アンチアフィニティールールを考慮します。
. **レビュー用の計画の提示** -- エージェントは、提案された各移行、移行タイプ、各ノードへの予想されるリソースへの影響を示す表として、完全な移行計画を表示します。
. **VM ごとの確認を伴う実行** -- 計画を承認すると、エージェントは各移行を個別に実行し、進捗状況を報告します。残りの移行はいつでもキャンセルできます。

== ライブマイグレーションとコールドマイグレーションの比較

`vm-rebalance` スキルは、VM のストレージ設定に基づいてマイグレーションタイプを選択します。

[cols="1,2,2",options="header"]
|===
| 基準 | ライブマイグレーション | コールドマイグレーション
| ストレージアクセスモード | ReadWriteMany (RWX) | ReadWriteOnce (RWO)
| VM のダウンタイム | ゼロ -- マイグレーション中も VM は稼働を継続 | 短時間 -- VM が停止され、ストレージが移行され、VM が再起動される
| 一般的な所要時間 | 30 秒から 5 分 (メモリサイズおよびダーティーページ率に依存) | 2 から 15 分 (ディスクサイズに依存)
| ネットワーク接続 | 保持 -- アクティブな TCP 接続は維持される | 切断 -- クライアントは再起動後に再接続が必要
| ユースケース | 本番ワークロード、ステートフルサービス | 開発用 VM、バッチジョブ、非クリティカルなワークロード
|===

=== ライブマイグレーションの仕組み

KubeVirt のライブマイグレーションは、ゲストオペレーティングシステムを中断することなく、実行中の VM のメモリ状態を送信元ノードからターゲットノードに転送します。このプロセスは以下の段階に従います。

. **スケジューリング** -- 新しい VirtualMachineInstance (VMI) Pod がターゲットノードにスケジュールされます。
. **事前コピー** -- VM がソースノード上で実行され続けている間に、VM のメモリページがターゲットにコピーされます。
. **反復コピー** -- ダーティーページ (コピー中に変更されたメモリ) は、残りの差分が迅速な切り替えに十分小さくなるまで、連続するラウンドで再送信されます。
. **切り替え** -- ソースノードで VM が一時的に停止され、最後のダーティーページが転送された後、ターゲットノードで VM が再開されます。
. **クリーンアップ** -- ソースの VMI Pod が終了されます。

マイグレーション状態の遷移を監視できます:

[source,bash,role=execute]
----
oc get vmim -n my-vms -w
----

=== コールドマイグレーションが必要な場合

コールドマイグレーションは、VM のストレージがノード間での共有アクセスをサポートしていない場合に使用されます。一般的なシナリオには以下が含まれます:

* VM が一度に 1 つのノードにのみマウントできる `ReadWriteOnce` (RWO) アクセスモードの PVC を使用している。
* 基盤となる StorageClass がボリュームのクローン作成またはマルチアタッチをサポートしていない。
* VM には共有できないローカルストレージ (hostPath または local-volume) があります。

エージェントは、コールドマイグレーションが使用される場合に常に通知し、処理を進める前に予想されるダウンタイムについて警告します。

== ストレージ互換性の検証

移行を開始する前に、`vm-rebalance` スキルは VM のストレージ設定が要求された移行タイプをサポートしているかどうかを検証します。エージェントは以下のチェックを実行します:

=== アクセスモードのチェック

エージェントは PVC のアクセスモードを検査して、移行の適格性を判断します:

[cols="1,2,2",options="header"]
|===
| アクセスモード | ライブマイグレーション | コールドマイグレーション
| ReadWriteMany (RWX) | サポート対象 | サポート対象
| ReadWriteOnce (RWO) | サポート対象外 | サポート対象
| ReadOnlyMany (ROX) | サポート対象 (読み取り専用ディスク) | サポート対象
|===

VM の PVC アクセスモードを確認できます:

[source,bash,role=execute]
----
oc get pvc -n my-vms -o custom-columns="NAME:.metadata.name,ACCESS:.status.accessModes[0],CAPACITY:.status.capacity.storage"
----

----
NAME         ACCESS     CAPACITY
db-01-rootdisk    ReadWriteOnce  30Gi
web-01-rootdisk   ReadWriteMany  30Gi
web-02-rootdisk   ReadWriteMany  30Gi
----

=== StorageClass の機能チェック

エージェントは、StorageClass が移行に必要な操作をサポートしていることも確認します:

[source,bash,role=execute]
----
oc get storageclass -o custom-columns="NAME:.metadata.name,PROVISIONER:.provisioner,BINDING:.volumeBindingMode"
----

マルチアタッチをサポートする CSI ドライバーを使用するストレージクラス (RWX を備えた Ceph RBD や CephFS など) は、ライブマイグレーションを可能にします。単一ノードへのアタッチに制限されているストレージクラス (local-volume や特定の LVM 実装など) では、コールドマイグレーションが必要です。

== ノード準備状況チェック

`vm-rebalance` スキルは、移行を提案または実行する前にターゲットノードを検証します。エージェントは以下の条件をチェックします。

=== ノードのスケジュール可能性

エージェントは、ターゲットノードが cordon されていないこと、またはスケジュール不可としてマークされていないことを検証します。

[source,bash,role=execute]
----
oc get nodes -o custom-columns="NAME:.metadata.name,STATUS:.status.conditions[-1].type,SCHEDULABLE:.spec.unschedulable"
----

----
NAME    STATUS  SCHEDULABLE
worker-01  Ready  <none>
worker-02  Ready  <none>
----

`SCHEDULABLE: true` (unschedulable フラグが設定されている) のノードは cordon されており、移行ターゲットから除外されます。

=== taint の検証

エージェントは、ターゲットノードに VM の Pod が許容 (tolerate) していないテイント (taint) があるかどうかを確認します。許容されない taint が存在する場合、エージェントは別のターゲットノードを選択するか、適切なターゲットが利用できないことを通知します。

[source,bash,role=execute]
----
oc get nodes -o custom-columns="NAME:.metadata.name,TAINTS:.spec.taints[*].key"
----

=== リソース容量

エージェントは、ターゲットノードに受信 VM 用の十分な割り当て可能 CPU およびメモリがあることを確認します。VM のリソース要求 (requests) とノードの残りの容量 (割り当て可能容量から現在割り当てられている容量を差し引いたもの) を比較します。

[source,bash,role=execute]
----
oc describe node worker-01 | grep -A 5 "Allocated resources"
----

ターゲットノードのリソースが不足している場合、エージェントは不足分を報告し、代替ノードを提案するか、クラスターのスケーリングを推奨します。

== Human-in-the-Loop による確認

`vm-rebalance` スキルは、移行が VM の可用性に影響を与えるため、すべての段階で明示的な確認を要求します。

**手動移行**:

* エージェントは、続行する前に移行タイプ (ライブまたはコールド)、移行元ノード、移行先ノード、および予想される影響を提示します。
* コールド移行には、ダウンタイムに関する明示的な警告が含まれます。
* 移行を実行する前に、「yes」で確認する必要があります。

**自動リバランス**:

* エージェントは、移行が開始される前に完全な移行プランをテーブル形式で提示します。
* プランを確認し、全体として承認または拒否します。
* 承認されたプラン内の個々の移行は順次実行されます。いずれかの移行が失敗した場合、エージェントは停止し、残りの移行を実行せずに失敗を報告します。

**ノードドレイン操作**:

* エージェントはノード上のすべての VM のインベントリを作成し、完全なドレイン計画を提示します。
* この計画には各 VM の移行タイプが表示されるため、全体的な影響を評価できます。
* 実行が開始される前に、ドレイン計画全体を承認します。

すべてのモードにおいて、いずれかの確認ステップで "no" または "cancel" と入力すると、操作がキャンセルされます。明示的に承認するまで VM は移動されません。

== クリーンアップ

このチュートリアル中に作成された VM を削除するには:

[source,bash,role=execute]
----
oc delete vm web-01 web-02 db-01 -n my-vms
----

または、自然言語を使用することもできます。IDE チャットに "Delete VM web-01 in namespace my-vms" と入力します。`vm-delete` スキルが完全な安全ワークフローで削除を処理します。

テスト中に cordon されたノードを uncordon するには:

[source,bash,role=execute]
----
oc adm uncordon worker-01
----

namespace を削除するには:

[source,bash,role=execute]
----
oc delete namespace my-vms
----

== まとめ

* `vm-rebalance` スキルは、クラスターノード間での手動 (ユーザー主導) および自動 (AI 主導) の VM 移行をサポートします。
* ライブマイグレーションは、ReadWriteMany (RWX) ストレージを持つ VM に対してダウンタイムなしの VM 移動を提供します。アクティブなネットワーク接続はライブマイグレーション中も維持されます。
* コールドマイグレーションは、ReadWriteOnce (RWO) ストレージを使用する VM に使用され、短時間のダウンタイムを伴う停止、再スケジュール、起動のシーケンスが行われます。
* ノードドレイン操作は、メンテナンス前にノードからすべての VM を移行し、ストレージ設定に基づいて各 VM に適したマイグレーションタイプを選択します。
* 自動リバランスは、クラスターの CPU およびメモリ使用率を分析し、VM を均等に分散するためのマイグレーションプランを提案します。
* エージェントは、マイグレーションを提案する前に、ターゲットノードの準備状態 (スケジューリング可能性、taint、リソース容量) およびストレージの互換性を検証します。
* すべてのマイグレーション操作には、ユーザーによる明示的な確認が必要です。コールドマイグレーションにはダウンタイムの警告が含まれます。
