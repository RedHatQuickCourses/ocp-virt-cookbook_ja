= リアルタイム仮想マシン
:navtitle: リアルタイム VM

== 概要

本チュートリアルでは、OpenShift Virtualization でリアルタイム仮想マシンを構成する方法を解説します。リアルタイム VM は、5G RAN (vDU/vCU)、産業用制御システム、金融の取引処理 (tick-to-trade)、高頻度テレメトリなど、厳密に上限が定められたレイテンシー要件を持つワークロード向けに設計されています。

共有 CPU ホスト上の標準的な VM では、数十ミリ秒のスケジューリングレイテンシーのスパイクが発生することがあります。適切に構成されたリアルタイム VM は、複数のチューニング層を組み合わせることで、最悪の場合のレイテンシーを数マイクロ秒の範囲まで低減します。

[cols="2,3,2",options="header"]
|===
|構成レイヤー |排除されるジッターのソース |設定場所

|専用 CPU の配置
|他ワークロードによる CPU steal
|VM スペック (`dedicatedCpuPlacement`)

|エミュレーターのスレッド分離
|vCPU コア上の QEMU のハウスキーピング
|VM スペック (`isolateEmulatorThread`)

|NUMA パススルー
|NUMA 間メモリアクセスのレイテンシー
|VM スペック (`guestMappingPassthrough`)

|Hugepages
|TLB ミスおよびページテーブルウォーク
|VM スペック (`memory.hugepages`)

|ホストの RT カーネル
|カーネルプリエンプションの遅延、タイマージッター
|PerformanceProfile (`realTimeKernel`)

|ホストの CPU 分離
|IRQ およびカーネルスレッドの干渉
|PerformanceProfile (`cpu.isolated`)

|ゲストの RT スケジューリング
|ゲスト vCPU のスケジューリング優先度
|VM スペック (`cpu.realtime`)

|バルーン/グラフィックスの無効化
|不要なデバイス割り込み
|VM スペック (`autoattachMemBalloon: false`)
|===

本チュートリアルは、パフォーマンスシリーズの 3 番目のチュートリアルです。xref:cpu-pinning.adoc[専用 CPU の配置]および xref:numa-hugepages.adoc[NUMA/Hugepages]のチュートリアルに基づいています。

== 前提条件

* OpenShift Virtualization Operator がインストールされた OpenShift 4.18 以上 (4.21 で検証済み) 
* クラスター管理者アクセス権 (`system:admin` または同等の権限) 
* `oc` および `virtctl` CLI のインストール
* 少なくとも 8 つの物理 CPU コアと 16Gi の RAM を備えた Worker Node
* CPU Manager static policy が有効であること (xref:cpu-pinning.adoc[専用 CPU の配置]チュートリアルを参照) 
* Hugepages と NUMA トポロジーに関する知識 (xref:numa-hugepages.adoc[NUMA と Hugepages]チュートリアルを参照) 
* Node Tuning Operator がインストールされていること (OpenShift にデフォルトで含まれています) 

== リアルタイム要件の理解

仮想化におけるリアルタイムとは、平均応答速度が最も速いことではなく、*最悪の場合のレイテンシーが一定の範囲に収まっていること*を意味します。リアルタイム VM は、負荷がかかっている状態であっても、特定の操作が決定論的な時間枠内で完了することを保証します。

これを実現するには、ホストカーネル、ハイパーバイザー、ゲストカーネル、アプリケーションというスタック全体を通じて、無制限のジッターの原因をすべて排除する必要があります。概要の構成表は、各 VM スペックのフィールドと、それが対応する特定のジッターソースを示しています。

IMPORTANT: リアルタイム VM は、最もチューニングが不十分なレイヤーと同程度の性能しか発揮できません。単一のレイヤーでも省略すると (例：RT カーネルを使用するが CPU 分離を行わない)、ジッターの原因が残存し、目的が果たせなくなります。

== ステップ 1: リアルタイム用 MachineConfigPool の準備

リアルタイムノードには専用の MachineConfigPool が必要です。これにより、他のノードに影響を与えることなく、PerformanceProfile によって RT カーネル、CPU 分離、Hugepages 構成を適用できます。

まず、対象の Worker Node に `worker-rt` ロールを付与します。

[source,bash,role=execute]
----
oc label node <node-name> node-role.kubernetes.io/worker-rt=
----

`worker` ロールと `worker-rt` ロールの両方を持つノードを選択する MachineConfigPool を作成します。

[source,bash,role=execute]
----
oc apply -f - <<EOF
apiVersion: machineconfiguration.openshift.io/v1
kind: MachineConfigPool
metadata:
  name: worker-rt
  labels:
    machineconfiguration.openshift.io/role: worker-rt
spec:
  machineConfigSelector:
    matchExpressions:
    - key: machineconfiguration.openshift.io/role
      operator: In
      values:
      - worker
      - worker-rt
  nodeSelector:
    matchLabels:
      node-role.kubernetes.io/worker-rt: ""
EOF
----

プールが作成され、ノードがリストに含まれていることを確認します。

[source,bash,role=execute]
----
oc get mcp worker-rt
----

想定される出力:

----
NAME        CONFIG   UPDATED   UPDATING   DEGRADED   MACHINECOUNT   READYMACHINECOUNT
worker-rt            True      False      False      1              1
----

== ステップ 2: PerformanceProfile の適用

PerformanceProfile リソースは、Node Tuning Operator を構成し、以下の操作を行います。

* リアルタイムカーネル (`kernel-rt`) のインストール
* ワークロード用の CPU 2-7 の分離 (カーネルスレッドや IRQ のスケジューリングを禁止) 
* システムサービス用の CPU 0-1 の予約
* 4 x 1GiHugepages の事前割り当て
* レイテンシーを最小化するカーネル起動パラメーターの適用

xref:attachment$realtime-vms/performance-profile.yaml[performance-profile.yaml をダウンロード]

[source,bash,role=execute]
----
oc apply -f - <<EOF
apiVersion: performance.openshift.io/v2
kind: PerformanceProfile
metadata:
  name: realtime-workers
spec:
  cpu:
    isolated: "2-7"
    reserved: "0-1"
  hugepages:
    defaultHugepagesSize: 1G
    pages:
    - size: 1G
      count: 4
  realTimeKernel:
    enabled: true
  additionalKernelArgs:
  - nmi_watchdog=0
  - audit=0
  - mce=off
  - processor.max_cstate=1
  - idle=poll
  - intel_idle.max_cstate=0
  nodeSelector:
    node-role.kubernetes.io/worker-rt: ""
  machineConfigPoolSelector:
    machineconfiguration.openshift.io/role: worker-rt
EOF
----

NOTE: Single Node OpenShift (SNO) の場合は、ステップ 1 の MachineConfigPool 作成をスキップしてください。代わりに、`nodeSelector` を `node-role.kubernetes.io/master: ""` に、`machineConfigPoolSelector` を `pools.operator.machineconfiguration.openshift.io/master: ""` に設定して、既存のマスタープールを直接ターゲットにします。`machineConfigPoolSelector` は、内部で使用される `machineConfigSelector` ではなく、MCP 自体の `metadata.labels` にあるラベルと一致させる必要があります。VM マニフェストの `nodeSelector` でそのラベルを使用するため、ステップ 1 の `worker-rt` ラベル (`oc label node <node-name> node-role.kubernetes.io/worker-rt=`) を付与しておく必要があります。

IMPORTANT: PerformanceProfile API では、Hugepages サイズに IEC 単位 (`1Gi`, `2Mi`) ではなく SI 単位 (`1G`, `2M`) を使用します。これは、VM スペックで使用される Kubernetes リソース構文 (`1Gi`, `2Mi`) とは異なります。

PerformanceProfile は、基礎となる複数のリソースを生成します。それらは `Tuned` プロファイル、カーネル引数用の `MachineConfig`、CPU Manager 設定用の `KubeletConfig` です。その後、Machine Config Operator がターゲットノードを再起動します。

WARNING: PerformanceProfile を適用すると、RT カーネルのインストールとカーネルパラメーターの適用のため、ターゲットノードが再起動されます。影響を受けるノードのダウンタイムを計画してください。

ロールアウトを監視します。

[source,bash,role=execute]
----
oc get mcp worker-rt -w
----

SNO の場合は、代わりに `master` プールを監視します。

[source,bash,role=execute]
----
oc get mcp master -w
----

`UPDATED` が `True` になり、`READYMACHINECOUNT` が `MACHINECOUNT` と一致するまで待ちます。ノードが RT カーネルをダウンロードし、再起動し、クラスターに再参加するため、10-20 分かかる場合があります。MCP は再起動完了後も `UPDATING: True` 状態のままになることがありますが、これはノードが構成の調整を完了し、クラスターに準備完了を報告している間です。ロールアウトが完全に完了するまで先に進まないでください。

=== カーネルパラメーターの理解

[cols="2,3",options="header"]
|===
|パラメーター |目的

|`nmi_watchdog=0`
|定期的な割り込みを削減するために、NMI ウォッチドッグタイマーを無効化

|`audit=0`
|監査に伴う遅延を回避するため、カーネル監査機能を無効化

|`mce=off`
|割り込み処理削減のため、マシンチェック例外ロギングを無効化

|`processor.max_cstate=1`
|CPU が深いスリープ状態 (C-states > C1) になるのを防ぎ、ウェイクアップレイテンシを回避

|`idle=poll`
|アイドル状態の CPU に対して停止 (halt) の代わりにポーリングを使用し、消費電力と引き換えにウェイクアップレイテンシを短縮

|`intel_idle.max_cstate=0`
|Intel の C-state ドライバーを無効化し、`processor.max_cstate` を補完
|===

NOTE: これらのパラメーターは、電力と遅延の間でアグレッシブなトレードオフを伴います。RT ノード上の CPU は、アイドル時であっても最大電力を消費します。レイテンシーの影響を受けやすいワークロード専用のノードにのみ適用してください。

== ステップ 3: RT ノードが準備完了であることの確認

MachineConfigPool のロールアウトが完了したら、ノード構成を確認します。

カーネルバージョンを確認します。

[source,bash,role=execute]
----
oc debug node/<node-name>
----

デバッグシェル内にて：

[source,bash,role=execute]
----
chroot /host uname -r
----

カーネル名に `rt` が含まれているはずです。例：

----
5.14.0-427.55.1.el9_4.x86_64+rt
----

カーネル起動パラメーターを確認して、CPU 分離が構成されていることを確認します。

[source,bash,role=execute]
----
chroot /host cat /proc/cmdline | grep -o 'isolcpus=managed_irq,[^ ]*'
----

想定される出力:

----
isolcpus=managed_irq,2-7
----

分離された CPU で tick-less (nohz) モードがアクティブであることを確認します。

[source,bash,role=execute]
----
chroot /host cat /sys/devices/system/cpu/nohz_full
----

想定される出力 (PerformanceProfile の `cpu.isolated` と一致):

----
2-7
----

デフォルトの IRQ アフィニティマスクを確認します。

[source,bash,role=execute]
----
chroot /host cat /proc/irq/default_smp_affinity
----

`managed_irq` モードでは、デフォルトのアフィニティマスクがすべての CPU を表示する可能性があります。IRQ ステアリングは静的なアフィニティマスクではなく、Tuned によって生成された `irqbalance` ヒントによって動的に処理されます。

Hugepages の割り当てを確認します。

[source,bash,role=execute]
----
chroot /host grep -i hugepages /proc/meminfo
----

`HugePages_Total` が要求された数 (1Gi ページの場合は 4) と一致することを確認します。

`kubevirt.io/realtime` ラベルが存在することを確認します。

[source,bash,role=execute]
----
exit
----

[source,bash,role=execute]
----
oc get node <node-name> -L kubevirt.io/realtime
----

KubeVirt は、`kernel.sched_rt_runtime_us` が -1 (無制限の RT スケジューリング) に設定されているノードに自動的にラベルを付けます。ラベルがない場合は、設定を確認してください。

[source,bash,role=execute]
----
oc debug node/<node-name> -- chroot /host sysctl kernel.sched_rt_runtime_us
----

想定される出力:

----
kernel.sched_rt_runtime_us = -1
----

== ステップ 5: リアルタイム VM のデプロイ

以下の VM マニフェストは、すべてのリアルタイムチューニングレイヤーを組み合わせています。ここでは標準的な Fedora コンテナディスクを使用します。リアルタイムカーネルを備えた専用の RT ゲストイメージを使用することで最良の結果が得られますが、標準イメージでもホスト側の構成を実証および検証するには十分です。

主要な構成フィールド：

* `cpu.model: host-passthrough` -- マスキングせずにすべてのホスト CPU 機能をゲストに公開
* `cpu.dedicatedCpuPlacement: true` -- vCPU を分離された物理 CPU に固定
* `cpu.isolateEmulatorThread: true` -- QEMU エミュレータースレッド専用の CPU を予約
* `cpu.ioThreadsPolicy: auto` -- I/O スレッドをエミュレータースレッドと同じ CPU に配置
* `cpu.numa.guestMappingPassthrough: {}` -- ホストの NUMA トポロジーをゲストに渡す
* `cpu.realtime.mask: "0"` -- vCPU 0 を SCHED_FIFO スケジューリング用に構成。vCPU 1 はハウスキーピングタスク用にデフォルトスケジューラーのまま維持
* `memory.hugepages.pageSize: 1Gi` -- 1GiHugepages プールからメモリを割り当て
* `autoattachMemBalloon: false` -- メモリ管理割り込みを回避するためにバルーンデバイスを無効化
* `autoattachGraphicsDevice: false` -- 割り込みソースを減らすためにグラフィックスデバイスを無効化

WARNING: この例の cloud-init パスワードはデモンストレーション専用です。本番環境では、SSH 鍵認証または強力で固有のパスワードを使用してください。

xref:attachment$realtime-vms/vm-realtime.yaml[vm-realtime.yaml をダウンロード]

[source,bash,role=execute]
----
oc apply -f - <<EOF
apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: vm-realtime
  namespace: realtime-demo
spec:
  runStrategy: Always
  template:
    metadata:
      labels:
        kubevirt.io/domain: vm-realtime
    spec:
      nodeSelector:
        node-role.kubernetes.io/worker-rt: ""
      domain:
        cpu:
          model: host-passthrough
          sockets: 1
          cores: 2
          threads: 1
          dedicatedCpuPlacement: true
          isolateEmulatorThread: true
          ioThreadsPolicy: auto
          numa:
            guestMappingPassthrough: {}
          realtime:
            mask: "0"
        memory:
          hugepages:
            pageSize: 1Gi
        resources:
          requests:
            memory: 2Gi
            cpu: 2
          limits:
            memory: 2Gi
            cpu: 2
        devices:
          autoattachSerialConsole: true
          autoattachMemBalloon: false
          autoattachGraphicsDevice: false
          disks:
          - name: rootdisk
            disk:
              bus: virtio
          - name: cloudinitdisk
            disk:
              bus: virtio
          interfaces:
          - name: default
            masquerade: {}
      networks:
      - name: default
        pod: {}
      terminationGracePeriodSeconds: 0
      volumes:
      - name: rootdisk
        containerDisk:
          image: quay.io/containerdisks/fedora:latest
      - name: cloudinitdisk
        cloudInitNoCloud:
          userData: |
            #cloud-config
            password: redhat
            chpasswd:
              expire: false
EOF
----

VM が Running ステータスになるまで待ちます。

[source,bash,role=execute]
----
oc get vm vm-realtime -n realtime-demo -w
----

想定される出力:

----
NAME          AGE   STATUS    READY
vm-realtime   90s   Running   True
----

NOTE: VM は `kubevirt.io/realtime` および `cpumanager=true` ラベルが付いたノードにのみスケジュールされます。KubeVirt は VM スペックで `realtime` が指定されると、これらのセレクターを自動的に追加します。VM が `Scheduling` 状態のままになる場合は、ターゲットノードが両方のラベルを持っていることを確認してください。

== ステップ 6: ホスト上でのリアルタイムチューニングの検証

=== CPU pinning の検証

VM が実行されているノードを検索します。

[source,bash,role=execute]
----
oc get vmi vm-realtime -n realtime-demo -o wide
----

そのノードでデバッグセッションを開きます。

[source,bash,role=execute]
----
oc debug node/<node-name>
----

CPU Manager の状態を確認し、どの物理 CPU が割り当てられているかを確認します。

[source,bash,role=execute]
----
chroot /host cat /var/lib/kubelet/cpu_manager_state
----

`entries` マップには、2 つの vCPU ID と 1 つのエミュレータースレッド用 CPU (合計 3 つ) を持つ `compute` コンテナが表示されるはずです。割り当てられたすべての CPU は、分離された範囲 (PerformanceProfile に従って 2-7) 内にある必要があります。

=== Hugepages の検証

[source,bash,role=execute]
----
chroot /host grep HugePages /proc/meminfo
----

`HugePages_Free` は、VM によって消費された分 (1GiHugepages を使用する 2Gi VM の場合は 2 ページ) だけ `HugePages_Total` よりも少なくなっているはずです。

IMPORTANT: `guestMappingPassthrough` を使用する場合、vCPU がスケジュールされている各 NUMA ノードで Hugepages が利用可能である必要があります。PerformanceProfile が Hugepages を NUMA ノード間で均等に分散している場合、単一ノードの割り当て分を超えるメモリを要求すると、割り当てに失敗します。VM のメモリ要求は、NUMA ノードごとの Hugepages 割り当て以下に抑えてください。

デバッグシェルを終了します。

[source,bash,role=execute]
----
exit
----

== ステップ 7: VM 内でのリアルタイム構成の検証

VM コンソールに接続します。

[source,bash,role=execute]
----
virtctl console vm-realtime -n realtime-demo
----

ユーザー `fedora`、パスワード `redhat` でログインします。

=== カーネルタイプの確認

[source,bash,role=execute]
----
uname -r
----

ゲストが標準カーネル (`rt` サフィックスなし) を実行している場合でも、vCPU のホストレベルではリアルタイムスケジューリングがアクティブになっています。ゲスト RT カーネルを使用すると、ゲスト内でのプリエンプション保証が追加されるため、本番ワークロードには推奨されます。

=== CPU 数の確認

[source,bash,role=execute]
----
lscpu | grep -E "^CPU\(s\)|^Socket|^Core|^Thread"
----

想定される出力:

----
CPU(s):                  2
Thread(s) per core:      1
Core(s) per socket:      2
Socket(s):               1
----

=== スケジューリングポリシーの確認 (ホストの視点から) 

`Ctrl+]` を押してゲストコンソールから切断します。

ホストレベルのリアルタイムスケジューリングは、QEMU vCPU スレッド上で KubeVirt によって構成されます。これはホストのデバッグセッションから確認できます。VM のノードでデバッグセッションを開きます。

[source,bash,role=execute]
----
oc debug node/<node-name>
----

QEMU プロセス ID を検索します。

[source,bash,role=execute]
----
chroot /host pgrep qemu-kvm
----

前のコマンドで取得した PID を `<qemu-pid>` に置き換え、そのプロセスのすべてのスレッドを、スケジューリングポリシーと優先度とともにリストします。

[source,bash,role=execute]
----
chroot /host ps -T -o tid,cls,rtprio,comm -p <qemu-pid>
----

想定される出力:

----
    TID CLS RTPRIO COMMAND
  70898  TS      - qemu-kvm
  70900  TS      - call_rcu
  70901  TS      - TC tc-ram-node0
  70941  TS      - IO mon_iothread
  70942  FF      1 CPU 0/KVM
  70943  TS      - CPU 1/KVM
----

`CLS` 列はスケジューリングクラスを示します (`SCHED_FIFO` は `FF`、`SCHED_OTHER` は `TS`) 。`RTPRIO` 列はリアルタイム優先度を示します。スレッド `CPU 0/KVM` は優先度 `1` の `FF` を示しており、`realtime.mask: "0"` で指定された通りに `SCHED_FIFO` でスケジュールされていることが確認できます。スレッド `CPU 1/KVM` は `TS` を示しており、ハウスキーピングタスク用にはデフォルトスケジューラーが維持されていることがわかります。

デバッグシェルを終了します。

[source,bash,role=execute]
----
exit
----

== ステップ 8: レイテンシーの測定とベースラインの設定

適切なレイテンシーベースラインを取得するには、`cyclictest` が標準的なツールです。これはリアルタイムスレッドの最悪値のウェイクアップレイテンシを測定します。

VM コンソールに接続します。

[source,bash,role=execute]
----
virtctl console vm-realtime -n realtime-demo
----

ログイン後、`realtime-tests` をインストールします (`cyclictest` を提供します) 。

[source,bash,role=execute]
----
sudo dnf install -y realtime-tests
----

短い cyclictest を実行し、3 スレッドのレイテンシーを 60 秒間測定します。

[source,bash,role=execute]
----
sudo cyclictest --mlockall --smp --priority=80 --interval=200 --distance=0 --duration=60
----

実行結果例:

----
# /dev/cpu_dma_latency が 0us に設定済み
policy: fifo: loadavg: 0.92 0.42 0.18 1/148 1599

T: 0 ( 1597) P:80 I:200 C: 156868 Min:      3 Act:    5 Avg:  191 Max:    9501
T: 1 ( 1598) P:80 I:200 C: 277750 Min:      3 Act:    7 Avg:   36 Max:    1406
----

`Max` 列はマイクロ秒単位の最悪値の遅延を示します。標準 (非 RT) ゲストカーネルの場合、ゲスト内部のスケジューリングはプリエンプションフリーではないため、数百から数千マイクロ秒の最大レイテンシーが予想されます。RT カーネルを実行する専用のゲストイメージを使用すると、最大レイテンシーは数十マイクロ秒まで低下します。

NOTE: RT Worker Node と最適化されたゲストイメージを備えた完全にチューニングされた OpenShift Virtualization デプロイメントでは、Red Hat のベンチマークにおいて 54-55 マイクロ秒の最大遅延が実現されています。詳細については、link:https://www.redhat.com/en/blog/benchmark-latency-openshift[Benchmarking Red Hat OpenShift Virtualization for latency-sensitive workloads,window=_blank] を参照してください。

IMPORTANT: 遅延の結果は、ハードウェア、BIOS 設定、ワークロードに基づいて大きく変動します。これらの数値は例示です。*必ず独自のベースラインを確立し、ワークロードのレイテンシー予算と比較してください。*

`Ctrl+]` を押してコンソールから切断します。

== ステップ 9: ゲスト RT カーネルによるフルスタックのリアルタイム化

ステップ 8 の cyclictest の結果では、最大レイテンシーが数百から数千マイクロ秒を示しています。これは、ゲスト内の標準 Fedora カーネルが `PREEMPT_DYNAMIC` スケジューリングを使用しており、カーネル内コードパスの制限付きプリエンプションを保証できないためです。ホスト側の `SCHED_FIFO` 優先度と CPU 分離により *外部* ジッター (他の Pod、IRQ、CPU 時間を奪うカーネルスレッド) は排除されますが、タイマー割り込みが vCPU に到達した後も、*ゲストカーネル* がスリープ状態の cyclictest スレッドを起動する必要があります。標準カーネルでは、プリエンプト不可能なコードセクションの処理を完了する間に、その起動が遅れる可能性があります。

ゲスト内に `PREEMPT_RT` カーネルをインストールすることで、リアルタイムスタックが完成します。ゲスト RT カーネルを使用すると、実質的にすべてのカーネルコードパスがプリエンプト可能になり、cyclictest の最大レイテンシーはミリ秒単位から数十マイクロ秒前半へと低下します。

[cols="2,3,3",options="header"]
|===
|構成 |ゲストカーネル |予想される cyclictest 最大レイテンシー

|ホスト RT のみ
|標準 (`PREEMPT_DYNAMIC`)
|数百から数千マイクロ秒

|フルスタック RT
|リアルタイム (`PREEMPT_RT`)
|数十マイクロ秒前半
|===

=== ゲスト内への RT カーネルのインストール

実行中の VM に接続します。

[source,bash,role=execute]
----
virtctl console vm-realtime -n realtime-demo
----

`fedora` としてパスワード `redhat` でログインします。

`PREEMPT_RT` カーネルパッケージを提供する Fedora Kernel Vanilla COPR リポジトリを有効にします。

[source,bash,role=execute]
----
sudo dnf -y copr enable @kernel-vanilla/stable
----

リアルタイムカーネルをインストールします。

[source,bash,role=execute]
----
sudo dnf -y install kernel-rt-core kernel-rt-modules
----

RT カーネルをデフォルトのブートエントリとして設定します。

[source,bash,role=execute]
----
sudo grubby --set-default /boot/vmlinuz-*rt*
----

`Ctrl+]` を押してコンソールから切断します。

=== VM の再起動

VM を再起動して RT カーネルで起動します。

[source,bash,role=execute]
----
virtctl restart vm-realtime -n realtime-demo
----

VM が Running 状態に戻るのを待ちます。

[source,bash,role=execute]
----
oc get vm vm-realtime -n realtime-demo -w
----

=== ゲスト RT カーネルの確認

VM コンソールに接続します。

[source,bash,role=execute]
----
virtctl console vm-realtime -n realtime-demo
----

ログインしてカーネルバージョンを確認します。

[source,bash,role=execute]
----
uname -r
----

出力のバージョン文字列に `rt` が含まれている必要があります (例:)。

----
6.15.2-0.rc0.20250604gite53b1bae1f73.502.vanilla.fc42.x86_64+rt
----

`PREEMPT_RT` がアクティブであることを確認します。

[source,bash,role=execute]
----
uname -v
----

出力に `PREEMPT_RT` が含まれており、完全なプリエンプティブルカーネルモードであることが確認できます。

=== RT カーネルでの cyclictest の再実行

VM は永続ストレージを使用しているため、ステップ 8 でインストールした `realtime-tests` が残っています。同じパラメーターで cyclictest を実行します。

[source,bash,role=execute]
----
sudo cyclictest --mlockall --smp --priority=80 --interval=200 --distance=0 --duration=60
----

ゲスト RT カーネルを使用すると、最大レイテンシーは数十マイクロ秒前半になることが期待されます。これは、ステップ 8 の標準カーネルで見られた数百から数千マイクロ秒と比べて大幅な改善です。

`Ctrl+]` を押してコンソールから切断します。

IMPORTANT: 本番環境のリアルタイムワークロードでは、実行時にインストールするのではなく、RT カーネルが事前インストールされたカスタムディスクイメージをビルドしてください。これにより、起動後のカーネルインストールと再起動のサイクルが不要になり、すべての RT VM にわたって一貫性のあるバージョン固定されたデプロイが保証されます。

== トラブルシューティング

=== VM のスケジュール失敗：リアルタイム対応ノードがない

ターゲットノードに `kubevirt.io/realtime` ラベルがあることを確認します。

[source,bash,role=execute]
----
oc get nodes -L kubevirt.io/realtime
----

ラベルがない場合は、RT カーネルがインストールされ、`kernel.sched_rt_runtime_us` が -1 であることを確認します。PerformanceProfile はこれを自動的に設定しますが、MachineConfigPool のロールアウトが完了していない場合、設定が適用されていない可能性があります。

=== PerformanceProfile が処理中で停止するか、ノードが異常 (Degraded) 状態になる

MachineConfigPool のステータスを確認します。

[source,bash,role=execute]
----
oc get mcp worker-rt
----

[source,bash,role=execute]
----
oc describe mcp worker-rt
----

`DEGRADED` が `True` の場合は、影響を受けるノードの machine-config-daemon ログを調査します。

[source,bash,role=execute]
----
oc logs -n openshift-machine-config-operator -l k8s-app=machine-config-daemon --tail=50
----

一般的な原因：RT カーネル RPM 用のディスク容量不足、または競合する MachineConfig

=== cyclictest での高い最大遅延

`cyclictest` で 100 マイクロ秒を超える最大遅延が表示される場合：

* QEMU vCPU スレッドが `SCHED_FIFO` で実行されていることを確認します (ステップ 7 を参照) 。
* 分離された CPU が IRQ を受信していないことを確認します。RT ノードで以下を確認してください。

[source,bash,role=execute]
----
oc debug node/<node-name> -- chroot /host cat /proc/interrupts
----

分離された CPU (2〜7 列) は、ほとんどの IRQ ラインで最小またはゼロの割り込みカウントを示すはずです。

* BIOS 設定が最適化されていることを確認します。必要に応じてハイパースレッディングを無効にし、C1 よりも深い C ステートを無効にし、パフォーマンスモードを有効にします。
* 最良の結果を得るには、ゲスト RT カーネルを使用してください。

=== VM が「insufficient hugepages (Hugepages 不足) 」で失敗する

PerformanceProfile は Hugepages を割り当てますが、既存の VM や Pod がそれらを消費している可能性があります。利用可能な Hugepages を確認します。

[source,bash,role=execute]
----
oc get node <node-name> -o jsonpath='{.status.allocatable.hugepages-1Gi}{"\n"}'
----

不足している場合は、他の Hugepages を消費するワークロードを停止するか、PerformanceProfile の `pages.count` を増やしてください。

== クリーンアップ

VM と Namespace を削除します。

[source,bash,role=execute]
----
oc delete namespace realtime-demo
----

PerformanceProfile を削除して、RT カーネルと CPU 分離を元に戻します。

[source,bash,role=execute]
----
oc delete performanceprofile realtime-workers
----

MachineConfigPool を削除します。

[source,bash,role=execute]
----
oc delete mcp worker-rt
----

ノードから `worker-rt` ロールラベルを削除します。

[source,bash,role=execute]
----
oc label node <node-name> node-role.kubernetes.io/worker-rt-
----

WARNING: PerformanceProfile と MachineConfigPool を削除すると、ノードを標準カーネルに戻すための再起動がトリガーされます。ロールアウトが完了するまで `worker` MachineConfigPool を監視してください。

== まとめ

本チュートリアルでは、以下の方法を学びました。

* リアルタイム Worker Node 専用の MachineConfigPool を作成する方法
* PerformanceProfile を適用して RT カーネルをインストールし、CPU を分離し、Hugepages を予約する方法
* RT ノードの準備状態を確認する方法: カーネルバージョン、分離 CPU、Hugepages 割り当て、`kubevirt.io/realtime` ラベル
* 遅延低減設定のフルスタックを備えたリアルタイム VM をデプロイする方法
* ホスト上で CPU pinning、Hugepages バックアップ、SCHED_FIFO スケジューリングを検証する方法
* `cyclictest` を使用して遅延を測定し、ベースラインを作成する方法
* 各構成レイヤーが特定のジッターソースを排除する役割を理解すること
