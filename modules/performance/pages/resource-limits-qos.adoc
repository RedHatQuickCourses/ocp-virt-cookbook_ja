= VM Resource LimitsとQoSの設定
:navtitle: Resource limitsとQoS

== 概要

このチュートリアルでは、OpenShift Virtualizationにおける仮想マシンのCPUおよびメモリのリソース requests、limits、QoS クラスの設定方法を解説します。適切なリソース管理を行うことで、リソースの枯渇を防ぎ、十分なVMパフォーマンスを確保し、効率的なマルチテナントクラスターの運用が可能になります。

KubeVirtがVMのリソース spec をコンテナレベルのrequestsとlimitsに変換する方法、KubernetesのQoS classをVMに適用する方法、ResourceQuotaやLimitRangeを使用してnamespaceレベルでガバナンスを強制する方法について学びます。

== 前提条件

* **OpenShift 4.18以降**  (OpenShift Virtualization Operator がインストール済みであること) 
* **クラスター管理者権限** (`system:admin` または同等の権限)
* **`oc` CLI** および **`virtctl` CLI** がインストール済みであること
* **デフォルト StorageClass** が設定済みであること (VMブートディスク用) 

検証済みバージョン:
----
OpenShift 4.20, 4.21
----

== VMリソース管理の理解

OpenShift VirtualizationでVMを作成すると、KubeVirtはそのVMのリソース spec を、VMをホストする `virt-launcher` コンテナの requests と limits に変換します。このマッピングを理解することは、キャパシティプランニングにおいて不可欠です。

=== CPU割り当て

* デフォルトでは、コンテナはvCPUあたり `1/cpuAllocationRatio` のCPUをrequestします (`cpuAllocationRatio` のデフォルト値は10)。1 vCPUを持つVMは100mのCPUをリクエストします。
* デフォルトではCPU limitsは設定されないため、キャパシティに余裕がある場合にVMはrequest値を超えてバーストできます。
* VMに対してCPU limitsを手動で設定した場合、CPU requestは自動的に算出されず、requestはlimits値と同じ値になります。
* vCPUの数は `sockets * cores * threads` として計算され、デフォルト値は1です。

=== メモリ割り当て

* VMは `spec.domain.memory.guest` または `spec.domain.resources.requests.memory` を介して必要なメモリを指定します。
* KubeVirtは、ゲストメモリに (QEMU、ファームウェア、ハイパーバイザーコンポーネント用の) オーバーヘッドを追加し、コンテナMemory requestを形成します。
* デフォルトでは Memory limits は設定されません。
* Memory limitsを設定する場合、オーバーヘッドを考慮して、ゲストメモリ値よりも少なくとも500 MiB または 2% 以上大きい値を設定する必要があります。

警告: VMに Memory limits を設定すると、ゲストOSやハイパーバイザーが一時的にそのlimitsを超えた場合にVMがクラッシュする可能性があります。limitsの設定には注意し、ゲストメモリとオーバーヘッドの合計よりも高い値を設定してください。

== ステップ 2: 異なるQoS classを持つVMのデプロイ

Kubernetesは、リソース構成に基づいてすべてのPodに3つのQoS classのうちの1つを割り当てます。VMはPod内で実行されるため、同じルールが適用されます。

=== Burstable QoS (デフォルト) 

リソースのrequestsのみがあり、limitsがないVMはBurstable QoSを取得します。これはOpenShift Virtualization VMのデフォルトの動作です。

警告: この例のcloud-initパスワードはデモ用です。本番環境では、常に強力で一意なパスワードまたはSSHキー認証を使用してください。

xref:attachment$resource-limits-qos/vm-burstable.yaml[vm-burstable.yaml をダウンロード]

[source,bash,role=execute]
----
oc apply -f - <<EOF
apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: vm-burstable
  namespace: resource-qos-demo
spec:
  runStrategy: Always
  template:
    metadata:
      labels:
        kubevirt.io/domain: vm-burstable
    spec:
      domain:
        memory:
          guest: 512Mi
        resources:
          requests:
            memory: 512Mi
        devices:
          disks:
          - name: rootdisk
            disk:
              bus: virtio
          - name: cloudinitdisk
            disk:
              bus: virtio
          interfaces:
          - name: default
            masquerade: {}
      networks:
      - name: default
        pod: {}
      volumes:
      - name: rootdisk
        containerDisk:
          image: quay.io/containerdisks/fedora:latest
      - name: cloudinitdisk
        cloudInitNoCloud:
          userData: |
            #cloud-config
            password: redhat
            chpasswd:
              expire: false
EOF
----

=== Guaranteed QoS

CPUとメモリの両方に対して、requestsとlimitsが等しいVMはGuaranteed QoSを取得します。これらのVMは最も高いスケジューリング優先度を持ち、メモリ圧迫時に最後に退避 (evict) されます。

xref:attachment$resource-limits-qos/vm-guaranteed.yaml[vm-guaranteed.yaml をダウンロード]

[source,bash,role=execute]
----
oc apply -f - <<EOF
apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: vm-guaranteed
  namespace: resource-qos-demo
spec:
  runStrategy: Always
  template:
    metadata:
      labels:
        kubevirt.io/domain: vm-guaranteed
    spec:
      domain:
        memory:
          guest: 512Mi
        resources:
          requests:
            memory: 1Gi
            cpu: "1"
          limits:
            memory: 1Gi
            cpu: "1"
        devices:
          disks:
          - name: rootdisk
            disk:
              bus: virtio
          - name: cloudinitdisk
            disk:
              bus: virtio
          interfaces:
          - name: default
            masquerade: {}
      networks:
      - name: default
        pod: {}
      volumes:
      - name: rootdisk
        containerDisk:
          image: quay.io/containerdisks/fedora:latest
      - name: cloudinitdisk
        cloudInitNoCloud:
          userData: |
            #cloud-config
            password: redhat
            chpasswd:
              expire: false
EOF
----

NOTE: Memory limits (1Gi) は、ハイパーバイザーのオーバーヘッドを考慮して、ゲストメモリ (512Mi) よりも十分に大きくする必要があります。limitsがゲストメモリに近すぎると、Podは拒否されます。

=== BestEffort QoS

リソースのrequestsやlimitsがないVMはBestEffort QoSを取得します。これらのVMは、リソースが逼迫した際に最初に 退避 (evict) されます。この構成は一般的に本番環境では推奨されません。

xref:attachment$resource-limits-qos/vm-besteffort.yaml[vm-besteffort.yaml をダウンロード]

[source,bash,role=execute]
----
oc apply -f - <<EOF
apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:

  namespace: resource-qos-demo
spec:
  runStrategy: Always
  template:
    metadata:

    spec:
      domain:
        memory:
          guest: 512Mi
        devices:
          disks:
          - name: rootdisk
            disk:
              bus: virtio
          - name: cloudinitdisk
            disk:
              bus: virtio
          interfaces:
          - name: default
            masquerade: {}
      networks:
      - name: default
        pod: {}
      volumes:
      - name: rootdisk
        containerDisk:
          image: quay.io/containerdisks/fedora:latest

== ステップ 3: QoS Classの検証

VMの起動を待ちます：

[source,bash,role=execute]
----
oc get vm -n resource-qos-demo
----

期待される出力：
----
NAME             AGE   STATUS    READY
vm-besteffort    30s   Running   True
vm-burstable     60s   Running   True
vm-guaranteed    45s   Running   True
----

各VMのPodに割り当てられたQoS classを確認します。

Burstable VMの場合：

[source,bash,role=execute]
----
oc get pod -n resource-qos-demo -l kubevirt.io/domain=vm-burstable -o jsonpath='{.items[0].status.qosClass}{"\n"}'
----

期待される出力：
----
Burstable
----

Guaranteed VMの場合：

[source,bash,role=execute]
----
oc get pod -n resource-qos-demo -l kubevirt.io/domain=vm-guaranteed -o jsonpath='{.items[0].status.qosClass}{"\n"}'
----

期待される出力：
----
Guaranteed
----

BestEffort VMの場合：

[source,bash,role=execute]
----
oc get pod -n resource-qos-demo -l kubevirt.io/domain=vm-besteffort -o jsonpath='{.items[0].status.qosClass}{"\n"}'
----

期待される出力：
----
Burstable
----

注記: `virt-launcher` コンテナのオーバーヘッドに対してKubeVirtが常に一定の基本となるResource requestsを追加するため、`vm-besteffort` であってもBestEffortではなくBurstableと表示されます。

`virt-launcher` Podの実際の詳細なリソース値を確認します。

Burstable VMの場合：

[source,bash,role=execute]
----
oc get pod -n resource-qos-demo -l kubevirt.io/domain=vm-burstable -o yaml
----

Guaranteed VMの場合：

[source,bash,role=execute]
----
oc get pod -n resource-qos-demo -l kubevirt.io/domain=vm-guaranteed -o yaml
----

BestEffort VMの場合：

[source,bash,role=execute]
----
oc get pod -n resource-qos-demo -l kubevirt.io/domain=vm-besteffort -o yaml
----

== ステップ 4: ResourceQuotaの適用

ResourceQuota は、namespace内のすべてのVMとPodにわたって合計の Resource limits を強制します。limits 付きの ResourceQuota が適用されると、KubeVirt は自動的に VM に Resource limits を設定します。

xref:attachment$resource-limits-qos/resource-quota.yaml[resource-quota.yaml をダウンロード]

[source,bash,role=execute]
----
oc apply -f - <<EOF
apiVersion: v1
kind: ResourceQuota
metadata:
  name: vm-resource-quota
  namespace: resource-qos-demo
spec:
  hard:
    requests.cpu: "4"
    requests.memory: 8Gi
    limits.cpu: "8"
    limits.memory: 16Gi
    pods: "10"
EOF
----

Quota を確認します：

[source,bash,role=execute]
----
oc describe resourcequota vm-resource-quota -n resource-qos-demo
----

出力には、namespaceの現在の使用量とハードlimitsが表示されます。このnamespaceで新しく作成されるVMには、quota に limits フィールドが含まれているため、自動的にCPU limits (1 vCPUあたり1) とMemory limits (requestsの2倍) が適用されます。

=== 自動 Memory Limits Ratio のカスタマイズ

デフォルトでは、自動Memory limitsはrequestsメモリの2倍に設定されます。これはnamespaceごとにカスタマイズ可能です：

[source,bash,role=execute]
----
oc label namespace resource-qos-demo alpha.kubevirt.io/auto-memory-limits-ratio=1.5
----

これにより、namespace内のすべての新しいVMに対して、自動 Memory limits ratio が1.5倍に設定されます。

== ステップ 5: LimitRangeの適用

LimitRangeは、namespace内のPodごとのデフォルト値および最大リソース値を設定し、すべてのVMが最小限のリソース割り当てを確実に受けられるようにします。

xref:attachment$resource-limits-qos/limit-range.yaml[limit-range.yaml をダウンロード]

[source,bash,role=execute]
----
oc apply -f - <<EOF
apiVersion: v1
kind: LimitRange
metadata:
  name: vm-limit-range
  namespace: resource-qos-demo
spec:
  limits:
  - type: Pod
    max:
      cpu: "4"
      memory: 8Gi
    min:
      cpu: 100m
      memory: 256Mi
  - type: Container
    default:
      cpu: 500m
      memory: 1Gi
    defaultRequest:
      cpu: 100m
      memory: 512Mi
    max:
      cpu: "4"
      memory: 8Gi
    min:
      cpu: 50m
      memory: 128Mi
EOF
----

検証します：

[source,bash,role=execute]
----
oc describe limitrange vm-limit-range -n resource-qos-demo
----

このLimitRangeが適用されている状態では、Resource requestsやlimitsを指定していない新しいPod (VM用の `virt-launcher` Podを含む) には、デフォルト値が適用されます。

== ステップ 6: リソース使用状況の監視

VM Podの実際のリソース消費量を確認します：

[source,bash,role=execute]
----
oc adm top pods -n resource-qos-demo
----

各 `virt-launcher` Podの現在のCPUおよびメモリ使用量が表示されます。これらの値をrequestsおよびlimitsと比較することで、サイジング最適化可能な箇所を特定します。

Quota に対する namespace レベルのリソース消費量を確認します：

[source,bash,role=execute]
----
oc describe resourcequota vm-resource-quota -n resource-qos-demo
----

== QoS classのまとめ

[cols="1,1,1,1",options="header"]
|===
| QoS class | 構成 | Eviction Priority | ユースケース

| Guaranteed
| CPUとメモリのrequests == limits
| 最後に退避 (evict)
| 本番データベース、重要なアプリケーション

| Burstable
| requestsが設定済み、limitsは未設定または異なる
| BestEffortの後に退避 (evict)
| 一般的なワークロード、開発用VM

| BestEffort
| requestsもlimitsも未設定
| 最初に退避 (evict)
| 一時的な、破棄可能なワークロード
|===

== サイジングの推奨事項

* **新しいワークロードにはBurstableから始める**: Memory requestを予想される使用量に設定し、必要に応じてVMがバーストできるようにします。
* **予測可能なパフォーマンスが必要で、退避 (evict) させたくない本番用VMにはGuaranteedを使用する**。
* **Memory limitsは控えめに設定する**: ハイパーバイザーのオーバーヘッドとメモリスパイクを考慮して、ゲストメモリの少なくとも2倍に設定します。
* **limitsする前に監視する**: 厳格なlimitsを設定する前に、`oc adm top pods` を使用して実際の使用量を観察します。
* **namespaceレベルでResourceQuotaを使用する**: 特定のチームがすべてのクラスターリソースを消費するのを防ぎます。
* **LimitRangeを使用して、すべてのVMに最小リソース割り当てと妥当なデフォルト設定を確保する**。

== まとめ

このチュートリアルでは、以下の方法を学びました：

* VMのCPUおよびメモリのrequestsとlimitsを設定する
* KubeVirtがどのようにVMリソースをコンテナリソースにマッピングするかを理解する
* Guaranteed、Burstable、BestEffort QoS classを持つVMをデプロイする
* ResourceQuotaを適用してnamespaceレベルのリソースガバナンスを強制する
* LimitRangeを適用してPodごとのデフォルト値と境界を設定する
* VMのリソース使用量を監視し、割り当てを最適化する
* namespaceごとに自動 Memory limits ratio をカスタマイズする
