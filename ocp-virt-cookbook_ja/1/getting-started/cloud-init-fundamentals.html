OpenShift Virtualization VM のための cloud-init 基礎

概要

cloud-init は、仮想マシンの初回起動時の初期化を自動化するための業界標準ツールです。 OpenShift Virtualization では、ほぼすべての VM が cloud-init を使用して、ユーザー設定、パスワード設定、SSH 鍵の設定、パッケージのインストール、ネットワークアドレスの割り当てを行います。 本チュートリアルでは、cloud-init の動作原理、KubeVirt による VM への cloud-init データの配信方法、VirtualMachine マニフェストへの cloud-init 設定の埋め込み方法について解説します。

学習内容

  • cloud-init とは何か、なぜ VM の自動化に重要なのか

  • 3 つの cloud-init データタイプ：userData、networkData、metadata

  • KubeVirt が NoCloud データソースを介して cloud-init データを VM に配信する仕組み

  • ユーザー作成、パッケージインストール、スクリプト実行のための一般的な cloud-config モジュール

  • VirtualMachine マニフェストに cloud-init を埋め込む 2 つのパターン (インライン記述と Secret 参照)

  • cloud-init が正常に実行されたことを確認する方法

検証済みバージョン：

OpenShift 4.18+

前提条件

  • OpenShift Virtualization がインストールされた OpenShift 4.18 以上

  • oc および virtctl CLI ツールがインストールされていること (virtctl を使用した VM 管理を参照)

  • YAML 構文の基礎知識

  • VM 作成の経験 (Web コンソールを使用したテンプレートからの VM の作成を参照)

cloud-init とは？

cloud-init は、仮想マシンの初回起動時にゲスト OS 内で実行されるオープンソースフレームワークです。 外部ソースから設定データを読み込み、ユーザーアカウントの作成、SSH アクセスの設定、パッケージのインストール、設定ファイルの書き込み、スクリプトの実行など、本来手動で行う必要のあるタスクを自動化するために使用されます。

cloud-init は、Fedora、RHEL、CentOS、Ubuntu、Debian など、ほとんどの Linux ディストリビューションでサポートされています。 これは、AWS、Azure、GCP などの主要なクラウドプラットフォームや、OpenShift Virtualization の基盤である KubeVirt を含む仮想化プラットフォーム全体で標準的な初期化メカニズムとなっています。

cloud-init はデフォルトでは VM の初回起動時にのみ実行されます。インスタンスデータが明示的にクリアされない限り、2 回目以降の再起動では cloud-init はスキップされます。

KubeVirt による cloud-init の配信

従来のクラウド環境では、VM はメタデータサービス (169.254.169.254 の HTTP エンドポイント) から cloud-init データを取得します。 KubeVirt は、*NoCloud データソース*と呼ばれる異なるアプローチを採用しています。

NoCloud を使用する場合、KubeVirt は以下の動作を行います。

  1. VirtualMachine マニフェスト (または参照された Secret) から cloud-init データを読み取る

  2. データを ISO イメージとしてフォーマットされた仮想ディスクにパッケージ化する

  3. virtio デバイスを介してディスクを VM に接続する

  4. ゲスト OS 内の cloud-init がそのディスクを検出し、データを読み取って設定を適用する

つまり、cloud-init の設定は Kubernetes リソース内に完結しており、外部のメタデータサービスは不要です。

spec:
  template:
    spec:
      volumes:
        - name: cloudinitdisk
          cloudInitNoCloud:        (1)
            userData: |
              #cloud-config
              ssh_pwauth: true
              user:
                name: fedora
                lock_passwd: false
                plain_text_passwd: changeme
1 cloudInitNoCloud ボリュームタイプを指定することで、KubeVirt に NoCloud データソースディスクを作成するよう指示。

cloud-init のデータタイプ

cloud-init は 3 種類の構成データを受け入れます。KubeVirt では、これらは cloudInitNoCloud ボリューム下のフィールドに対応します。

userData (cloud-config)

主要な構成チャネルです。userData には cloud-config ドキュメントが含まれます。これは #cloud-config ヘッダーで始まる YAML ファイルです。ここでユーザー、パッケージ、スクリプト、ファイル、VM のほとんどのカスタマイズを定義します。

cloudInitNoCloud:
  userData: |
    #cloud-config
    ssh_pwauth: true
    user:
      name: fedora
      lock_passwd: false
      plain_text_passwd: s3cur3p4ss
      ssh_authorized_keys:
        - ssh-ed25519 AAAA... user@workstation
    packages:
      - vim
      - tmux
1 行目の #cloud-config ヘッダーは必須です。これがないと、cloud-init はデータを cloud-config ドキュメントとして認識せず、処理を黙ってスキップします。

networkData (network-config v2)

VM インターフェース用のネットワーク設定です。Netplan 互換の network-config version 2 形式を使用します。静的 IP、カスタム DNS、マルチインターフェース設定が必要な場合に使用します。

シンプルな DHCP 設定の例：

cloudInitNoCloud:
  networkData: |
    version: 2
    ethernets:
      enp1s0:
        dhcp4: true

DNS とルートを指定した静的 IP 設定の例：

cloudInitNoCloud:
  networkData: |
    version: 2
    ethernets:
      enp1s0:
        addresses:
          - 192.168.1.100/24             (1)
        nameservers:
          addresses:
            - 192.168.1.1
            - 8.8.8.8                    (2)
        routes:
          - to: default
            via: 192.168.1.1             (3)
          - to: 10.0.0.0/8
            via: 192.168.1.254           (4)
1 CIDR 表記でのサブネットマスク付きの静的 IP アドレス
2 DNS リゾルバのアドレス
3 ルートとして定義されたデフォルトゲートウェイ (gateway4 は非推奨)
4 特定のゲートウェイ経由で 10.0.0.0/8 ネットワークに到達するための追加ルート

インターフェース名が予測できない場合に備え、名前の代わりに MAC アドレスでインターフェースを指定することも可能です。

cloudInitNoCloud:
  networkData: |
    version: 2
    ethernets:
      primary:
        match:
          macaddress: "52:54:00:12:34:56"
        addresses:
          - 192.168.1.100/24
        routes:
          - to: default
            via: 192.168.1.1
KubeVirt VM では、最初のインターフェースは通常 enp1s0、2 番目は enp2s0 となります。これらの名前は NetworkAttachmentDefinition の順序ではなく、VirtualMachine Spec でインターフェースが定義された順序に対応します。

マルチインターフェース設定や VLAN、高度なシナリオについては、静的 IP 設定を参照してください。

metadata

instance-id や local-hostname などの VM インスタンスメタデータです。多くの場合、KubeVirt は VirtualMachine リソースからメタデータを自動的に生成するため、手動で設定する必要はほとんどありません。

cloudInitNoCloud:
  metadata: |
    instance-id: my-vm-001
    local-hostname: my-vm
ホスト名のみを設定したい場合は、カスタムメタデータを提供するのではなく、userData 内の hostname モジュールを使用してください。

cloud-init の実行ステージ

cloud-init は起動プロセス中に 5 つのステージで実行されます。これらのステージを理解すると、設定がいつ反映されるかを予測するのに役立ちます。

ステージ 実行タイミング 動作

Generator

非常に早い起動時 (systemd generator)

cloud-init を実行するかどうかを判断

Local

ネットワークが立ち上がる前

networkData からネットワーク設定を適用

Network

ネットワークが利用可能になった後

残りのデータソース情報を取得し、ホスト名を設定

Config

Network ステージの後

設定モジュールの実行：ユーザー作成、ファイル書き込み、SSH 鍵のインストール

Final

起動の終了付近

runcmd コマンドの実行、パッケージのインストール、最終スクリプトの実行

この順序により、ネットワーク設定 (networkData) はユーザー設定 (userData モジュール) よりも先に適用されます。runcmd で指定されたコマンドは、他のすべてのモジュールが完了した後に最後に実行されます。

一般的な Cloud-config モジュール

以下のモジュールは、最も一般的な VM 初期化タスクをカバーしています。各例は #cloud-config userData ドキュメントの該当セクションを示しています。

ユーザー作成とパスワード設定

#cloud-config
ssh_pwauth: true
user:
  name: fedora
  lock_passwd: false
  plain_text_passwd: s3cur3p4ss
  ssh_authorized_keys:
    - ssh-ed25519 AAAA...key-data... user@workstation

user キーはデフォルトユーザーを設定します。パスワードログインを許可するには lock_passwd: false と plain_text_passwd を設定します。最上位レベルで ssh_pwauth: true を追加すると、SSH でのパスワード認証が有効になります (多くのクラウドイメージではデフォルトで無効になっています)。

デフォルト以外の追加ユーザーを作成するには、users リストを使用します。

#cloud-config
users:
  - name: admin
    groups: wheel
    sudo: ALL=(ALL) NOPASSWD:ALL
    ssh_authorized_keys:
      - ssh-ed25519 AAAA...key-data...
  - name: developer
    shell: /bin/bash

パッケージのインストール

#cloud-config
package_update: true
packages:
  - vim
  - git
  - tmux
  - python3
パッケージのインストールは final ステージで実行されます。VM はパッケージのインストール完了前であっても、コンソールからアクセス可能です。

コマンドの実行

#cloud-config
runcmd:
  - systemctl enable --now cockpit.socket
  - echo "VM initialized at $(date)" >> /var/log/vm-init.log

コマンドは final ステージ中に順番に実行されます。各エントリは文字列 (/bin/sh 経由で実行) またはリスト (直接実行) にできます。

ファイルの書き込み

#cloud-config
write_files:
  - path: /etc/motd
    content: |
      Welcome to the OpenShift Virtualization VM.
      Managed by cloud-init.
    permissions: '0644'
  - path: /etc/myapp/config.yaml
    content: |
      database: postgres
      port: 5432
    owner: root:root
    permissions: '0600'
write_files によって書き込まれたファイルは config ステージ中に作成されるため、runcmd が実行される前に存在します。これにより、設定ファイルを安全に書き込んでから、それに依存するサービスを runcmd で開始できます。

VirtualMachine マニフェストへの cloud-init 埋め込み

VirtualMachine に cloud-init データを提供するには 2 つのパターンがあります。

インライン記述 (cloudInitNoCloud)

最も簡単な方法は、cloud-init データを VirtualMachine マニフェストに直接埋め込む方法です。

minimal-cloud-init-vm.yaml をダウンロード

apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: fedora-cloud-init-demo
  namespace: demo
spec:
  runStrategy: Always
  template:
    metadata:
      labels:
        app: fedora-cloud-init-demo
    spec:
      domain:
        devices:
          disks:
            - disk:
                bus: virtio
              name: rootdisk
            - disk:
                bus: virtio
              name: cloudinitdisk
          interfaces:
            - masquerade: {}
              name: default
        resources:
          requests:
            memory: 2Gi
      networks:
        - name: default
          pod: {}
      volumes:
        - dataVolume:
            name: fedora-cloud-init-demo
          name: rootdisk
        - cloudInitNoCloud:                    (1)
            userData: |                        (2)
              #cloud-config
              ssh_pwauth: true
              user:
                name: fedora
                lock_passwd: false
                plain_text_passwd: s3cur3p4ss
                ssh_authorized_keys:
                  - 'ssh-ed25519 AAAA...your-key... user@workstation'
              users:
                - name: userone
                  lock_passwd: false
                  plain_text_passwd: s3cur3p4ss
                  ssh_authorized_keys:
                    - 'ssh-ed25519 AAAA...your-key... user@workstation'
              packages:
                - vim
                - git
              runcmd:
                - echo "cloud-init complete" > /tmp/cloud-init-done
          name: cloudinitdisk
  dataVolumeTemplates:
    - metadata:
        name: fedora-cloud-init-demo
      spec:
        sourceRef:
          kind: DataSource
          name: fedora
          namespace: openshift-virtualization-os-images
        storage:
          resources:
            requests:
              storage: 30Gi
1 cloudInitNoCloud ボリュームタイプが NoCloud データソースディスクを作成します。
2 userData フィールドに #cloud-config で始まる cloud-config YAML を含めます。

このパターンは小規模な設定に適しています。大規模な設定や機密情報を含む場合は、Secret 参照を使用してください。

Secret 参照

複雑な設定や、パスワードやトークンなどの機密値が cloud-init に含まれる場合は、Kubernetes Secret にデータを格納し、VirtualMachine から Secret を参照します。

cloud-init-secret-vm.yaml をダウンロード

まず、Secret を作成します。

oc create secret generic my-vm-cloud-init \
  --from-literal=userdata='#cloud-config
ssh_pwauth: true
user:
  name: fedora
  lock_passwd: false
  plain_text_passwd: s3cur3p4ss
  ssh_authorized_keys:
    - ssh-ed25519 AAAA...your-key... user@workstation
users:
  - name: userone
    lock_passwd: false
    plain_text_passwd: s3cur3p4ss
    ssh_authorized_keys:
      - ssh-ed25519 AAAA...your-key... user@workstation
packages:
  - vim
  - git
' \
  -n demo

次に、VirtualMachine マニフェストから参照します。

volumes:
  - cloudInitNoCloud:
      secretRef:
        name: my-vm-cloud-init         (1)
    name: cloudinitdisk
1 KubeVirt は Secret から userdata キーを読み取り、それを cloud-init の userData として提供します。

cloud-init の実行確認

VM が起動した後、cloud-init の設定処理が成功したかを確認します。

VM コンソールにアクセスします。

virtctl console fedora-cloud-init-demo -n demo

cloud-init の状態を確認します。

cloud-init status --long

成功した場合に想定される出力：

status: done
extended_status: done
boot_status_code: enabled-by-generator
detail:
DataSourceNoCloud [seed=/dev/vdb]

cloud-init がエラーを報告している場合は、ログを確認します。

cat /var/log/cloud-init.log | tail -50

詳細な診断手順や一般的な問題の解決策については、cloud-init のトラブルシューティングを参照してください。

よくある間違い

#cloud-config ヘッダーの欠落

userData の 1 行目は、正確に #cloud-config である必要があります。これがないと、cloud-init はエラーメッセージを出さずに userData ブロック全体を無視します。

YAML のインデントエラー

Cloud-config は YAML です。インデントの不整合 (タブとスペースの混在、ネストの深さ間違い) は解析失敗の原因となります。VM 内で cloud-init devel schema --config-file /path/to/config.yaml を使用して構文を検証してください。

ネットワーク設定を userData に記述

ネットワークインターフェースの設定は userData ではなく networkData に記述します。userData 内に network-config v2 の YAML を配置しても反映されません。

再起動時に cloud-init が再実行されるという期待

cloud-init は初回起動時に一度だけ実行されます。再実行させるには、cloud-init clean を実行してから再起動する必要があります。

Secret キー名の間違い

secretRef を使用する場合、Secret は userdata という名前のキー (すべて小文字) を持つ必要があります。userData や user-data という名前のキーは検出されません。

Windows VM の場合：Sysprep

cloud-init は Linux 専用のツールです。Windows VM の場合、OpenShift Virtualization は Sysprep をサポートしています。これは Microsoft System Preparation ツールのことで、初回起動時の同様のカスタマイズ (ホスト名、管理者パスワード、ドメイン参加、無人セットアップ) を実行します。

Windows VM の設定については、Windows VM へのリモートアクセスを参照してください。

クリーンアップ

本チュートリアルで作成したデモ用リソースを削除します。

oc delete vm fedora-cloud-init-demo -n demo
oc delete vm fedora-cloud-init-secret-demo -n demo
oc delete secret my-vm-cloud-init -n demo
oc delete namespace demo

まとめ

本チュートリアルでは以下の内容を学びました。

  • cloud-init は標準の Linux VM 初期化フレームワークであり、初回起動時に自動的に設定を行う

  • KubeVirt は NoCloud データソースを介して cloud-init データを配信し、VM に接続された virtio ディスクとしてパッケージ化する

  • 3 つのデータタイプ：userData (ユーザー・パッケージ・スクリプト用の cloud-config)、networkData (network-config v2)、metadata (インスタンス識別子)

  • cloud-init はステージ順に実行される：ネットワーク設定が最初、次にユーザー/ファイル設定、最後にコマンドとパッケージ

  • 2 つのマニフェストパターン：シンプルな構成にはインライン cloudInitNoCloud、複雑なデータや機密データには Secret 参照

  • cloud-init status --long および /var/log/cloud-init.log を使用した検証
