仮想マシンのネットワークポリシー

概要

このチュートリアルでは、OpenShift Virtualization の仮想マシンワークロードに Kubernetes NetworkPolicy および AdminNetworkPolicy を適用する方法を説明します。VM は virt-launcher Pod 内で実行されるため、ネットワークポリシーは VM の spec.template.metadata.labels で定義されたラベルを使用して Pod レベルで適用されます。このガイドでは、VM 向けのゼロトラストネットワークモデルの構築手順を順を追って説明します。まずすべてを拒否するベースラインから開始し、フロントエンド/バックエンドアーキテクチャに対して選択的にトラフィックを許可します。

VM トラフィックを分離し、VM ティア間で特定のポートアクセスを許可し、テナントユーザーがオーバーライドできないクラスター全体のガードレールとして AdminNetworkPolicy を使用する方法を学びます。

前提条件

  • OpenShift Virtualization Operator がインストールされた OpenShift 4.18+

  • クラスターネットワークプラグインとしての OVN-Kubernetes (OpenShift 4.12 以降のデフォルト)

  • AdminNetworkPolicy リソース用のクラスター管理者アクセス権

  • oc CLI がインストールされていること

ネットワークポリシーが VM Pod を選択する方法

OpenShift Virtualization が実行中の VM を作成すると、virt-launcher Pod が生成されます。VirtualMachine リソースの spec.template.metadata.labels で定義したラベルは、この Pod に適用されます。NetworkPolicy オブジェクトは、他のワークロードと同様に podSelector を使用してこれらの Pod を選択します。

apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
 name: web-vm
 labels:
  app: web
spec:
 template:
  metadata:
   labels:
    app: web    (1)
    role: frontend (1)
  spec:
   # ...
1 これらのラベルは virt-launcher Pod に伝播され、NetworkPolicy の podSelector フィールドで使用できます。
VirtualMachine リソース自体の metadata.labels にあるラベルは、virt-launcher Pod に影響を与えません。ポリシーに関連するラベルは、必ず spec.template.metadata.labels に配置してください。

ステップ 1: Namespace の作成と VM のデプロイ

デモ用の Namespace を作成し、フロントエンドの Web サーバーとバックエンドのデータベースリスナーという 2 つの VM をデプロイします。

oc create namespace netpol-demo

ポート 80 で Nginx を実行するフロントエンド VM をデプロイします。

vm-web.yaml のダウンロード

oc apply -f - <<EOF
apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
 name: web-vm
 namespace: netpol-demo
 labels:
  app: web
  role: frontend
spec:
 runStrategy: Always
 instancetype:
  name: u1.small
 preference:
  name: fedora
 template:
  metadata:
   labels:
    app: web
    role: frontend
  spec:
   domain:
    devices:
     disks:
      - name: containerdisk
       disk: {}
      - name: cloudinitdisk
       disk: {}
     interfaces:
      - name: default
       masquerade: {}
   networks:
    - name: default
     pod: {}
   volumes:
    - name: containerdisk
     containerDisk:
      image: quay.io/containerdisks/fedora:40
    - name: cloudinitdisk
     cloudInitNoCloud:
      userData: |
       #cloud-config
       password: changeme
       chpasswd:
        expire: false
       packages:
        - nginx
       runcmd:
        - systemctl enable --now nginx
EOF

ポート 5432 でリッスンするバックエンド VM をデプロイします。

vm-db.yaml をダウンロード

oc apply -f - <<EOF
apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
 name: db-vm
 namespace: netpol-demo
 labels:
  app: database
  role: backend
spec:
 runStrategy: Always
 instancetype:
  name: u1.small
 preference:
  name: fedora
 template:
  metadata:
   labels:
    app: database
    role: backend
  spec:
   domain:
    devices:
     disks:
      - name: containerdisk
       disk: {}
      - name: cloudinitdisk
       disk: {}
     interfaces:
      - name: default
       masquerade: {}
   networks:
    - name: default
     pod: {}
   volumes:
    - name: containerdisk
     containerDisk:
      image: quay.io/containerdisks/fedora:40
    - name: cloudinitdisk
     cloudInitNoCloud:
      userData: |
       #cloud-config
       password: changeme
       chpasswd:
        expire: false
       packages:
        - nmap-ncat
       runcmd:
        - ncat -l -k -p 5432 -e /usr/bin/echo &
EOF

両方の VM の準備が整うまで待機します。

oc wait vm web-vm db-vm -n netpol-demo --for=condition=Ready --timeout=300s

virt-launcher Pod に期待されるラベルが付与されていることを確認します。

oc get pods -n netpol-demo -l app=web --show-labels
oc get pods -n netpol-demo -l app=database --show-labels

ステップ 2: ベースライン接続の確認 (ポリシー適用前)

ポリシーを適用する前に、トラフィックが VM に問題なく流れることを確認します。両方の VM の Pod IP を取得します。

oc get vmi -n netpol-demo -o 'custom-columns=NAME:.metadata.name,IP:.status.interfaces[0].ipAddress'

表示された IP アドレスを書き留めます。このチュートリアル全体で接続テストに使用します。

接続確認に使用する長期間実行されるテスト Pod を default namespace に作成します。

oc run curl-test -n default --image=registry.access.redhat.com/ubi9/ubi-minimal --restart=Never -- sleep 3600

web VM への接続をテストします (<web-vm-ip> を上記の IP に置き換えます)。

oc exec -n default curl-test -- curl -s --connect-timeout 5 http://<web-vm-ip>:80

Nginx のウェルカムページの HTML が表示され、制限なく接続できることが確認できます。

ステップ 3: すべてを拒否するベースラインの適用

ゼロトラストモデルは、まずすべてのトラフィックを拒否し、その後に必要なトラフィックのみを明示的に許可することから始まります。このポリシーは、 namespace 内のすべての Pod に対して、すべての Ingress および Egress を拒否します。

deny-all.yaml のダウンロード

oc apply -f - <<EOF
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
 name: deny-all
 namespace: netpol-demo
spec:
 podSelector: {}
 policyTypes:
  - Ingress
  - Egress
EOF

トラフィックがブロックされていることを確認します。テスト Pod から Web VM への接続を試みます。

oc exec -n default curl-test -- curl -s --connect-timeout 5 http://<web-vm-ip>:80
想定される出力
command terminated with exit code 28

終了コード 28 は接続がタイムアウトしたことを意味します。OVN-Kubernetes は TCP RST を送信するのではなく、ポリシーに違反するパケットをサイレントにドロップするため、curl は --connect-timeout が切れるまで待機します。

ステップ 4: DNS Egress の許可

すべて拒否 (deny-all) ポリシーが適用されている場合、DNS 解決もブロックされます。名前解決が引き続き機能するように、すべての Pod がクラスター DNS サービスに到達できるようにします。

allow-dns-egress.yaml のダウンロード

oc apply -f - <<EOF
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
 name: allow-dns-egress
 namespace: netpol-demo
spec:
 podSelector: {}
 policyTypes:
  - Egress
 egress:
  - to:
    - namespaceSelector:
      matchLabels:
       kubernetes.io/metadata.name: openshift-dns
   ports:
    - protocol: UDP
     port: 5353
    - protocol: TCP
     port: 5353
EOF

ステップ 5: Web VM への HTTP Ingress の許可

任意の送信元から TCP ポート 80 で Web VM への ingress トラフィックを許可します。これは、フロントエンドを内部の利用者に公開するシナリオを想定しています。

allow-web-ingress.yaml のダウンロード

oc apply -f - <<EOF
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
 name: allow-web-ingress
 namespace: netpol-demo
spec:
 podSelector:
  matchLabels:
   app: web
 policyTypes:
  - Ingress
 ingress:
  - ports:
    - protocol: TCP
     port: 80
EOF

テスト Pod から Web VM のポート 80 にアクセスできるようになったことを確認します。

oc exec -n default curl-test -- curl -s --connect-timeout 5 http://<web-vm-ip>:80

Nginx のウェルカムページが再度表示され、Ingress 許可ルールが機能していることが確認できます。

ステップ 6: Web VM からデータベース VM への通信を許可する

一般的なアーキテクチャーでは、フロントエンドからバックエンドのデータベースへのアクセスが必要です。Web VM からデータベースポートへの Egress を許可するポリシーと、app: web ラベルを持つ Pod からデータベース VM への Ingress のみを許可するポリシーの 2 つを作成します。

allow-web-to-db-egress.yaml をダウンロード

oc apply -f - <<EOF
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
 name: allow-web-to-db-egress
 namespace: netpol-demo
spec:
 podSelector:
  matchLabels:
   app: web
 policyTypes:
  - Egress
 egress:
  - to:
    - podSelector:
      matchLabels:
       app: database
   ports:
    - protocol: TCP
     port: 5432
EOF

allow-db-from-web.yaml をダウンロード

oc apply -f - <<EOF
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
 name: allow-db-from-web
 namespace: netpol-demo
spec:
 podSelector:
  matchLabels:
   app: database
 policyTypes:
  - Ingress
 ingress:
  - from:
    - podSelector:
      matchLabels:
       app: web
   ports:
    - protocol: TCP
     port: 5432
EOF

テスト Pod (app: web ラベルを持たない Pod) がデータベースにアクセスできないことを確認します (接続がタイムアウトするはずです)。

oc exec -n default curl-test -- curl -s --connect-timeout 5 http://<db-vm-ip>:5432

<db-vm-ip> をステップ 2 のデータベース VM の IP に置き換えます。

想定される出力
command terminated with exit code 28

タイムアウトが発生することで、ポリシーによってデータベースへの不正なアクセスがブロックされていることが確認できます。

allow-db-from-web ポリシーが namespace 内のラベル app: web を持つ pod への ingress を制限しているため、データベースポートには web VM の virt-launcher pod からのみ到達可能です。

ステップ 7: アクティブなポリシーの表示

セキュリティポスチャーを確認するために、namespace 内のすべての NetworkPolicy リソースを一覧表示します。

oc get networkpolicy -n netpol-demo
想定される出力
NAME           POD-SELECTOR  AGE
allow-db-from-web    app=database  ...
allow-dns-egress     <none>     ...
allow-web-ingress    app=web    ...
allow-web-to-db-egress  app=web    ...
deny-all         <none>     ...

クラスター全体のガードレール用の AdminNetworkPolicy

NetworkPolicy は namespace スコープであり、アプリケーションチームによって管理されますが、クラスター管理者は AdminNetworkPolicy (ANP) を使用してオーバーライド不可能なルールを適用できます。OVN-Kubernetes は以下の順序でポリシーを評価します。

  1. AdminNetworkPolicy (最高優先度) — Allow または Deny ルールが最終決定となります。Pass は次の階層に委任します。

  2. NetworkPolicy — 標準の namespace スコープのルール。

  3. BaselineAdminNetworkPolicy — NetworkPolicy に一致するものがない場合に適用されるクラスター全体のフォールバック。

次の ANP の例は、OpenShift Virtualization インフラストラクチャーの namespace を不正アクセスから保護します。

admin-network-policy.yaml のダウンロード

apiVersion: policy.networking.k8s.io/v1alpha1
kind: AdminNetworkPolicy
metadata:
 name: cluster-deny-to-virt-infra
spec:
 priority: 50
 subject:
  namespaces:
   matchExpressions:
    - key: kubernetes.io/metadata.name
     operator: NotIn
     values:
      - openshift-cnv
      - openshift-virtualization-os-images
 ingress:
  - name: deny-ingress-to-virt-infra
   action: Deny
   from:
    - namespaces:
      matchExpressions:
       - key: kubernetes.io/metadata.name
        operator: NotIn
        values:
         - openshift-cnv
         - openshift-virtualization-os-images
   ports:
    - portRange:
      start: 1
      end: 65535
      protocol: TCP
AdminNetworkPolicy は v1alpha1 API バージョンです。この API は安定しており、OpenShift 4.14 以降の OVN-Kubernetes クラスターでデフォルトで有効になっていますが、v1 に達する前に変更される可能性があります。

重要な考慮事項

セカンダリーネットワーク

NetworkPolicy は、プライマリー Pod ネットワーク (デフォルトのクラスターネットワークまたは Primary UDN) 上のトラフィックにのみ適用されます。NetworkAttachmentDefinition、localnet、Linux ブリッジインターフェース経由で接続されたセカンダリーネットワーク上のトラフィックは、NetworkPolicy によって管理されません。セカンダリーネットワーク上のトラフィックを制御するには、VM ゲスト内のファイアウォールルールまたは外部ネットワークインフラストラクチャーの制御を使用してください。

ライブマイグレーション

ライブマイグレーション中、VM の virt-launcher Pod はターゲットノード上に再作成されます。新しい Pod は spec.template.metadata.labels から同じラベルを継承するため、既存の NetworkPolicy ルールは変更なしで引き続き適用されます。マイグレーション自体は、namespace スコープの NetworkPolicy の影響を受けない内部 KubeVirt 通信チャネルを使用します。

Masquerade vs Bridge Binding

masquerade interface binding (Pod ネットワークのデフォルト) を使用する場合、VM ゲストと Pod ネットワーク間のトラフィックは NAT されます。NetworkPolicy は virt-launcher Pod の IP を送信元/送信先として認識します。bridge binding を使用すると、VM は Pod IP を直接取得します。どちらの場合も、ポリシーは virt-launcher Pod をターゲットにします。

トラブルシューティング

ポリシーが有効にならない

virt-launcher Pod のラベルがポリシーセレクターと一致していることを確認します。

oc get pods -n netpol-demo --show-labels

VM が metadata.labels だけでなく、spec.template.metadata.labels にもラベルを定義していることを確認します。

Deny-All の適用後に DNS 解決が機能しなくなる

すべて拒否する egress ポリシーを適用し、DNS の許可を忘れた場合、すべての名前解決が失敗します。ステップ 4 の DNS egress ポリシーを適用してください。

すべて拒否した後にトラフィックが引き続き流れる場合

policyTypes に Ingress のみを指定した場合、egress は制限されません (逆も同様です)。双方向をブロックするには、policyTypes に Ingress と Egress の両方を含めます。

クリーンアップ

テスト Pod と namespace を削除します。

oc delete pod curl-test -n default
oc delete namespace netpol-demo
AdminNetworkPolicy の例を適用した場合は、クラスタースコープであるため別途削除してください。 
oc delete adminnetworkpolicy cluster-deny-to-virt-infra

まとめ

このチュートリアルでは、以下について学びました。

  • NetworkPolicy は、virt-launcher Pod に伝播される spec.template.metadata.labels のラベルを通じて VM ワークロードを選択します

  • すべて拒否 (deny-all) のベースラインにより、VM namespace にゼロトラスト分離が提供されます

  • きめ細かな Ingress および Egress ルールにより、VM 階層間の制御された通信が可能になります

  • すべて拒否のベースラインを使用する場合は、DNS Egress を明示的に許可する必要があります

  • AdminNetworkPolicy は、テナントユーザーがオーバーライドできないクラスター全体のガードレールを提供します

  • NetworkPolicy はプライマリーネットワークのトラフィックのみを制御します。セカンダリーネットワークインターフェースには個別の制御が必要です

  • Pod ラベルが保持されるため、ポリシーはライブマイグレーションをまたいで維持されます
