LVM Storage Operator のインストール

概要

本チュートリアルでは、OpenShift ノード上の未使用のローカルディスクを使用するために、LVM Storage Operator をインストールおよび設定する方法を解説します。LVM Operator は、Logical Volume Manager (LVM) を使用した動的なストレージプロビジョニングを提供し、Single Node OpenShift (SNO) やローカルストレージを使用するベアメタルクラスターに最適です。

前提条件

  • OpenShift 4.18 以上

  • 利用可能なローカルディスク: クラスターノード上に少なくとも 1 台の未使用ディスクが必要です

  • クラスター管理者権限: Operator のインストールおよび StorageClass の作成に必要です

  • ディスク内の既存データ: Operator は forceWipeDevicesAndDestroyAllData パラメーターを使用してディスクを強制的に初期化できます

検証済みバージョン:

OpenShift 4.19, 4.20

重要な警告

forceWipeDevicesAndDestroyAllData: true パラメーターを使用すると、指定したディスク上のすべてのデータが完全に破棄されます。進める前に、必ずバックアップを取得し、正しいディスクデバイスパスを指定していることを確認してください。

ステップ 1: 利用可能なディスクの特定

LVM Operator を設定する前に、ストレージに使用するディスクを特定します。

# ノード名を取得
oc get nodes

# ノード上のすべてのブロックデバイスを一覧表示
oc debug node/<node-name> -- chroot /host lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINT,MODEL

出力例:

NAME    SIZE TYPE FSTYPE      MOUNTPOINT MODEL
sda   558.4G disk LVM2_member            PERC H730 Adp
sdc   558.4G disk                        PERC H730 Adp
|-sdc1   1M part
|-sdc2 127M part vfat
|-sdc3 384M part ext4        /boot
`-sdc4 557.9G part xfs        /sysroot

この例では以下のようになっています。

  • sda - 既存の LVM データがある空きディスク (これがターゲットになります)

  • sdc - OS パーティションがあるシステムディスク (使用しないでください)

既存の LVM 使用状況を確認します。

oc debug node/<node-name> -- chroot /host pvs

出力例:

PV         VG  Fmt  Attr PSize   PFree
/dev/sda   vg1 lvm2 a--  558.37g <55.84g

これは、/dev/sda に既存の LVM 設定があり、forceWipeDevicesAndDestroyAllData: true を使用すると消去されることを示しています。

永続的な識別のためにディスクデバイスパスを取得します。

oc debug node/<node-name> -- chroot /host ls -la /dev/disk/by-path/ | grep -E "pci.*scsi"

出力例:

lrwxrwxrwx. 1 root root 9 Oct 6 13:30 pci-0000:03:00.0-scsi-0:2:1:0 -> ../../sda

永続パス /dev/disk/by-path/pci-0000:03:00.0-scsi-0:2:1:0 は /dev/sda を指しています。

ステップ 2: LVM Storage Operator のインストール

namespace を作成し、LVM Storage Operator をインストールします。

LVM Operator 用の namespace を作成します。

lvm-namespace.yaml をダウンロード

oc apply -f - <<EOF
apiVersion: v1
kind: Namespace
metadata:
  name: openshift-lvm-storage
EOF

OperatorGroup を作成します。

lvm-operatorgroup.yaml をダウンロード

oc apply -f - <<EOF
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: openshift-lvm-storage-operatorgroup
  namespace: openshift-lvm-storage
spec:
  targetNamespaces:
  - openshift-lvm-storage
EOF

Operator をインストールするための Subscription を作成します。

lvm-subscription.yaml をダウンロード

oc apply -f - <<EOF
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: lvms-operator
  namespace: openshift-lvm-storage
spec:
  channel: stable-4.20
  name: lvms-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
  installPlanApproval: Automatic
EOF

Operator のインストールを確認します。

# Operator がインストールされるまで待機 (2〜3 分かかる場合があります)
oc get csv -n openshift-lvm-storage

# Operator Pod が Running であることを確認
oc get pods -n openshift-lvm-storage

想定される出力 (Operator インストール後、LVMCluster 作成前):

NAME                             READY   STATUS    RESTARTS   AGE
lvms-operator-864b6975bb-kxt4t   1/1     Running   0          2m
この段階では lvms-operator pod のみが表示されるはずです。vg-manager pod は、ステップ 3 で LVMCluster リソースを作成した後に自動的に作成されます。

想定される出力 (ステップ 3 で LVMCluster を作成した後):

NAME                                  READY   STATUS    RESTARTS   AGE
lvms-operator-864b6975bb-kxt4t        1/1     Running   0          5m
vg-manager-xxxxx                      1/1     Running   0          1m

ステップ 3: LVMCluster 設定の作成

LVM ストレージバックエンドを設定するために LVMCluster リソースを作成します。ここで、どのディスクを使用するか、既存データを強制的に消去するかどうかを指定します。

既存データがあるディスクの設定

ディスクに既存のデータやパーティションがある場合 (例の sda のように)、forceWipeDevicesAndDestroyAllData: true を使用します。

forceWipeDevicesAndDestroyAllData: true を使用すると、指定したディスク上のすべてのデータが完全に破棄されます。進める前に、必ずバックアップを取得し、正しいディスクデバイスパスを指定していることを確認してください。

lvmcluster-with-wipe.yaml をダウンロード

oc apply -f - <<EOF
apiVersion: lvm.topolvm.io/v1alpha1
kind: LVMCluster
metadata:
  name: lvmcluster
  namespace: openshift-lvm-storage
spec:
  storage:
    deviceClasses:
    - name: vg1
      default: true
      thinPoolConfig:
        name: thin-pool-1
        sizePercent: 90
        overprovisionRatio: 10
      nodeSelector:
        nodeSelectorTerms:
        - matchExpressions:
          - key: node-role.kubernetes.io/worker
            operator: In
            values:
            - ""
      deviceSelector:
        paths:
        - /dev/sda
        forceWipeDevicesAndDestroyAllData: true
EOF

クリーンなディスク (新規ディスク) の設定

ディスクがクリーンで、既存のデータやパーティションがない場合:

lvmcluster-clean-disk.yaml をダウンロード

oc apply -f - <<EOF
apiVersion: lvm.topolvm.io/v1alpha1
kind: LVMCluster
metadata:
  name: lvmcluster
  namespace: openshift-lvm-storage
spec:
  storage:
    deviceClasses:
    - name: vg1
      default: true
      thinPoolConfig:
        name: thin-pool-1
        sizePercent: 90
        overprovisionRatio: 10
      nodeSelector:
        nodeSelectorTerms:
        - matchExpressions:
          - key: node-role.kubernetes.io/worker
            operator: In
            values:
            - ""
      deviceSelector:
        paths:
        - /dev/sda
EOF

設定パラメーターの解説

  • name: vg1: ボリュームグループ名 (ディスク上に作成されます)

  • default: true: deviceClass をクラスターのデフォルトに設定

    • 目的: デフォルトの deviceClass がないという警告を防止

    • 効果: PVC で明示的に指定しなくても、生成された StorageClass を利用可能に設定

    • 注意: 複数の deviceClass を持つ場合、デフォルトに設定できるのは 1 つのみ

  • thinPoolConfig: 効率的なストレージ使用のためのシンプロビジョニングを設定

    • sizePercent: 90: thin pool にディスク領域の 90%を使用

    • overprovisionRatio: 10: 10 倍のオーバープロビジョニングを許可 (物理的に利用可能な容量以上のストレージをプロビジョニング)

  • nodeSelector: 設定するノード (この例では Worker Node)

  • deviceSelector.paths: 使用する特定のディスクデバイスパス

    • /dev/sda、/dev/disk/by-path/…​、/dev/disk/by-id/…​ などが使用可能

  • forceWipeDevicesAndDestroyAllData: true: 重要なパラメータ

    • 目的: ディスク上のすべての既存データとパーティションを消去

    • 使用条件: ディスクに既存のファイルシステム、パーティション、LVM 設定がある場合

    • 効果: 完全なデータ破棄 - 回復は不可

    • 省略する場合: ディスクが既に clean/empty である場合

ステップ 4: LVMCluster ステータスの確認

LVMCluster の準備ができているか、簡単なヘルスチェックを実行します。

# LVMCluster ステータスを確認
oc get lvmcluster -n openshift-lvm-storage

# volume group が作成されたことを確認
oc debug node/<node-name> -- chroot /host vgs

# thin pool が作成されたことを確認
oc debug node/<node-name> -- chroot /host lvs

健全な状態の出力例:

  • LVMCluster が STATUS: Ready と表示される

  • VG vg1 が適切なサイズで表示される

  • シンプール thin-pool-1 がアクティブであり、データ/メタデータの使用量が少ない

詳細な確認手順、想定される出力、トラブルシューティングについては、LVM Storage トラブルシューティングガイドを参照してください。

ステップ 5: デフォルト StorageClass の設定

LVM Operator は lvms-vg1 という名前の StorageClass を自動的に作成しますが、デフォルトには設定しません。OpenShift Virtualization が VM ディスクおよび DataVolume 用のストレージを自動的にプロビジョニングするためには、lvms-vg1 をデフォルト StorageClass に設定することが不可欠です。

StorageClass が存在することの確認

oc get storageclass

想定される出力:

NAME       PROVISIONER   RECLAIMPOLICY   VOLUMEBINDINGMODE      ALLOWVOLUMEEXPANSION   AGE
lvms-vg1   topolvm.io    Delete          WaitForFirstConsumer   true                   5m
(default) アノテーションが表示されていません。この StorageClass はまだデフォルトではありません。

デフォルト StorageClass の設定

LVM StorageClass をクラスターのデフォルトに設定します。

oc patch storageclass lvms-vg1 -p '{"metadata": {"annotations":{"storageclass.kubernetes.io/is-default-class":"true"}}}'

デフォルトステータスの確認

oc describe sc | grep IsDefaultClass

デフォルト設定後の想定される出力:

NAME                 PROVISIONER   RECLAIMPOLICY   VOLUMEBINDINGMODE      ALLOWVOLUMEEXPANSION   AGE
lvms-vg1 (default)   topolvm.io    Delete          WaitForFirstConsumer   true                   6m

(default) アノテーションにより、これがデフォルト StorageClass であることが確認できます。

OpenShift Virtualization にとって重要な理由

デフォルト StorageClass の設定は、OpenShift Virtualization にとって非常に重要です。

DataSource OS イメージはデフォルトストレージが必要

OpenShift Virtualization の DataSource OS イメージ (Fedora、RHEL、CentOS Stream、Windows) は、ブートソースボリュームを自動的に作成するためにデフォルト StorageClass を必要とします。

# 利用可能な OS イメージを確認
oc get datasources -n openshift-virtualization-os-images

デフォルト StorageClass がない場合、これらの DataSource は保留状態のままとなり、VM 作成に使用できません。

VM 用の自動 PVC 作成

dataVolumeTemplates を使用して VM を作成する際、storageClassName が指定されていない場合は、デフォルト StorageClass が使用されます。

dataVolumeTemplates:
- metadata:
    name: fedora-volume
  spec:
    pvc:
      accessModes:
      - ReadWriteOnce
      resources:
        requests:
          storage: 30Gi
    sourceRef:
      kind: DataSource
      name: fedora
      namespace: openshift-virtualization-os-images

これにより、明示的に指定しなくても、デフォルト StorageClass (lvms-vg1) が自動的に使用されます。

VM 作成の簡素化

デフォルト StorageClass があれば、以下のメリットがあります。

  • VM テンプレートがそのまま動作する

  • DataSource のクローンが自動的に行われる

  • すべての PVC に storageClassName を指定する必要がない

  • クラスター全体で一貫したストレージプロビジョニングが可能

ブートソースの準備

デフォルト StorageClass が利用可能な場合、OpenShift Virtualization Operator は一般的な OS イメージのブートソースを自動的に準備できます。

# ブートソースの準備状況を確認
oc get DataImportCron -n openshift-virtualization-os-images

代替手段：VM 内での StorageClass の明示的指定

デフォルト StorageClass を設定しない場合は、すべての VM 定義で明示的に指定する必要があります。

dataVolumeTemplates:
- metadata:
    name: fedora-volume
  spec:
    pvc:
      accessModes:
      - ReadWriteOnce
      resources:
        requests:
          storage: 30Gi
      storageClassName: lvms-vg1  # Must be explicit
    sourceRef:
      kind: DataSource
      name: fedora
      namespace: openshift-virtualization-os-images
運用を簡素化し、ブートソースの自動プロビジョニングを有効にするため、OpenShift Virtualization クラスターには必ずデフォルト StorageClass を設定してください。

ステップ 6: ストレージプロビジョニングのテスト

ストレージプロビジョニングが機能することを確認するために、テスト用の PVC を作成します。

test-pvc.yaml をダウンロード

oc apply -f - <<EOF
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: lvms-test-pvc
  namespace: default
spec:
  accessModes:
  - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi
  storageClassName: lvms-vg1
EOF

PVC を使用するためのテスト用 Pod を作成します。

test-pod.yaml をダウンロード

oc apply -f - <<EOF
apiVersion: v1
kind: Pod
metadata:
  name: lvms-test-pod
  namespace: default
spec:
  containers:
  - name: test
    image: registry.access.redhat.com/ubi9/ubi:latest
    command: ["sleep", "3600"]
    volumeMounts:
    - name: data
      mountPath: /data
  volumes:
  - name: data
    persistentVolumeClaim:
      claimName: lvms-test-pvc
EOF

PVC がバインドされていることを確認します。

oc get pvc lvms-test-pvc

# STATUS が "Bound" と表示されるはずです

Pod が実行中で、ストレージに書き込めることを確認します。

# Pod が起動するまで待機
oc wait --for=condition=Ready pod/lvms-test-pod --timeout=120s

# ボリュームへの書き込みをテスト
oc exec lvms-test-pod -- sh -c "echo 'LVM Storage Test' > /data/test.txt && cat /data/test.txt"

# 想定される出力: LVM Storage Test

テストリソースをクリーンアップします。

oc delete pod lvms-test-pod
oc delete pvc lvms-test-pvc

forceWipeDevicesAndDestroyAllData の理解

概要

forceWipeDevicesAndDestroyAllData: true パラメーターは以下の動作を行います。

  1. パーティションテーブルの削除: GPT、MBR、およびすべてのパーティション情報を消去します

  2. ファイルシステムの破壊: ext4、xfs、btrfs、およびその他のファイルシステムの署名を削除します

  3. LVM メタデータの消去: 既存の物理ボリューム、ボリュームグループ、論理ボリュームを削除します

  4. ディスク先頭のゼロ埋め: ディスクの最初の数メガバイトをゼロで埋め、クリーンな状態を確保します

  5. 再利用の強制: LVM Operator がディスクの所有権を取得できるようにします

いつ使用すべきか

forceWipeDevicesAndDestroyAllData: true は以下の場合に使用してください。

  • ディスクに既存のパーティションやファイルシステムがある場合

  • ディスクが以前 LVM に使用されていた場合 (PV/VG/LV が存在する)

  • 破棄したいデータがディスクにある場合

  • 他の用途で使用されていたディスクを再利用する場合

以下の場合には使用しないでください。

  • ディスクが新品でフォーマットされていない場合

  • 使用すべきディスクが不明な場合 (事前に確認してください！)

  • ディスクに保持する必要があるデータが含まれている場合

使用前の安全確認

このパラメーターを有効にする前に、必ずディスクデバイスパスを確認してください。

# 1. ディスクパスを確認
oc debug node/<node-name> -- chroot /host lsblk -o NAME,SIZE,TYPE,MOUNTPOINT

# 2. ディスクがマウントされていないことを確認
oc debug node/<node-name> -- chroot /host mount | grep /dev/sda

# 3. システムディスクを使用していないことを再確認
oc debug node/<node-name> -- chroot /host df -h | grep sda

# 4. ディスクのシリアル番号を確認
oc debug node/<node-name> -- chroot /host lsblk -d -o NAME,SERIAL /dev/sda

まとめ

このチュートリアルでは、以下について学びました。

  • LVM ストレージのためにクラスターノード上の未使用の空きディスクを特定する方法

  • 既存データがあるディスク向けの forceWipeDevicesAndDestroyAllData パラメーターを含め、LVMCluster リソースを作成および設定する方法

  • PVC と Pod を使用してストレージプロビジョニングをテストし、LVMCluster の健全性を確認する方法
