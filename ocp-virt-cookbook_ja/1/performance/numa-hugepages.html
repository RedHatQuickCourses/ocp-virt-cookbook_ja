仮想マシンの NUMA トポロジーと Hugepages

概要

このチュートリアルでは、OpenShift Virtualization において、Hugepages を使用したメモリと NUMA トポロジーのパススルーを仮想マシン向けに設定する方法を説明します。デフォルトでは、VM のメモリは標準的な 4Ki ページを使用し、ゲスト OS はホストの NUMA レイアウトを認識できません。NFV/テレコム、HPC、リアルタイム処理、大規模メモリデータベースなどのパフォーマンスが重要なワークロードにおいて、このデフォルト設定は以下の 2 つの想定されるボトルネックを引き起こします。

  • TLB pressure: 16Gi のメモリを持ち、4Ki ページを使用する VM は、400 万以上のページテーブルエントリを必要とします。CPU の TLB (Translation Lookaside Buffer) はサイズが制限されているため、頻繁な TLB ミスが発生し、コストのかかるページテーブルウォークが強制されます。

  • Cross-NUMA memory latency: マルチソケットまたはマルチチップレットのホストでは、リモートの NUMA ノード上のメモリへのアクセスは、ローカルメモリへのアクセスよりも 1.5-3 倍低速になる可能性があります。NUMA を意識しない場合、ゲスト OS はメモリとスレッドを同一の物理 NUMA ノード上に配置できません。

Hugepages は、4Ki の代わりに 2Mi または 1Gi のページを使用することで TLB pressure を軽減します。NUMA パススルー (guestMappingPassthrough) は、ホストの物理 NUMA トポロジーをゲストに公開し、VM 内での NUMA を意識したスケジューリングを可能にします。専用 CPU 配置と併せて、これらの機能は決定論的で低レイテンシな VM パフォーマンスの基盤となります。

前提条件

  • OpenShift Virtualization Operator がインストールされた OpenShift 4.18 以上 (4.21 でテスト済み)

  • クラスター管理者アクセス権 (system:admin または同等の権限)

  • oc および virtctl CLI がインストールされていること

  • 複数の物理 CPU コア (推奨 8 以上) および Hugepages 予約のための十分な RAM を備えた Worker Node

  • CPU Manager static policy が有効になっていること (専用 CPU 配置を参照)

  • Kubernetes QoS クラスに関する知識 (VM Resource Limits と QoS の設定を参照)

Hugepages の理解

標準的な Linux のメモリ管理では 4Ki ページが使用されます。2Gi のメモリを持つ VM では、524,288 個の個別のページマッピングが必要です。各 TLB ミスは、数百ナノ秒にわたって CPU を停止させる可能性のあるマルチレベルのページテーブルウォークを引き起こします。

Hugepages は、より大きなページサイズを使用することでこのオーバーヘッドを回避します。

VM spec に memory.hugepages.pageSize が含まれている場合、KubeVirt はホストの事前割り当て済み Hugepages プールからすべてのゲストメモリを割り当てるように QEMU を設定します。このメモリは固定 (pinned) され、スワップされることはありません。

Hugepages はオーバーコミットできません。ホストは、VM がスケジュールされる NUMA ノード上に十分な空き Hugepages を持っている必要があります。そうでない場合、VM の起動は失敗します。NUMA パススルーを使用する場合、VM の CPU に割り当てられた特定の NUMA ノード上で Hugepages が利用可能である必要があります。NUMA ノードごとの分散と QEMU のオーバーヘッドを考慮し、すべての VM Memory requests の合計よりも多くの Hugepages を予約してください。

NUMA トポロジーの理解

NUMA (Non-Uniform Memory Access) は、各 CPU ソケット (またはチップレット) が独自のローカルメモリを持つハードウェアアーキテクチャです。ローカルメモリへのアクセスは高速ですが、リモートメモリへのアクセスは相互接続を経由するため低速になります。

一般的な 2 ソケットサーバーの場合:

NUMA Node 0: CPUs 0-19, 40-59   Local Memory: 128Gi
NUMA Node 1: CPUs 20-39, 60-79  Local Memory: 128Gi

NUMA を考慮していない場合、ゲスト OS は NUMA ノード 0 にマップされる vCPU 上でスレッドをスケジュールする一方で、メモリが NUMA ノード 1 に割り当てられる可能性があります。このようなノードをまたぐアクセスにより、すべてのメモリ操作に遅延が発生します。

KubeVirt の guestMappingPassthrough 戦略は、ホストの NUMA トポロジーをゲストにパススルーすることでこれを解決します。ゲストは (割り当てられた専用 CPU に基づいて) 物理ホストと同じ NUMA 構造を認識し、独自の NUMA を意識したスケジューリングの決定を行うことができます。

NUMA パススルーには以下の 3 つの前提条件が必要です。

  1. 専用 CPU 配置 (dedicatedCpuPlacement: true)

  2. ターゲットノード上に割り当てられた Hugepages

  3. KubeVirt CR で NUMA フィーチャーゲートが有効であること (OpenShift Virtualization 4.18 以降ではデフォルトで有効)

ステップ 1: ノードでの Hugepages の予約

連続した物理メモリを保証するために、Hugepages はブート時に事前割り当てする必要があります。OpenShift では、Node Tuning Operator が Tuned リソースを通じてカーネルブートパラメーターの挿入を処理します。

以下の Tuned プロファイルは、ブート時に各 Worker Node で 2Mi サイズのページを 1024 ページ (合計 2Gi) 予約します。

hugepages-tuned-boottime.yaml をダウンロード

oc apply -f - <<EOF
apiVersion: tuned.openshift.io/v1
kind: Tuned
metadata:
  name: hugepages
  namespace: openshift-cluster-node-tuning-operator
spec:
  profile:
  - data: |
      [main]
      summary=Boot time configuration for hugepages
      include=openshift-node
      [bootloader]
      cmdline_openshift_node_hugepages=hugepagesz=2M hugepages=1024
    name: openshift-node-hugepages
  recommend:
  - machineConfigLabels:
      machineconfiguration.openshift.io/role: "worker"
    priority: 20
    profile: openshift-node-hugepages
EOF
Single Node OpenShift (SNO) では、machineConfigLabels ロールの worker を master に置き換えてください。
priority の値は、同じノードに一致する Tuned プロファイル間で一意である必要があります。デフォルトの openshift-control-plane および openshift-node プロファイルは優先度 30 を使用します。Hugepages プロファイルを確実に適用させるには、20 のようなより小さい数値 (高い優先度) を使用してください。

Node Tuning Operator は、カーネルコマンドラインに hugepagesz=2M hugepages=1024 を追加する MachineConfig を生成します。その後、Machine Config Operator が各 Worker Node を再起動して変更を適用します。ロールアウトを監視します。

oc get mcp worker -w

UPDATED が True になり、MACHINECOUNT と READYMACHINECOUNT が等しくなるまで待ちます。

NAME     CONFIG                                             UPDATED   UPDATING   DEGRADED
worker   rendered-worker-xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx   True      False      False
これにより、対象の MachineConfigPool 内のすべてのノードでローリング再起動がトリガーされます。本番クラスターでは計画的に実施してください。

Hugepages 割り当ての確認

ロールアウト完了後、各ノードが期待どおりの Hugepages 容量を報告していることを確認します。

oc get node <node-name> -o jsonpath='{.status.allocatable.hugepages-2Mi}{"\n"}'

想定される出力:

2Gi

詳細を確認するには、ノードでデバッグセッションを開き、/proc/meminfo を調査します。

oc debug node/<node-name>

デバッグシェル内:

chroot /host grep -i hugepages /proc/meminfo

想定される出力:

AnonHugePages:         0 kB
ShmemHugePages:        0 kB
FileHugePages:         0 kB
HugePages_Total:    1024
HugePages_Free:     1024
HugePages_Rsvd:        0
HugePages_Surp:        0
Hugepagesize:       2048 kB

HugePages_Total は設定した数 (1024) と一致するはずです。HugePages_Free は現在割り当て可能な数を示します。

デバッグシェルを終了します。

exit

ステップ 2: ノードでの NUMA トポロジーの確認

NUMA を意識した VM をデプロイする前に、Worker Node の物理 NUMA レイアウトを調査します。以下のツールは、パッケージを追加インストールすることなく、すべての RHCOS ノードで使用可能です。

デバッグセッションを開きます。

oc debug node/<node-name>

システム上の NUMA ノードをリストアップします。

chroot /host ls /sys/devices/system/node/

2 ソケットサーバーでの出力例:

node0  node1

各 NUMA ノードに属する CPU を確認します。

chroot /host cat /sys/devices/system/node/node0/cpulist
0-9,40-49
chroot /host cat /sys/devices/system/node/node1/cpulist
20-29,60-69

NUMA ノードごとのメモリ情報を調査します。

chroot /host cat /sys/devices/system/node/node0/meminfo

出力例 (短縮版) :

Node 0 MemTotal:       131072000 kB
Node 0 MemFree:        125000000 kB
Node 0 HugePages_Total:      512
Node 0 HugePages_Free:       512

NUMA ノード数と CPU-to-node マッピングを含む概要には lscpu を使用します。

chroot /host lscpu | grep -i numa

出力例:

NUMA node(s):          2
NUMA node0 CPU(s):     0-9,40-49
NUMA node1 CPU(s):     20-29,60-69
シングルソケットシステムや Single Node OpenShift では、NUMA ノードが 1 つしか表示されない場合があります。NUMA パススルーは機能しますが、すべての CPU とメモリがローカルであるため、ノード間最適化のメリットはありません。

デバッグシェルを終了します。

exit

ステップ 3: Namespace の作成

oc create namespace numa-hugepages-demo

ステップ 4: Hugepages を使用した VM のデプロイ

この最初の VM は、NUMA パススルーを使用せず、専用 CPU 配置と Hugepages メモリを使用します。この設定により、TLB オーバーヘッドが排除され、VM マニフェストが簡素化されます。

重要なフィールド:

  • dedicatedCpuPlacement: true — vCPU を物理 CPU に固定します (KubeVirt における Hugepages の前提条件) 。

  • memory.hugepages.pageSize: 2Mi — 2Mi Hugepages プールからゲストメモリを割り当てます。

  • メモリの requests と limits は等しくする必要があります (Guaranteed QoS) 。

この例の cloud-init パスワードはデモンストレーション目的専用です。本番環境では SSH 鍵認証または強力で一意なパスワードを使用してください。

vm-hugepages.yaml をダウンロード

oc apply -f - <<EOF
apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: vm-hugepages
  namespace: numa-hugepages-demo
spec:
  runStrategy: Always
  template:
    metadata:
      labels:
        kubevirt.io/domain: vm-hugepages
    spec:
      nodeSelector:
        cpumanager: "true"
      domain:
        cpu:
          sockets: 2
          cores: 1
          threads: 1
          dedicatedCpuPlacement: true
        memory:
          hugepages:
            pageSize: 2Mi
        resources:
          requests:
            memory: 2Gi
          limits:
            memory: 2Gi
        devices:
          disks:
          - name: rootdisk
            disk:
              bus: virtio
          - name: cloudinitdisk
            disk:
              bus: virtio
          interfaces:
          - name: default
            masquerade: {}
      networks:
      - name: default
        pod: {}
      volumes:
      - name: rootdisk
        containerDisk:
          image: quay.io/containerdisks/fedora:latest
      - name: cloudinitdisk
        cloudInitNoCloud:
          userData: |
            #cloud-config
            password: redhat
            chpasswd:
              expire: false
EOF

VM が Running 状態になるまで待ちます。

oc get vm vm-hugepages -n numa-hugepages-demo -w

想定される出力:

NAME           AGE   STATUS    READY
vm-hugepages   45s   Running   True

ステップ 5: Hugepages 使用の確認

ホスト側の検証

VM が実行されているノードを見つけます。

oc get vmi vm-hugepages -n numa-hugepages-demo -o wide

そのノードでデバッグセッションを開きます。

oc debug node/<node-name>

Hugepages の消費量を確認します。HugePages_Free 数は、VM によって消費された分だけ HugePages_Total よりも少なくなっているはずです。

chroot /host grep -i hugepages /proc/meminfo

2Mi ページを使用する 2Gi の VM の場合、1024 ページが消費されるため、HugePages_Free は元の値から約 1024 減少するはずです。

デバッグシェルを終了します。

exit

ゲスト側の検証

VM コンソールに接続します。

virtctl console vm-hugepages -n numa-hugepages-demo

ユーザー名 fedora、パスワード redhat でログインします。ゲストが使用可能な合計メモリを確認します。

free -h

ゲストはメモリを標準的な RAM として認識します。Hugepages は QEMU レベルではゲストから透過的であり、ゲスト OS 自身が受け取ったメモリから独自の Hugepages を個別に設定できます。

Ctrl+] を押してコンソールから切断します。

Hugepages VM の停止

次に進む前に、最初の VM を停止して Hugepages 割り当てを解放します。次のステップの NUMA パススルー VM は同じプールから Hugepages を必要とするため、ノードによっては両方の VM を同時に実行できない可能性があります。

virtctl stop vm-hugepages -n numa-hugepages-demo

VM が停止したことを確認します。

oc get vm vm-hugepages -n numa-hugepages-demo

想定される出力:

NAME           AGE    STATUS    READY
vm-hugepages   5m     Stopped   False

ステップ 6: NUMA パススルーを使用した VM のデプロイ

この VM は、専用 CPU、Hugepages、NUMA トポロジーパススルーという 3 つのパフォーマンス機能をすべて組み合わせます。追加された重要な設定は numa.guestMappingPassthrough: {} であり、これにより KubeVirt にホストの NUMA トポロジーをゲストにマップするよう指示します。

NUMA パススルーのための追加設定:

  • isolateEmulatorThread: true — QEMU エミュレータスレッドが vCPU と競合するのを防ぎます。

  • autoattachMemBalloon: false — メモリバルーンデバイスを無効化します。このデバイスは、確定的なメモリ割り当てと互換性がありません。

vm-numa-hugepages.yaml をダウンロード

oc apply -f - <<EOF
apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: vm-numa-hugepages
  namespace: numa-hugepages-demo
spec:
  runStrategy: Always
  template:
    metadata:
      labels:
        kubevirt.io/domain: vm-numa-hugepages
    spec:
      nodeSelector:
        cpumanager: "true"
      domain:
        cpu:
          sockets: 1
          cores: 2
          threads: 1
          dedicatedCpuPlacement: true
          isolateEmulatorThread: true
          numa:
            guestMappingPassthrough: {}
        memory:
          hugepages:
            pageSize: 2Mi
        resources:
          requests:
            memory: 1Gi
          limits:
            memory: 1Gi
        devices:
          autoattachMemBalloon: false
          disks:
          - name: rootdisk
            disk:
              bus: virtio
          - name: cloudinitdisk
            disk:
              bus: virtio
          interfaces:
          - name: default
            masquerade: {}
      networks:
      - name: default
        pod: {}
      volumes:
      - name: rootdisk
        containerDisk:
          image: quay.io/containerdisks/fedora:latest
      - name: cloudinitdisk
        cloudInitNoCloud:
          userData: |
            #cloud-config
            password: redhat
            chpasswd:
              expire: false
EOF

VM が Running 状態になるまで待ちます。

oc get vm vm-numa-hugepages -n numa-hugepages-demo -w

想定される出力:

NAME                AGE   STATUS    READY
vm-numa-hugepages   60s   Running   True

ステップ 7: VM 内での NUMA トポロジーの確認

VMI での NUMA 設定の確認

まず、VMI で NUMA パススルーが設定されていることを確認します。

oc get vmi vm-numa-hugepages -n numa-hugepages-demo -o jsonpath='{.spec.domain.cpu.numa}{"\n"}'

想定される出力:

{"guestMappingPassthrough":{}}

ゲスト側の NUMA 検証

VM コンソールに接続します。

virtctl console vm-numa-hugepages -n numa-hugepages-demo

ユーザー名 fedora、パスワード redhat でログインします。ゲストから見える NUMA トポロジーを確認します。

lscpu | grep -i numa

複数の NUMA ノードを持つホストでは、物理 CPU のトポロジーと一致する複数の NUMA ノードが報告される可能性があります。単一 NUMA ノードのホストでは、ゲストは 1 つの NUMA ノードを報告します。

詳細な CPU トポロジーを確認します。

lscpu

ゲストから見える NUMA ノードをリストアップします。

ls /sys/devices/system/node/

出力例:

node0

各 NUMA ノードに割り当てられた CPU を確認します。

cat /sys/devices/system/node/node0/cpulist

出力例:

0-1

ノードごとのメモリを調査します。

cat /sys/devices/system/node/node0/meminfo | head -5

出力例:

Node 0 MemTotal:        1048576 kB
Node 0 MemFree:          800000 kB
Node 0 MemUsed:          248576 kB
Node 0 Active:           120000 kB
Node 0 Inactive:          80000 kB

ゲストから見える NUMA トポロジーは、ホストから受け取った専用 CPU の物理トポロジーを反映しています。

Ctrl+] を押してコンソールから切断します。

ホスト側の NUMA 検証

ノードを見つけ、CPU Manager の状態を通じて CPU pinning を確認します。

oc get vmi vm-numa-hugepages -n numa-hugepages-demo -o wide
oc debug node/<node-name>
chroot /host cat /var/lib/kubelet/cpu_manager_state

entries マップには、専用 CPU ID を持つ compute コンテナが表示されるはずです。isolateEmulatorThread: true を使用すると、さらに 1 つの CPU が予約されます (合計 3 つ：vCPU 2 つ + エミュレータスレッド 1 つ) 。

デバッグシェルを終了します。

2Mi と 1Gi Hugepages の選択

検討事項 2Mi ページ 1Gi ページ

エントリあたりの TLB カバレッジ

2Mi

1Gi (512 倍)

事前割り当ての粒度

細かい (例: 100Mi 単位)

粗い (最低 1Gi)

メモリの浪費

最小限

メモリが 1Gi の倍数でない場合、VM ごとに最大 1Gi が未使用

ブート時の予約

メモリを枯渇させずに数百ページを予約可能

大きな単位でメモリを確保するため、Hugepages を使用しない通常のワークロードが利用できるページ数が減少

一般的なユースケース

ほとんどの VM、適度な TLB の改善

非常に大きなメモリを持つ VM (64Gi 以上)、データベース、最高の TLB 効率

1Gi ページを使用するには、Tuned プロファイルを変更します。

[bootloader]
cmdline_openshift_node_hugepages=hugepagesz=1G hugepages=16

そして VM spec を更新します。

memory:
  hugepages:
    pageSize: 1Gi
resources:
  requests:
    memory: 16Gi
  limits:
    memory: 16Gi
Memory requests は Hugepages サイズで均等に割り切れる必要があります。1Gi の Hugepages で 1.5Gi のメモリを要求することはできません。

トラブルシューティング

VM の起動失敗：Hugepages 不足

VM が Scheduling または Pending 状態のままになる場合は、VMI イベントを確認します。

oc describe vmi vm-hugepages -n numa-hugepages-demo

Hugepages 不足やスケジューリング失敗に関するイベントを探します。ターゲットノードで使用可能な Hugepages を確認します。

oc get node <node-name> -o jsonpath='{.status.allocatable.hugepages-2Mi}{"\n"}'

割り当て可能な値が VM の Memory requests よりも小さい場合は、VM のメモリを減らすか、ノードの Hugepages 予約を増やしてください。

NUMA パススルー VM の失敗：「cannot bind memory to host NUMA nodes」

このエラーは、virt-launcher Pod が特定の NUMA ノードにメモリをバインドできない場合に発生します。考えられる原因:

  • ターゲット NUMA ノード上の Hugepages 不足: Hugepages はホスト全体では利用可能でも、VM の CPU が割り当てられている特定の NUMA ノードでは不足している可能性があります。Hugepages 割り当てを再調整するか、合計予約量を増やしてください。

  • Topology Manager が一致していない: kubelet の Topology Manager ポリシーが none に設定されている場合、CPU とメモリの割り当てが NUMA ノードをまたぐ可能性があります。厳密な NUMA 整合性を必要とするワークロードの場合は、Topology Manager ポリシーを single-numa-node または restricted に設定することを検討してください。

ゲストが複数の NUMA ノードを認識しない

ホストが複数持っているにもかかわらず、ゲストが 1 つの NUMA ノードしか報告しない場合:

  • VMI spec で guestMappingPassthrough が設定されていることを確認します。

  • VM の専用 CPU が複数の物理 NUMA ノードにまたがっていることを確認します。割り当てられた CPU がすべて単一の NUMA ノード上にある場合、ゲストが 1 つしかノードを認識しないのは正常です。

  • NUMA ノードの境界を越えてより多くの物理 CPU を使用するように、VM の vCPU 数を増やしてください。

MachineConfigPool が Updating のまま停止

Tuned プロファイルの適用後、MachineConfigPool のロールアウトが完了しない場合:

oc get mcp worker
oc describe mcp worker

劣化しているノードがないか確認し、影響を受けているノードの machine-config-daemon ログを調査します。

oc logs -n openshift-machine-config-operator -l k8s-app=machine-config-daemon --tail=50

クリーンアップ

VM と Namespace を削除します。

oc delete namespace numa-hugepages-demo

Hugepages Tuned プロファイルを削除し、カーネルブートパラメーターを元に戻します。

oc delete tuned hugepages -n openshift-cluster-node-tuning-operator
Tuned プロファイルを削除すると MachineConfig の更新がトリガーされ、Hugepages カーネルパラメーターを削除するために影響を受けるノードのローリング再起動が行われます。ロールアウトが完了するまで MachineConfigPool を監視してください。

まとめ

このチュートリアルでは、以下の方法を学びました。

  • Node Tuning Operator を使用して、OpenShift ノードでブート時に Hugepages を予約する

  • Kubernetes API とノードの /proc/meminfo の両方から Hugepages の割り当てを確認する

  • /sys/devices/system/node/ および lscpu を使用してホストの NUMA トポロジーを調査する

  • TLB オーバーヘッドを軽減するために、Hugepages メモリを持つ VM をデプロイする

  • NUMA を意識したゲストスケジューリングのために、NUMA パススルー (guestMappingPassthrough) を持つ VM をデプロイする

  • ゲスト内から NUMA トポロジーを検証する

  • ワークロードの要件に基づいて 2Mi と 1Gi の Hugepages サイズを選択する
