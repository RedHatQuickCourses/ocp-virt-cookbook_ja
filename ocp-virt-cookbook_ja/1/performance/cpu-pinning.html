仮想マシン向けの専用 CPU 配置

概要

本チュートリアルでは、OpenShift Virtualization において仮想マシン向けの専用 CPU 配置を設定する方法を解説します。デフォルトでは、仮想マシンの vCPU はホスト上の他のワークロードと物理 CPU の処理時間を共有します。専用 CPU 配置を使用すると、各 vCPU が特定の物理 CPU に固定 (pinning) されるため、CPU スティールが排除され、スケジューラーによる割り当ての揺らぎ (jitter) を低減します。

この設定は、予測可能な低遅延が求められる NFV/通信アプリケーション、リアルタイム処理、HPC、遅延に敏感なデータベースなどのワークロードに不可欠です。

前提条件

  • OpenShift Virtualization Operator がインストールされた OpenShift 4.18 以上 (4.21 で検証済み)

  • クラスター管理者アクセス権 (system:admin または同等の権限)

  • oc および virtctl CLI がインストール済みであること

  • 十分な物理 CPU コアを持つ Worker Node (少なくとも 4 コア推奨)

  • Kubernetes の QoS クラスに関する知識 (VM Resource Limits と QoS の設定を参照)

専用 CPU 配置の理解

OpenShift は Kubernetes の CPU Manager を使用して、Pod に排他的な物理 CPU を割り当てます。CPU Manager が static ポリシーで実行されている場合、Pod のコンテナをホストの専用 CPU に固定し、他のワークロードがそれらの CPU を使用できないように制限できます。

KubeVirt の dedicatedCpuPlacement フィールドは、CPU Manager に対して virt-launcher Pod の vCPU を物理 CPU に固定するように指示します。Pod が実行されると、各ゲスト vCPU は予約された物理 CPU に直接マッピングされます。

専用配置が機能するには、以下の 2 つの要件を満たす必要があります。

  • ノードの CPU Manager が static ポリシーで実行されていること。

  • VM の QoS が Guaranteed であること：CPU およびメモリの requests が limits と一致しており、かつ CPU 数が整数である必要があります。

モード vCPU の動作 ユースケース

デフォルト (shared)

vCPU が他のすべてのワークロードと物理 CPU の処理時間を共有する

汎用 VM、開発環境、遅延が重要ではないワークロード

専用 (dedicatedCpuPlacement: true)

vCPU が予約済み物理 CPU に固定され、CPU スティールが発生しない

NFV/通信、リアルタイム処理、HPC、遅延に敏感なデータベース

ステップ 1: CPU Manager の Static Policy を有効にする

CPU Manager のポリシーは、KubeletConfig リソースを使用して MachineConfigPool ごとに設定します。

まず、この設定の対象を識別するために、Worker の MachineConfigPool にラベルを追加します。

oc label machineconfigpool worker custom-kubelet=cpumanager-enabled
シングルノード OpenShift (SNO) クラスターの場合、ノードは worker ではなく master MachineConfigPool に属します。上記のコマンドおよび後述する KubeletConfig の machineConfigPoolSelector において、worker を master に置き換えてください。

kubeletconfig-static-policy.yaml をダウンロード

KubeletConfig を適用して、Static CPU manager policy を有効にします。

oc apply -f - <<EOF
apiVersion: machineconfiguration.openshift.io/v1
kind: KubeletConfig
metadata:
  name: cpumanager-enabled
spec:
  machineConfigPoolSelector:
    matchLabels:
      custom-kubelet: cpumanager-enabled
  kubeletConfig:
    cpuManagerPolicy: static
    cpuManagerReconcilePeriod: 5s
EOF

Machine Config Operator が、ターゲットプール内の全ノードに新しい kubelet 設定を適用します。ロールアウトを監視します。

oc get mcp worker -w

UPDATING 列が False に戻り、READYMACHINECOUNT が MACHINECOUNT と一致するまで待ちます。

NAME     CONFIG                                             UPDATED   UPDATING   DEGRADED
worker   rendered-worker-xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx   True      False      False

CPU Manager Policy の確認

各 Worker Node の kubelet が static ポリシーで実行されていることを確認します。

oc debug node/<node-name> -- chroot /host cat /etc/kubernetes/kubelet.conf

出力に以下が含まれている必要があります。

cpuManagerPolicy: static
cpuManagerReconcilePeriod: 5s

ステップ 2: 専用 CPU ワークロード用のノードにラベルを付ける

専用 CPU 配置をリクエストする VM は、CPU Manager が実行されているノードのみをターゲットにするために NodeSelector が必要です。Static Policy が有効な各 Worker Node に cpumanager=true ラベルを適用します。

oc label node <node-name> cpumanager=true

ラベルが付与されていることを確認します。

oc get nodes -L cpumanager

期待される出力：

NAME         STATUS   ROLES    AGE   VERSION   CPUMANAGER
worker-01    Ready    worker   10d   v1.34.5   true
worker-02    Ready    worker   10d   v1.34.5   true
KubeVirt CR で CPUManager フィーチャーゲートが有効になっている場合、KubeVirt が自動的に cpumanager=true ラベルを管理できます。有効な場合、KubeVirt は Static CPU manager policy が実行されているノードを検出し、ラベルの付与や削除を自動的に行います。フィーチャーゲートがない場合は、ノードの追加や再設定のたびにこのラベルを手動で管理してください。

ステップ 3: namespace の作成

oc create namespace cpu-pinning-demo

ステップ 4: 専用 CPU 配置で VM をデプロイする

以下の VM 仕様は、dedicatedCpuPlacement: true を使用して 2 つの専用 vCPU をリクエストします。nodeSelector により、VM は cpumanager=true とラベル付けされたノードでのみスケジューリングされます。メモリの requests と limits は同一であり、Guaranteed QoS 要件を満たしています。

この例の cloud-init パスワードはデモンストレーション目的のみです。本番環境では、SSH キー認証または強力でユニークなパスワードを使用してください。

vm-dedicated-cpu.yaml をダウンロード

oc apply -f - <<EOF
apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: vm-dedicated-cpu
  namespace: cpu-pinning-demo
spec:
  runStrategy: Always
  template:
    metadata:
      labels:
        kubevirt.io/domain: vm-dedicated-cpu
    spec:
      nodeSelector:
        cpumanager: "true"
      domain:
        cpu:
          sockets: 2
          cores: 1
          threads: 1
          dedicatedCpuPlacement: true
        memory:
          guest: 1Gi
        resources:
          requests:
            memory: 2Gi
          limits:
            memory: 2Gi
        devices:
          disks:
          - name: rootdisk
            disk:
              bus: virtio
          - name: cloudinitdisk
            disk:
              bus: virtio
          interfaces:
          - name: default
            masquerade: {}
      networks:
      - name: default
        pod: {}
      volumes:
      - name: rootdisk
        containerDisk:
          image: quay.io/containerdisks/fedora:latest
      - name: cloudinitdisk
        cloudInitNoCloud:
          userData: |
            #cloud-config
            password: redhat
            chpasswd:
              expire: false
EOF
QEMU およびハイパーバイザーのオーバーヘッドを考慮し、メモリ制限 (2Gi) はゲストメモリ (1Gi) よりも高く設定されています。KubeVirt がどのように VM のメモリ仕様をコンテナリソース値に変換するかについては、VM Resource Limits と QoS の設定を参照してください。

VM が Running 状態になるまで待ちます。

oc get vm vm-dedicated-cpu -n cpu-pinning-demo -w

期待される出力：

NAME              AGE   STATUS    READY
vm-dedicated-cpu  30s   Running   True

ステップ 5: CPU pinning の確認

ホスト側での確認

VM が実行されているノードを特定します。

oc get vmi vm-dedicated-cpu -n cpu-pinning-demo -o wide

出力例：

NAME              AGE   PHASE     IP            NODENAME    READY
vm-dedicated-cpu  60s   Running   10.128.0.45   worker-01   True

そのノードでデバッグセッションを開きます。

oc debug node/<node-name>

デバッグシェル内で、CPU Manager state file を確認します。このファイルには、各コンテナにどの物理 CPU が割り当てられているかが記録されています。

chroot /host cat /var/lib/kubelet/cpu_manager_state

出力は JSON オブジェクトです。entries マップは virt-launcher Pod の UID をキーとしており、各エントリにはその Pod 内の compute コンテナに排他的に割り当てられた物理 CPU ID がリストされています。

{"policyName":"static","defaultCpuSet":"0-1,3-41,43-79","entries":{"<pod-uid>":{"compute":"2,42"}},"checksum":...}

この例では、CPU 2 と 42 が VM の 2 つの vCPU 専用に予約されています。これらは defaultCpuSet から削除されるため、VM の実行中には他のワークロードがそれらを使用することはできません。

デバッグシェルを終了します。

exit

ゲスト側での確認

VM コンソールに接続します。

virtctl console vm-dedicated-cpu -n cpu-pinning-demo

ユーザー fedora、パスワード redhat でログインします。ゲスト OS 内で認識されている vCPU の数を確認します。

lscpu | grep -E "^CPU\(s\)|^Socket|^Core|^Thread"

期待される出力：

CPU(s):                  2
Thread(s) per core:      1
Core(s) per socket:      1
Socket(s):               2

ゲストは 2 つの vCPU (2 ソケット、1 コア、各 1 スレッド) を認識しており、リクエストされた Topology と一致しています。

Ctrl+] を押してコンソールから切断します。

Emulator Thread の分離

QEMU は、I/O、タイマー、その他のハイパーバイザータスクを処理する Emulator Thread を実行します。デフォルトでは、このスレッドは VM の vCPU と物理 CPU の処理時間を共有するため、遅延のスパイクを引き起こす可能性があります。isolateEmulatorThread オプションは、このスレッド専用に追加の物理 CPU を予約します。

Emulator Thread の分離を有効にするには、VM スペックの CPU セクションに dedicatedCpuPlacement: true と併せて isolateEmulatorThread: true を追加します。

domain:
  cpu:
    sockets: 2
    cores: 1
    threads: 1
    dedicatedCpuPlacement: true
    isolateEmulatorThread: true

この設定により、KubeVirt は合計 3 つの物理 CPU をリクエストします (2 つは vCPU 用、1 つは Emulator Thread 専用) 。エミュレーターに起因するわずかな揺らぎにも敏感なワークロードの場合にこのオプションを使用してください。

Simultaneous Multithreading (SMT) が有効なノードで full-pcpus-only CPU Manager option を使用している場合、偶数の vCPU で isolateEmulatorThread を使用するとスケジューリングエラーが発生することがあります。これを解決するには、KubeVirt CR で AlignCPUs フィーチャーゲートを有効にしてください。

トラブルシューティング

VM が Pending 状態のままになる

スケジューリングの失敗がないか VMI イベントを確認します。

oc describe vmi vm-dedicated-cpu -n cpu-pinning-demo

以下のようなイベントを探します。

Warning  FailedScheduling  0/3 nodes are available: 3 node(s) didn't match Pod's node affinity/selector

考えられる原因と解決策:

  • cpumanager=true ラベル付きノードがない: oc get nodes -L cpumanager を実行し、Static CPU manager policy が適用されているノードにラベルを付与します。

  • 利用可能な固定可能 CPU が不足している: CPU Manager は割り当て可能なプールから CPU を予約します。oc describe node <node-name> でノードのキャパシティを確認し、リクエストを満たすのに十分な CPU があるか検証します。

VM 起動後に CPU pinning が有効にならない

KubeletConfig が正しく適用されたか確認します。

oc get kubeletconfig cpumanager-enabled

MachineConfigPool の状態を確認します。

oc get mcp worker

UPDATED が False または DEGRADED が True の場合、設定は完全に適用されていません。MCO ログを調査してください。

oc logs -n openshift-machine-config-operator -l k8s-app=machine-config-operator --tail=50

VM が "insufficient dedicated CPU resources" でアドミッションに失敗する

このエラーは、dedicatedCpuPlacement: true が設定されているが、QoS クラスが Guaranteed ではないことを意味します。CPU requests と limits が等しいこと、両方が整数値であることを確認してください。

virt-launcher Pod に実際に割り当てられている QoS クラスを確認します。

oc get pod -n cpu-pinning-demo -l kubevirt.io/domain=vm-dedicated-cpu -o jsonpath='{.items[0].status.qosClass}{"\n"}'

値は Guaranteed である必要があります。Burstable の場合は、VM のリソース仕様を見直し、Memory requests と Memory limits が一致していることを確認してください。

cpu_manager_state に VM のエントリが表示されない

CPU Manager state file に virt-launcher Pod の CPU 割り当てがリストされていない場合、ノードの kubelet がまだ none ポリシーで動作している可能性があります。ポリシーを確認します。

oc debug node/<node-name> -- chroot /host cat /etc/kubernetes/kubelet.conf

cpuManagerPolicy が存在しないか none に設定されている場合、KubeletConfig がそのノードにまだ適用されていません。MachineConfigPool のロールアウトが完了するまで待機してください。

クリーンアップ

本チュートリアルで作成した全リソースを削除します。

oc delete namespace cpu-pinning-demo

必要なくなった場合は、ノードから cpumanager=true ラベルを削除します。

oc label node <node-name> cpumanager-

CPU manager policy を元に戻すには、KubeletConfig を削除し、MachineConfigPool からラベルを削除します。

oc delete kubeletconfig cpumanager-enabled
oc label machineconfigpool worker custom-kubelet-
KubeletConfig を削除すると、kubelet 設定を元に戻すために別の MCO ロールアウトがトリガーされます。CPU Manager の動作に依存する追加のワークロードをスケジュールする前に、MachineConfigPool のロールアウトが完了したことを確認してください。

まとめ

このチュートリアルでは、以下の方法を学びました。

  • KubeletConfig リソースを使用して、Kubernetes CPU Manager で static ポリシーを設定する

  • 専用 CPU 配置が利用可能であることを示すノードラベルを付ける

  • dedicatedCpuPlacement: true と Guaranteed QoS を持つ仮想マシンをデプロイする

  • CPU Manager state file を使用して、ホスト側から CPU pinning を確認する

  • ゲスト内から vCPU Topology を確認する

  • 必要に応じて isolateEmulatorThread: true を使用して QEMU Emulator Thread を分離する
